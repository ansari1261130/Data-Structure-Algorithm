# Reverse a Stack (Using Recursion) — FAANG Interview Master Note

> **Problem:** [Reverse a Stack — GeeksforGeeks](https://www.geeksforgeeks.org/problems/reverse-a-stack/1)
> **Primary Pattern:** Pop → Reverse Remaining → Insert at Bottom
> **Secondary Patterns:** Remove-Recurse-Restore · Call-Stack-as-Buffer · Building a Missing ADT Operation
> **Difficulty:** Medium · **Interview Difficulty:** Easy code, tests whether you truly *own* the idiom
> **Asked By:** Amazon, Microsoft, Adobe, Morgan Stanley, Oracle, Samsung, Flipkart

```text
   MEMORY HOOK FOR THIS ENTIRE PROBLEM

   TWO FUNCTIONS, TWO MANTRAS:

   reverseStack()    ->   POP  ->  REVERSE REST  ->  INSERT AT BOTTOM
   insertAtBottom()  ->   POP  ->  RECURSE       ->  PUSH BACK

   +--------------------------------------------------------------+
   |   THE ONE IDEA:                                              |
   |   push() only reaches the TOP.                               |
   |   The bottom is unreachable...                               |
   |   ...UNLESS you empty the stack first.                       |
   |                                                              |
   |   So: BUILD the operation the ADT refuses to give you.       |
   +--------------------------------------------------------------+

   SIBLING PROBLEM: "Sort a Stack" — IDENTICAL skeleton.
   ONLY the helper's base case changes:
        sort    -> stop at the RIGHT POSITION   (peek() <= e)
        reverse -> stop only at the BOTTOM      (isEmpty())
```

### Missing Concepts

- **`Θ(n²)`, not just `O(n²)`** — the cost is `0+1+2+…+(n−1)` *regardless of input*, because
  `insertAtBottom` never short-circuits. **This is the key contrast with Sort a Stack.**
- **The `O(n)` solution** using an auxiliary list (and why the pop-order refill works).
- **`Collections.reverse(stack)`** — legal on `java.util.Stack` because it extends `Vector`
  implements `List`. `O(n)`, one line. A great "know your library" moment.
- **The iterative version** with an explicit auxiliary structure.
- **`insertAtBottom` vs `insertInSortedPosition`** — identical code, different base case.
  Seeing this makes both problems one problem.
- **Correctness by induction** for both functions.
- **Stack-overflow ceiling** at `O(n)` depth (~10⁴ in Java).
- **Tower of Hanoi connection** — move blockers aside, act, restore.
- The fact that reversing is **its own inverse** — applying it twice restores the original
  (a free property test).

### Missing Interview Patterns

- **Building a missing ADT operation** — the stack has no `pushToBottom`, so you synthesise it

- **Base-case-defines-behaviour** — the two helpers differ *only* in when they stop. Change the

- **Involution / self-inverse operation** — reverse twice is identity, which gives you a free

- **Tower of Hanoi shape** — relocate obstructions, perform one move, restore.

## 1) Core idea

Given a stack, reverse it using recursion.

Example:

```text
Original stack: [1, 2, 3, 4]
TOP = 4
```

After reversing:

```text
[4, 3, 2, 1]
TOP = 1
```

Important requirement:

- use recursion
- do not use another stack

## 2) First observation

The key question is:

```text
What does reversing a stack actually mean?
```

Suppose:

```text
[1, 2, 3, 4]
      ↑
     TOP
```

If we pop:

```text
4
```

then the remaining stack becomes:

```text
[1, 2, 3]
```

If we recursively reverse that stack, we get:

```text
[3, 2, 1]
```

Now the removed value 4 must go to the bottom:

```text
[4, 3, 2, 1]
```

So the real operation is:

```text
Pop one element
→ reverse remaining stack
→ insert removed element at bottom
```

---

## 3) Important difference from sort stack

In Sort Stack, we insert the element at its correct sorted position.

Here, in Reverse Stack, we always insert at the bottom.

So:

- Sort Stack: value-based insertion
- Reverse Stack: bottom insertion

This is the main difference.

## 14) Final Java code

```java
class Solution {

    public static void reverseStack(Stack<Integer> st) {

        if (st.isEmpty()) {
            return;
        }

        int element = st.pop();

        reverseStack(st);

        insertElement(st, element);
    }

    private static void insertElement(Stack<Integer> st, int element) {

        if (st.isEmpty()) {
            st.push(element);
            return;
        }

        int remove = st.pop();

        insertElement(st, element);

        st.push(remove);
    }
}
```

## 28) ADDED — It is `Θ(n²)`, not just `O(n²)` (and why that differs from Sort a Stack)

Your `O(n²)` is right, but the truth is sharper and it's the best observation available on
this problem.

```text
   insertAtBottom ALWAYS travels the ENTIRE depth.
   It has NO early exit. Its only stopping condition is isEmpty().

   Cost of insertAtBottom on a stack of size k  =  EXACTLY k pops + k pushes.
                                                   Never fewer. Never more.

   TOTAL  =  0 + 1 + 2 + ... + (n-1)  =  n(n-1)/2   ALWAYS

   => BEST = AVERAGE = WORST = Theta(n^2)
```

```text
   THE CONTRAST WITH SORT A STACK — say this out loud, it lands hard

   +---------------------+---------------------------+--------------------------+
   |                     | SORT A STACK              | REVERSE A STACK          |
   +---------------------+---------------------------+--------------------------+
   | Helper stops when   | peek() <= element         | isEmpty()                |
   |                     | (a VALUE condition)       | (a POSITION condition)   |
   +---------------------+---------------------------+--------------------------+
   | Can it short-circuit| YES — if the element      | NO — the bottom is       |
   | early?              | belongs on top, O(1)      | always n levels down     |
   +---------------------+---------------------------+--------------------------+
   | Best case           | O(n)  (already sorted)    | Theta(n^2)  — NO best    |
   | Worst case          | O(n^2)                    | Theta(n^2)               |
   +---------------------+---------------------------+--------------------------+
   | Input-sensitive?    | YES                       | NO — input never matters |
   +---------------------+---------------------------+--------------------------+

   WHY: sorting asks "where does this belong?" — the answer can be "right here".
        reversing asks "get to the bottom" — the answer is always "all the way".
```

> **Interview line:** *"Note this is `Θ(n²)`, not merely `O(n²)` — unlike the sort variant,
> `insertAtBottom` can never short-circuit, because its base case is positional (`isEmpty`)
> rather than value-based. So even an already-reversed or all-duplicates input costs the full
> `n(n−1)/2` operations. The running time is completely input-insensitive."*

## 29) ADDED — The `O(n)` solutions (and the one-line library answer)

Recursion-only forces `Θ(n²)`. **If auxiliary storage is permitted, `O(n)` is easy** — and you
should always say so.

### Option A — auxiliary list, refill in pop order (`O(n)` time, `O(n)` space)

```java
public static void reverseStackLinear(Deque<Integer> st) {
    List<Integer> buffer = new ArrayList<>(st.size());

    while (!st.isEmpty()) {
        buffer.add(st.pop());          // buffer = top-to-bottom order
    }
    for (int v : buffer) {
        st.push(v);                    // pushing in that SAME order reverses it
    }
}
```

**Why pushing in pop order reverses the stack** — this is the neat part:

```text
   START (bottom -> top):  [1, 2, 3, 4]        top = 4

   POP PHASE  -> buffer = [4, 3, 2, 1]         (top-to-bottom order)

   PUSH PHASE (iterate buffer left to right):
        push 4  ->  [4]
        push 3  ->  [4, 3]
        push 2  ->  [4, 3, 2]
        push 1  ->  [4, 3, 2, 1]               top = 1

   RESULT: [4, 3, 2, 1]   ✓  REVERSED

   The trick: popping reads top->bottom, pushing writes bottom->top.
   Doing both in the SAME sequence flips the orientation exactly once.

   2n operations total  ->  O(n)     vs  n(n-1)/2  ->  Theta(n^2)
```

### Option B — the one-liner (know your library)

```java
Collections.reverse(stack);     // works on java.util.Stack. O(n).
```

```text
   WHY THIS IS LEGAL:
        java.util.Stack  extends  Vector  implements  List

   So a Stack IS a List, and Collections.reverse works on it directly,
   reversing the underlying element order in O(n).

   ⚠ This does NOT work on ArrayDeque — Deque is not a List.

   Say this as an aside: "In production I'd just call Collections.reverse.
   I assume the point of the exercise is the recursive technique?"
   That one sentence shows library knowledge AND respect for the exercise.
```

### Option C — iterative, no recursion (no stack-overflow risk)

```java
public static void reverseStackIterative(Deque<Integer> st) {
    Deque<Integer> temp = new ArrayDeque<>();
    while (!st.isEmpty()) temp.push(st.pop());   // temp is now reversed...
    // temp already holds the reversed order relative to st's original bottom-up view
    while (!temp.isEmpty()) st.push(temp.pop()); // ...but this reverses it BACK
    // NOTE: one transfer reverses; TWO transfers restore. Use ONE buffer + direct refill:
}
```

> **Careful — the classic bug:** transferring a stack to another stack reverses it **once**.
> Transferring it *back* reverses it **again**, returning you to the original. Use **Option A**
> (list + refill in pop order), or transfer once and treat the *temp* stack as the answer.
> This off-by-one-reversal is a genuinely common interview slip.

### Honest complexity comparison

```text
   +---------------------------------+--------------+-------------------+----------+
   | APPROACH                        |   TIME       |   SPACE           | RECURSION|
   +---------------------------------+--------------+-------------------+----------+
   | Recursive insertAtBottom (this) | Theta(n^2)   | O(n) call stack   | yes      |
   | Auxiliary list + refill         | O(n)         | O(n) heap         | no       |
   | Collections.reverse             | O(n)         | O(1)              | no       |
   | Two-stack transfer (once)       | O(n)         | O(n) heap         | no       |
   +---------------------------------+--------------+-------------------+----------+

   ALWAYS SAY: "The Theta(n^2) is the price of the 'recursion only, no extra
   data structure' constraint. With O(n) auxiliary space it's O(n)."
```

## 30) ADDED — `insertAtBottom` vs `insertInSortedPosition`: one function, two base cases

This is the insight that collapses **two problems into one**.

```java
// REVERSE a stack — stop only when the stack is EMPTY (positional)
void insertAtBottom(Deque<Integer> st, int e) {
    if (st.isEmpty()) { st.push(e); return; }          // <-- base case
    int remove = st.pop();
    insertAtBottom(st, e);
    st.push(remove);
}

// SORT a stack — stop at the correct POSITION (value-based)
void insertInSortedPosition(Deque<Integer> st, int e) {
    if (st.isEmpty() || st.peek() <= e) { st.push(e); return; }   // <-- base case
    int remove = st.pop();
    insertInSortedPosition(st, e);
    st.push(remove);
}
```

```text
   LOOK AT WHAT IS IDENTICAL:

       int remove = st.pop();
       recurse(st, e);
       st.push(remove);

   LINE FOR LINE THE SAME. Only the BASE CASE differs.

   +-------------------------------------------------------------------+
   |  THE BASE CASE IS THE ALGORITHM.                                  |
   |  The recursive body is just "dig and restore" — pure mechanism.   |
   |  WHERE YOU STOP DIGGING is the entire behavioural difference.     |

       stop at isEmpty()          -> element lands at the BOTTOM  -> REVERSE
       stop at peek() <= e        -> element lands IN ORDER       -> SORT
```

# PHASE 2 — CONCEPT REBUILDING

## CONCEPT 1: Building a Missing ADT Operation

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because the stack ADT gives you exactly four operations — `push`, `pop`,
`peek`, `isEmpty` — and **none of them touch the bottom**. The operation you need
(`pushToBottom`) simply does not exist. So you build it.

```text
   WHAT YOU HAVE                    WHAT YOU NEED
   -------------                    -------------
   push(x)  -> adds at TOP          pushToBottom(x) -> adds at BOTTOM
   pop()    -> removes from TOP                        ✗ DOESN'T EXIST
   peek()   -> reads TOP
   isEmpty()

   THE ONLY WAY TO REACH THE BOTTOM:
        make the bottom become the top — by removing everything above it.
        And "everything above it" is the WHOLE stack.

   So: empty the stack, push at the (now reachable) bottom, put everything back.
```

**What problem does it solve?** It turns "the interface doesn't support this" into "I'll
compose it from what the interface does support" — which is the essence of software design.

**When to use it:** Any time a restricted structure lacks the operation you need, but the
operation is *expressible* in terms of the ones you have.

### LEVEL 2 — Mental Visualization

```text
   THE WHOLE ALGORITHM, TWO PHASES

   PHASE 1 — TEAR DOWN (reverseStack recursion)

     [1,2,3,4]  pop 4 ──┐
     [1,2,3]    pop 3 ──┤   each value parked in its own
     [1,2]      pop 2 ──┤   stack frame's local variable
     [1]        pop 1 ──┤
     []         BASE ───┘

   PHASE 2 — BUILD UP (each value inserted at the BOTTOM)

     []              insertAtBottom 1  -> [1]
     [1]             insertAtBottom 2  -> [2,1]
     [2,1]           insertAtBottom 3  -> [3,2,1]
     [3,2,1]         insertAtBottom 4  -> [4,3,2,1]     ✓ REVERSED

   WHY THIS REVERSES:
       The FIRST element popped (4, the original top) is the LAST one
       inserted — and it goes to the BOTTOM. So the original top ends up
       at the bottom. That is exactly a reversal.
```

**The stack drawn vertically (top really at the top):**

```text
   BEFORE                 AFTER
   +-----+                +-----+
   |  4  | <- TOP         |  1  | <- TOP
   +-----+                +-----+
   |  3  |                |  2  |
   +-----+                +-----+
   |  2  |                |  3  |
   +-----+                +-----+
   |  1  |                |  4  |
   +-----+                +-----+
    BOTTOM                 BOTTOM

   Top and bottom have swapped ends. Everything flipped.
```

**`insertAtBottom([1,2,3], 4)` — the full dig, step by step:**

```text
   GOAL: get 4 UNDER 1, 2 and 3.

   depth 0   +-----+
             |  3  | <- top    not empty -> pop 3, remember it in frame 0
             +-----+
             |  2  |
             +-----+
             |  1  |
             +-----+

   depth 1   +-----+
             |  2  | <- top    not empty -> pop 2, remember it in frame 1
             +-----+
             |  1  |
             +-----+

   depth 2   +-----+
             |  1  | <- top    not empty -> pop 1, remember it in frame 2
             +-----+

   depth 3    (empty)          BASE CASE -> push 4

             +-----+
             |  4  |
             +-----+

   ===== UNWIND — frames push their values back, LIFO =====

   frame 2 pushes 1   ->  [4,1]
   frame 1 pushes 2   ->  [4,1,2]
   frame 0 pushes 3   ->  [4,1,2,3]        ✓ 4 is at the bottom

   The blockers returned in the CORRECT ORDER automatically,
   because the call stack unwinds last-in-first-out.
```

**Why `push(remove)` must come after the recursive call:**

```text
   int remove = st.pop();     // 1. lift the blocker
   insertAtBottom(st, e);     // 2. dig deeper
   st.push(remove);           // 3. put the blocker back

   ┌────────────────────────────────────────────────────────────┐
   │  Swap lines 2 and 3 and you push the blocker back BEFORE    │
   │  you have dug — the stack returns to its previous state,    │
   │  nothing changes, and you recurse forever.                  │
   │                                                             │
   │  The restoration MUST be work-after-the-call.               │
   │  That is exactly why this is NOT tail recursion.            │
   └────────────────────────────────────────────────────────────┘
```

### LEVEL 3 — Real-World Analogy

> **A tube of Pringles.** You want to put a new crisp at the **bottom**. There is only one
> opening. So you take every crisp out (holding them in order), drop the new one in, and put
> them all back. That is `insertAtBottom`, exactly.

> **A single-lane garage.** To park a car at the back, every car already inside must reverse
> out onto the street, then drive back in afterwards. The street is the call stack.

> **A stack of plates in a cafeteria dispenser.** Only the top plate is reachable. To slip a
> plate underneath, you lift the whole column.

> **Reversing the queue at a ticket counter** by sending everyone out of the door and letting
> them back in from the other end — the first person out becomes the last person in.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The difficulty is that `push` only reaches the top, but reversing requires the old top to
> end up at the bottom. The stack ADT has no `pushToBottom`, so I build it: to reach the
> bottom, I pop everything — each frame holding one value in a local — and once the stack is
> empty, the bottom *is* the top, so I push there and let the unwinding frames restore the rest
> in LIFO order. Then the main function is just: pop one element, recursively reverse the rest,
> and insert that element at the bottom. Because the first element popped is the last one
> inserted at the bottom, the whole stack flips. It's `Θ(n²)` since each insertion must travel
> the full depth, and `O(n)` call-stack space."*

## CONCEPT 2: Why This Reverses (Correctness)

### LEVEL 1 — Beginner Intuition

The reversal isn't obvious. Here's the one-sentence reason:

```text
   THE FIRST ELEMENT REMOVED IS THE LAST ELEMENT PLACED — AND IT IS
   PLACED AT THE BOTTOM.

   original TOP     -> popped FIRST  -> inserted LAST  -> ends at the BOTTOM
   original BOTTOM  -> popped LAST   -> inserted FIRST -> ends at the TOP

   Both ends swap. Everything between swaps symmetrically. That is a reversal.
```

### LEVEL 2 — Mental Visualization

```text
   TRACKING ONE ELEMENT (the original top, 4) THROUGH THE ALGORITHM

   [1,2,3,4]
         ^ 4 is the TOP

   pop 4          -> 4 parked in the OUTERMOST frame
   ...            -> everything else is reversed first
   [3,2,1]        -> the rest has been fully reversed
   insertAtBottom(4)
   [4,3,2,1]
    ^ 4 is now the BOTTOM                          ✓

   The outermost frame resumes LAST, so its value is placed LAST,
   and insertAtBottom puts it at the deepest position.
   FIRST OUT = LAST IN = DEEPEST.  That is the reversal.
```

**Proof by induction (say this if asked — it's short):**

```text
   CLAIM A: insertAtBottom(st, e) places e below every existing element.
     BASE: st empty -> push(e). e is the only element, so trivially at the bottom. ✓
     STEP: st non-empty. Pop the top t. By hypothesis the recursive call puts e
           below everything in the smaller stack. Pushing t back places it ABOVE
           all of them — and t was already above all of them. Order preserved,
           e still at the bottom.                                              ∎

   CLAIM B: reverseStack(st) reverses st.
     BASE: n = 0. Empty stack is its own reversal.                             ✓
     STEP: Assume correct for n-1. Let st = [b ... t] with top t.
           1. pop t            -> stack is [b ... ] of size n-1
           2. reverseStack     -> by hypothesis it is now reversed
           3. insertAtBottom t -> by CLAIM A, t goes below everything
           The original top t is now the bottom, and the rest is reversed.
           That is precisely the reversal of st.                               ∎
```

### LEVEL 3 — Real-World Analogy

> **Unloading and reloading a lift (elevator) from the other side.** Everyone exits through the
> front; then they re-enter through a rear door. The person who exited first walks in first —
> but from the *other end* — so they end up furthest back. First out, deepest in.

> **A railway siding.** Reverse the carriages out one at a time and re-attach each one to the
> *far* end of the new train. The engine that left first ends up at the tail.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The reversal works because of an ordering inversion: the first element popped is the last
> element inserted, and every insertion goes to the bottom. So the original top is placed last,
> at the deepest position, and the original bottom is placed first, ending at the top. Formally
> I'd prove it in two steps — first that `insertAtBottom` really does place the element below
> everything while preserving the relative order of the rest, then induction on the stack size
> for the main function, using that as the inductive step."*

## CONCEPT 3: The Base Case Is the Algorithm

### LEVEL 1 — Beginner Intuition

**Why does it matter?** Because `Sort a Stack` and `Reverse a Stack` have **byte-identical
recursive bodies**. The only thing that differs is *when you stop digging* — and that single
condition changes the entire behaviour.

```text
   THE SHARED MECHANISM (the "digging engine")

       int remove = st.pop();     // lift
       recurse(st, e);            // dig
       st.push(remove);           // restore

   THE VARIABLE PART (the "policy")

       stop at isEmpty()        -> bottom        -> REVERSE
       stop at peek() <= e      -> sorted slot   -> SORT
       stop at counter == 0     -> depth k       -> INSERT AT DEPTH k
```

### LEVEL 2 — Mental Visualization

```text
   ONE ENGINE, FOUR ALGORITHMS

                        +---------------------------+
                        |   int r = st.pop();       |
                        |   recurse(...);           |  <- IDENTICAL in all four
                        |   st.push(r);             |
                        +---------------------------+
                                     ^
                                     |
           +-------------+-----------+-----------+-------------+
           |             |                       |             |
     isEmpty()     peek() <= e             k == 0        peek() == x
           |             |                       |             |
        REVERSE        SORT              INSERT AT DEPTH k   INSERT ABOVE x
     insertAtBottom  insertSorted           deleteMid        conditional
           |             |                       |             |
      Theta(n^2)     O(n) best              O(n)            depends
      NO early exit  O(n^2) worst
                     CAN exit early


   +------------------------------------------------------------------+
   | MEMORISE ONE ENGINE. SWAP THE BASE CASE. GET A DIFFERENT PROBLEM.|
   +------------------------------------------------------------------+
```

### LEVEL 3 — Real-World Analogy

> **A drill with interchangeable bits.** The motor (the recursive body) is always the same;
> the bit (the base case) decides whether you're making a hole, driving a screw, or sanding.
> Learn the motor once.

> **A lift with a destination button.** The mechanism for moving between floors never changes.
> Which button you press decides where you stop — and that's the whole difference between
> "go to the basement" and "go to the floor where you belong".

### LEVEL 4 — Interview Explanation (30 seconds)

> *"I think of these stack-recursion problems as one engine with a swappable stopping rule. The
> body — pop the blocker, recurse, push it back — is identical across sort, reverse, delete-
> middle and insert-at-depth. What changes is the base case: stopping at `isEmpty()` drives the
> element to the bottom and gives a reversal; stopping at `peek() <= element` gives a sorted
> insert; stopping at a counter gives insertion at a fixed depth. That's also why reverse is
> `Θ(n²)` while sort has an `O(n)` best case — a positional base case can't short-circuit, but
> a value-based one can."*

## CONCEPT 4: The Cost of a Constraint

### LEVEL 1 — Beginner Intuition

Reversing a stack is *intrinsically* an `O(n)` job — you touch each element a constant number
of times. The `Θ(n²)` here is **entirely** the price of the artificial constraint "recursion
only, no extra data structure."

```text
   WITH AUXILIARY SPACE:   pop all into a list, push back in pop order.
                           2n operations.  O(n).

   WITHOUT:                every element must be re-dug to the bottom.
                           n(n-1)/2 operations.  Theta(n^2).

   THE CONSTRAINT COSTS YOU A FACTOR OF n.
```

### LEVEL 2 — Mental Visualization

```text
   OPERATION COUNT, SIDE BY SIDE

   n = 1,000

   O(n)      approach :        2,000 operations      ~instant
   Theta(n^2) approach:      499,500 operations      still fast
   n = 100,000
   O(n)      approach :      200,000 operations      instant
   Theta(n^2) approach: 4,999,950,000 operations     ~minutes
                                                     (and it overflows the
                                                      call stack long before)

   +-----------------------------------------------------------------+
   | The recursive solution is a TEACHING exercise about the call    |
   | stack. It is NOT what you would ship. Say so — explicitly.      |
   +-----------------------------------------------------------------+
```

### LEVEL 3 — Real-World Analogy

> **Moving house without a van.** You *could* carry everything one item at a time, walking back
> and forth. It works. It's also `O(n)` trips instead of one. The van (auxiliary memory) is
> cheap; refusing to use it is a deliberate exercise, not an optimisation.

> **A one-lane bridge.** Traffic still flows, but every crossing blocks the others. The
> constraint — not the traffic — sets the throughput.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"I want to be explicit about the trade-off: reversing a stack is fundamentally an `O(n)`
> operation — with an auxiliary list I'd pop everything and push it back in pop order, which
> reverses it in `2n` steps. The `Θ(n²)` comes entirely from the constraint that I may only use
> recursion and no extra data structure, which forces every element to be re-dug to the bottom.
> So the recursive version is the right answer to *this exercise*, but in production I'd use
> `Collections.reverse` or a buffer. Should I treat the no-extra-space constraint as strict?"*

## 2. STORY METHOD

### The Master Story: **THE PRINGLES TUBE**

> You have a tube of crisps, numbered 1 at the bottom through 4 at the top. Your task: **turn
> the whole tube upside down** — but the tube has **one opening**, you may only take the top
> crisp, and **you are given no second tube, no bowl, no table.**
>
> **The wrong idea first.** *"Easy — I'll take the top crisp out, flip the rest somehow, then
> put it back."* You take out crisp 4, flip the remaining three to get 3-2-1, and drop 4 back
> in. But it lands **on top**: `[3,2,1,4]`. Wrong. **`push` always lands on top — that is the
> entire difficulty of this problem.**
>
> **The realisation.** Crisp 4 doesn't belong on top; it belongs at the **very bottom**. But
> the bottom is unreachable... *unless the tube is empty.* So you invent an operation the tube
> never offered you: **"insert at bottom."**
>
> **How you insert at the bottom.** You take out crisp 3 and hold it. Then 2. Then 1. Now your
> hands hold three crisps **in a definite order**, and the tube is empty — which means the
> bottom is finally reachable. You drop crisp 4 in. Then you put back 1, then 2, then 3 —
> and because your hands release in the reverse of the order you picked them up, they go back
> **exactly as they were**, now sitting on top of 4.
>
> **Your hands are the call stack.** You were never without storage; you just weren't allowed
> to *name* it.
>
> **The expensive truth.** Every single crisp has to be driven all the way to the bottom. There
> is no shortcut, no "oh, this one already belongs here" — unlike sorting, where a crisp can
> sometimes stop immediately. That's why this is **`Θ(n²)` always**: the bottom is always the
> full depth away.
>
> **The van you refused.** If someone hands you a **bowl**, you tip all four crisps out and
> drop them back in, in the order they came out — and the tube is reversed in one pass. `O(n)`.
> The quadratic cost was never the problem's fault; it was the **constraint's** price.

```text
   THE TUBE                  YOUR HANDS (call stack)
   ========                  =======================
   [1,2,3,4]                       (empty)
   []                        4,3,2,1  <- tear-down complete
   [4,3,2,1]                       (empty)  <- reversed ✓
```

### Mini-story: **Why you can't just push it back**

> A man tries to put a new card at the **bottom** of a deck by placing it on **top** and hoping.
> It is at the top. It will always be at the top. `push` has exactly one destination.

### Mini-story: **The two drills**

> A builder owns one drill motor and two bits. With the **basement bit** he always bores to the
> very bottom — slow, fixed cost, every time. With the **depth-gauge bit** he stops as soon as
> the depth is right — sometimes instantly. Same motor. The bit is the base case, and it alone
> decides whether the job is `Θ(n²)` or sometimes `O(n)`.

### Mini-story: **Reverse twice**

> Stand between two mirrors facing each other and your reflection is reversed — then reversed
> back. `reverse(reverse(s)) == s`. That's a free unit test you get for nothing.

```text
   USE WHEN:

   ✓ The ADT exposes only ONE end (stack: top; queue: front)
   ✓ You must place/remove something at the OTHER end
   ✓ The operation you need DOESN'T EXIST in the interface
   ✓ The problem says "recursion only" / "no extra data structure"
   ✓ Everything must be restored exactly as it was, except your change

   DO NOT USE WHEN:

   ✗ Auxiliary space is allowed -> a buffer gives O(n) instead of O(n^2)
   ✗ n is large (~10^4+) -> stack overflow
   ✗ The structure is a List/array -> you have random access; just use it
   ✗ A library call exists (Collections.reverse) and the exercise permits it
```

## WHEN TO USE: Remove → Recurse → Restore

```text
   ✓ You must dig past obstructions to reach a target position
   ✓ The obstructions must come back in their ORIGINAL order (LIFO = free)
   ✓ The structure must be left intact apart from the intended change
   ✓ You're doing backtracking (remove -> try -> restore is the same shape)
```

# PHASE 8 — FAANG FOLLOW-UP QUESTIONS

**Q1. "Can you reverse it in `O(n)`?"**
Yes — **if auxiliary space is allowed**. Pop everything into an `ArrayList`, then push back in
**pop order** (§29). That's `2n` operations. The `Θ(n²)` comes purely from the
"no extra data structure" constraint, not from the problem itself. Always state this.

**Q2. "Why is there no best case, when Sort a Stack has one?"**
Because `insertAtBottom`'s base case is **positional** (`isEmpty()`), not value-based. It can
never stop early — the bottom is always the full depth away. Sort's helper stops at
`peek() <= element`, which can be true immediately, giving `O(n)` on already-sorted input.
So reverse is `Θ(n²)` and completely input-insensitive. **This is the sharpest observation
available on this problem.**

**Q3. "Do it iteratively."**
Pop everything into a buffer and push back in pop order (§29 Option A). Careful with the
classic bug: transferring stack → stack reverses **once**, and transferring back reverses
**again**, restoring the original. Transfer once, or use a list.

**Q4. "What happens with 100,000 elements?"**
`StackOverflowError`. Depth is `O(n)` for `reverseStack` plus up to `O(n)` for `insertAtBottom`
— still `O(n)` simultaneously, but Java's ~512 KB–1 MB stack fails around 10⁴ frames. Also,
`n(n−1)/2 ≈ 5×10⁹` operations would be far too slow anyway. Use the `O(n)` buffer version.

**Q5. "How does this relate to Sort a Stack?"**
They are the **same algorithm with different base cases**. The recursive body — `pop`,
`recurse`, `push back` — is identical line for line. `isEmpty()` drives the element to the
bottom (reverse); `peek() <= e` drives it to its sorted slot (sort). §30 shows them side by
side.

**Q6. "Prove it's correct."**
Two inductions (Concept 2). First: `insertAtBottom` places `e` below everything while
preserving the relative order of the rest. Second: induction on size for `reverseStack`, using
the first claim in the inductive step. Key line: *the original top is popped first and inserted
last, at the bottom.*

**Q7. "Reverse only the bottom `k` elements."**
Dig down `k` levels with a counter (holding the top `n−k` in frames), reverse the remaining
sub-stack, then restore. Alternatively pop `n−k` into a buffer, reverse the rest, and push
back. `O(n + k²)` recursively.

**Q8. "Reverse a queue instead."**
`dequeue` the front, recursively reverse the rest, then `enqueue` that element at the **back**.
Because a queue appends at the back, no helper is needed — the enqueue *is* the
"insert at the far end". That makes it `O(n)`, not `O(n²)` — a nice asymmetry to point out.

**Q9. "How would you test this?"**
The free property test: **`reverse(reverse(s)) == s`** — reversal is an involution. Plus:
empty, single, two elements, duplicates, a large random stack compared against
`Collections.reverse`, and a multiset check (same elements, none lost or duplicated).

**Q10. "What's the minimum number of push/pop operations needed?"**
With a buffer, `2n` (each element popped once, pushed once) — provably optimal, since every
element must move. The recursive version uses `n(n−1)` push/pop pairs, roughly `n/2` times more
than necessary. Good way to quantify the constraint's cost.

**Q11. "Can you do it with `O(1)` extra space and no recursion?"**
Not through a pure stack interface. Any reordering needs somewhere to hold removed elements.
If you could access the **underlying array**, you'd swap ends in `O(n)`/`O(1)` — but that
breaks the abstraction. Knowing *why* it's impossible is worth as much as an algorithm.

**Q12. "Why does `Collections.reverse` work on a `Stack`?"**
`java.util.Stack extends Vector implements List`, so a `Stack` *is* a `List` and
`Collections.reverse` reverses the backing element order in `O(n)`. It does **not** work on
`ArrayDeque`, which isn't a `List`. A nice "know your library" point — but say you assume the
exercise wants the recursive technique.

**Q13. "Why must `push(remove)` come after the recursive call?"**
Because the blocker was lifted specifically to allow digging. Pushing it back first restores
the obstruction, the state is unchanged, and you recurse forever. This is also why the function
is deliberately **not** tail-recursive — the restoration is work-after-the-call.

**Q14. "What if the stack holds objects?"**
Nothing changes — reversal never compares values, it only moves them. This is actually a *nice*
contrast with Sort a Stack, which needs a `Comparator`. Reversal is **type-agnostic**.

**Q15. "Is the relative order of duplicates preserved?"**
Reversal reverses *everything*, including equal elements, so duplicates appear in reversed
relative order. That's correct by definition — but worth stating precisely if the elements are
objects with identity.

**Q16. "Convert the recursion into an explicit state machine."**
Replace each frame with a record holding the local `element` plus a resume point, driven by an
explicit `ArrayDeque`. This mirrors what the JVM does and proves you understand that recursion
*is* a stack. It also removes the overflow ceiling.

**Q17. "Can this be parallelised?"**
Not usefully. Each `insertAtBottom` depends on the fully reversed state of the smaller stack,
and the stack is a single contention point. The `O(n)` buffer version is trivially
parallelisable in the copy phase, but at `O(n)` there's nothing to gain.

**Q18. "What's the recursion depth exactly?"**
`reverseStack` reaches depth `n`. At depth `d`, `insertAtBottom` adds up to `n−d` more frames.
The maximum **simultaneous** depth is `O(n)` — the two recursions are sequential, not
multiplicative. (Candidates often wrongly say `O(n²)` space.)

**Q19. "Where does this idiom appear in real systems?"**
Undo/redo, backtracking search (`choose → explore → un-choose` is exactly
remove-recurse-restore), transaction rollback, DFS traversal, expression evaluation, and
browser history. The "restore on unwind" discipline is the heart of backtracking.

**Q20. "Reverse a stack using exactly two stacks, iteratively."**
Transfer from `A` to `B` — that reverses **once**. `B` is now the answer. The trap: transferring
back to `A` reverses again and undoes it. If you must end up in the original object, use a
third transfer (three reversals = one net reversal) or a list buffer.

**Q21. "What if elements arrive as a stream and you must keep a reversed view?"**
Maintain a second structure that appends at the opposite end — that's exactly a **deque**. With
an `ArrayDeque` you get both orders in `O(1)` per element, making the whole problem disappear.
Recognising that the right data structure eliminates the problem is a strong signal.

**Q22. "Compare the call stack with an explicit stack."**
Same LIFO semantics, very different limits: the call stack is ~512 KB–1 MB (≈10⁴ frames) and
carries per-frame overhead (return address, saved registers); an explicit `ArrayDeque` lives on
the heap (gigabytes, millions of elements) and stores only your data. Same algorithm, three
orders of magnitude difference in capacity.

**Q23. "Can you reverse in place if it's backed by an array?"**
Yes — two pointers, swap ends, `O(n)` time and `O(1)` space. But that requires breaking the
stack abstraction and touching the backing store. It's the right answer *if* you own the
implementation, and the wrong answer if you only have the ADT.

**Q24. "How does the two-stack queue relate to this?"**
`LC 232` relies on exactly the same fact you're using: **transferring a stack into another
stack reverses the order.** One reversal turns LIFO into FIFO. Your problem applies the same
inversion; theirs exploits it to build a different ADT.

**Q25. "If you could add one method to the stack ADT, what would it be?"**
`pushToBottom` — or better, expose it as a **deque**, which gives `addFirst`/`addLast` and makes
reversal `O(n)` trivially. That's exactly why `ArrayDeque` exists and why the JDK deprecated
`Stack` in favour of `Deque`. Good design-thinking answer.

# PHASE 10 — REVISION SECTIONS

## 2-MINUTE REVISION

```text
   TWO FUNCTIONS, TWO MANTRAS

   reverseStack(st)                    insertAtBottom(st, e)
   ----------------                    ---------------------
   if empty -> return                  if empty -> push(e), return
   e = pop()                           remove = pop()
   reverseStack(st)    <- FLIP REST    insertAtBottom(st, e)  <- DIG
   insertAtBottom(st,e)<- NOT push()!  push(remove)           <- RESTORE AFTER

   POP -> REVERSE REST -> INSERT AT BOTTOM     POP -> RECURSE -> PUSH BACK

   WHY push() FAILS:  push always lands on TOP. You need the BOTTOM.
                      [1,2,3,4] -> pop 4 -> reverse -> [3,2,1] -> push 4
                      gives [3,2,1,4]  ✗   need [4,3,2,1]  ✓

   WHY IT REVERSES:   FIRST OUT = LAST IN = DEEPEST.
                      Original top is popped first, inserted last, at the bottom.

   COMPLEXITY   Time  Theta(n^2)  — NO best case, input-INSENSITIVE
                      (insertAtBottom can never short-circuit)
                Space O(n) call stack — NOT O(1), NOT O(n^2)

   VS SORT A STACK:   identical body; only the base case differs
                      isEmpty()      -> bottom  -> REVERSE  -> Theta(n^2)
                      peek() <= e    -> sorted  -> SORT     -> O(n) best

   IF UNCONSTRAINED:  pop all to a list, push back in POP ORDER -> O(n)
                      or Collections.reverse(stack)  (Stack IS a List)

   HOOK: THE PRINGLES TUBE — empty it to reach the bottom.
```

## 10-MINUTE REVISION

**The failed idea you must remember (it's the whole lesson)**

```text
   [1,2,3,4]  ->  pop 4  ->  reverse rest  ->  [3,2,1]  ->  push(4)
                                                             ^^^^^^^
                                                             lands on TOP
   RESULT: [3,2,1,4]   ✗
   WANTED: [4,3,2,1]   ✓

   => the popped element must be inserted at the BOTTOM
   => the stack ADT has no pushToBottom()
   => so BUILD it
```

**How `insertAtBottom` works**

```text
   To reach the bottom, make the bottom become the top:
   pop EVERYTHING (each value parked in a frame), push at the empty stack,
   then let the frames restore the blockers on unwind — LIFO, so the
   original order is preserved automatically.

   insertAtBottom([1,2,3], 4):
       pop 3, pop 2, pop 1   -> empty
       push 4                -> [4]
       push 1, push 2, push 3 -> [4,1,2,3]    ✓
```

**Why `push(remove)` is last**

```text
   remove = pop();          // lift
   insertAtBottom(...);     // dig
   push(remove);            // restore

   Restoring before digging returns the stack to its prior state
   -> nothing changes -> infinite recursion.
   This is why it is NOT tail recursion.
```

**Complexity, stated precisely**

| | Value | Why |
|---|---|---|
| Best | `Θ(n²)` | `insertAtBottom` never short-circuits |
| Average | `Θ(n²)` | Same |
| Worst | `Θ(n²)` | `0+1+2+…+(n−1) = n(n−1)/2` |
| Space | `O(n)` | Sequential recursions: `O(n) + O(n)` |
| With buffer | `O(n)` | `2n` operations — the constraint's real cost |

**The sibling comparison**

```text
   SAME BODY:   r = pop();  recurse();  push(r);

   REVERSE:  base = isEmpty()          -> positional -> no early exit -> Theta(n^2)
   SORT   :  base = isEmpty()||peek()<=e -> value    -> can exit early -> O(n) best
```

**Edge cases to say out loud**

```text
   []         -> []           base case
   [5]        -> [5]          single element
   [1,2]      -> [2,1]        smallest real reversal
   [1,1,1]    -> [1,1,1]      unchanged, but STILL Theta(n^2)
   reverse^2  -> original     free property test (involution)
   10^5 elts  -> StackOverflowError -> use the O(n) buffer version
```

# PHASE 12 — FINAL CHEAT SHEETS

## Complexity cheat sheet

| Approach | Time | Space | Recursion? | Notes |
|---|---|---|---|---|
| **Recursive `insertAtBottom` (this)** | `Θ(n²)` | `O(n)` call stack | yes | No best case; overflows ~10⁴ |
| Buffer (list) + refill in pop order | `O(n)` | `O(n)` heap | no | **Optimal**; `2n` operations |
| `Collections.reverse(stack)` | `O(n)` | `O(1)` | no | Works — `Stack` is a `List` |
| Single transfer to a second stack | `O(n)` | `O(n)` heap | no | Transfer **once** (twice undoes it) |
| Swap ends on the backing array | `O(n)` | `O(1)` | no | Breaks the ADT abstraction |

## Code skeletons cheat sheet

```text
   REVERSE A STACK (recursion only)
   --------------------------------
   void reverseStack(Deque<Integer> st) {
       if (st.isEmpty()) return;
       int element = st.pop();
       reverseStack(st);
       insertAtBottom(st, element);     // NOT st.push(element)!
   }

   void insertAtBottom(Deque<Integer> st, int e) {
       if (st.isEmpty()) { st.push(e); return; }   // POSITIONAL base case
       int remove = st.pop();
       insertAtBottom(st, e);
       st.push(remove);                             // AFTER the recursion
   }

   SORT A STACK — change ONE line
   ------------------------------
   if (st.isEmpty() || st.peek() <= e) { st.push(e); return; }  // VALUE base case

   O(n) VERSION (if a buffer is allowed)
   -------------------------------------
   List<Integer> buf = new ArrayList<>();
   while (!st.isEmpty()) buf.add(st.pop());   // top -> bottom order
   for (int v : buf) st.push(v);              // pushing in pop order REVERSES

   ONE-LINER (java.util.Stack only)
   --------------------------------
   Collections.reverse(stack);
```

## The three-step idiom cheat sheet

```text
   +--------------------------------------------------------------+
   |   int saved = st.pop();      // 1. REMOVE the obstruction     |
   |   recurse(...);              // 2. SOLVE the smaller problem  |
   |   st.push(saved);            // 3. RESTORE the obstruction    |
   +--------------------------------------------------------------+

   THE BASE CASE DECIDES THE ALGORITHM:

       isEmpty()          -> bottom       -> REVERSE   -> Theta(n^2)
       isEmpty()||peek()<=e -> sorted slot -> SORT     -> O(n) .. O(n^2)
       counter == 0       -> depth k      -> INSERT/DELETE AT k -> O(n)

   Applies to: reverse stack | sort stack | delete middle | insert at bottom
               reverse linked list | Tower of Hanoi | ALL backtracking
```

## Final takeaway (upgraded)

```text
   THREE THINGS TO CARRY OUT OF THIS PROBLEM INTO EVERY OTHER PROBLEM:

   1. WHEN THE INTERFACE LACKS AN OPERATION, BUILD IT
      The stack has no pushToBottom(). Rather than declaring the problem
      impossible, you COMPOSE the missing operation from the primitives
      you do have. That is the core move of both algorithm design and
      API design — and it's why "insert at bottom" deserves its own name
      and its own function.

   2. THE BASE CASE IS THE ALGORITHM
      Reverse and Sort share a byte-identical recursive body. Only the
      stopping rule differs — positional (isEmpty) versus value-based
      (peek <= e). That one line decides the behaviour AND the complexity:
      a positional base case can never short-circuit, which is exactly why
      reverse is Theta(n^2) while sort gets an O(n) best case.

   3. SEPARATE THE PROBLEM'S COST FROM THE CONSTRAINT'S COST
      Reversing a stack is intrinsically O(n). The quadratic blow-up comes
      entirely from "recursion only, no extra structure". Always be able to
      say what the unconstrained solution costs — and then say what the
      constraint is buying you. Here it buys nothing but understanding,
      which is precisely the point of the exercise.
```

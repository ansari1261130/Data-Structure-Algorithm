### Missing Interview Patterns

- **Accumulator (tail) recursion** — carry the answer down, not build it up.
- **Finite State Machine** — `START → SIGN → NUMBER → END`.
- **Two-pointer / index-pointer scanning** — avoid substring allocation (this note nails it, but never names it).
- **Guard-before-mutate** — check the invariant *before* changing state (transfers directly to Reverse Integer, Multiply Strings, Add Two Numbers).
- **Saturating arithmetic** — clamp instead of wrap.
- **Parser design** — lex → validate → accumulate → terminate.

### Missing Optimization Techniques

| Technique | Gain |
|---|---|
| Convert recursion → iteration | `O(n)` stack → `O(1)` stack |
| Early exit once clamped | Avoids scanning a 1M-digit tail |
| `char[] c = s.toCharArray()` | Avoids repeated `charAt` bounds checks (JIT usually handles it, but say it) |
| Precompute `limit/10` and `limit%10` outside the loop | Removes 2 divisions per digit |
| Branchless sign: `sign = 1 - 2*(c=='-' ? 1:0)` | Micro-opt, good to mention, not to write |
| Skip leading zeros before accumulating | Guarantees ≤ 10 meaningful digits |

# PART A — CORE NOTES (ORIGINAL, CORRECTED & EXPANDED)

## 1) Core idea

Convert a string into a 32-bit signed integer.

Examples:

- "1337c0d3" -> 1337
- "   -1337abc" -> -1337
- "+42" -> 42
- "4193 with words" -> 4193
- "words 987" -> 0

Important: once digit reading starts, stop at the first non-digit.

---

## 2) Problem breakdown

1. Skip leading spaces
2. Handle optional `+` / `-`
3. Read consecutive digits
4. Stop at first non-digit
5. Handle overflow
6. Return the answer

Example:

Input: "   -1337c0d3"

- Skip spaces
- Detect `-`
- Read `1, 3, 3, 7`
- Stop at `c`
- Apply sign
- Result = -1337

---

## 3) Whitespace rule to remember

Leading spaces are skipped before recursion.

After number starts, any non-digit (including space) ends digit reading.

```text
"   1337"  -> skip leading spaces
"1337 abc" -> stop at space after number
```

> **⚠ CORRECTION — be precise here.** LeetCode 8 skips **only the ASCII space `' '` (0x20)**.
> It does **not** skip `\t`, `\n`, `\r`, or `\f`. So `"\t123"` returns `0`, not `123`.
>
> Do **not** write `Character.isWhitespace(c)` — that is a silent wrong-answer bug.
>
> ```text
>   "   123"   ->  123    (spaces skipped)
>   "\t123"    ->    0    (TAB is a non-digit terminator, NOT whitespace to skip)
>   "\n123"    ->    0
> ```
>
> In a real interview, **say this out loud**: "I'm assuming only `' '` is skipped —
> should I also handle tabs?" That one sentence reads as senior.

**Whitespace is a PREFIX-ONLY privilege:**

```text
  "   -  42"
   ^^^   ^
    |    |
    |    +--- space AFTER the sign -> INVALID -> return 0
    +-------- leading spaces -> skipped, allowed

  Rule: space is allowed ONLY before the sign.
        Once you leave the whitespace zone, you never return to it.
```

---

## 4) Why use index instead of substring?

String is immutable, so we should not keep creating smaller substrings.

Use a single string and a moving index instead.

```text
helper(s, 0, 0)
helper(s, 1, 1)
helper(s, 2, 13)
helper(s, 3, 133)
helper(s, 4, 1337)
```

This is the key recursion idea:

A problem does not need a smaller string; it needs a smaller logical state.

---

## 5) Recursive state

```java
helper(s, i, res)
```

Meaning:

> Process the string starting from index `i`, while `res` stores the number built so far.

State meaning:

- `s` -> original string
- `i` -> current index
- `res` -> accumulated number

Example:

```java
helper(s, 3, 133)
```

means: "I am at index 3 and already built 133."

---

## 6) State propagation

```text
"1337c0d3"

helper(s, 0, 0)
 -> helper(s, 1, 1)
 -> helper(s, 2, 13)
 -> helper(s, 3, 133)
 -> helper(s, 4, 1337)
 -> stop at 'c'
 -> return 1337
```

Every call has its own state.

```java
helper(s, i + 1, newRes)
```

does not change the previous call's values.

---

## 7) Convert char to digit

```java
int digit = s.charAt(i) - '0';
```

Because:

```java
'7' - '0' = 7
```

Do not use `- 'a'` for digits.

---

## 8) Base case

Recursion stops when:

- end of string reached
- current char is not a digit

```java
if (i == s.length()
        || s.charAt(i) < '0'
        || s.charAt(i) > '9') {
    return res;
}
```

Very important: base case should return the valid accumulated answer, not always `0`.

---

## 9) Transition step

At every valid digit:

```java
digit = s.charAt(i) - '0';
res = res * 10 + digit;
i = i + 1;
return helper(s, i, res);
```

This is the standard pattern:

```text
current state -> read digit -> update res -> move index -> recurse
```

---

## 10) Sign handling

Do not do:

```java
int res = 0;
if (s.charAt(i) == '-') {
    res = -res;
}
```

Why? Because `-0` is still `0`, so sign information is lost.

Instead:

```java
int sign = 1;

if (s.charAt(i) == '-') {
    sign = -1;
    i++;
}
else if (s.charAt(i) == '+') {
    i++;
}
```

Then build magnitude recursively and do:

```java
result = sign * result;
```

---

## 11) When does sign belong in recursion?

Ask: does this value change during recursion?

- `i` changes -> yes, recursive state
- `res` changes -> yes, recursive state
- `sign` stays fixed -> no, handle outside recursion

---

## 12) Overflow is the dangerous part

Wrong order:

```java
res = res * 10 + digit;
if (res > Integer.MAX_VALUE) return ...;
```

This can overflow before checking.

Correct approach:

```java
if (res > (limit - digit) / 10) {
    return limit;
}
```

This checks safety before creating the next state.

---

## 13) Limits

For 32-bit signed integer:

- `Integer.MAX_VALUE = 2147483647`
- `Integer.MIN_VALUE = -2147483648`

So:

```java
long limit = (sign == -1)
        ? 2147483648L
        : 2147483647L;
```

---

## 14) Final recursion flow

```text
myAtoi(s)
  -> skip spaces
  -> read optional sign
  -> set limit
  -> helper(s, i, 0, limit)
      -> if digit: check overflow, update res, recurse
      -> else: return res
  -> apply sign once
```

---

## 15) Final Java code

```java
class Solution {
    public int myAtoi(String s) {
        int i = 0;

        while (i < s.length() && s.charAt(i) == ' ') {
            i++;
        }

        int sign = 1;

        if (i < s.length() && s.charAt(i) == '-') {
            sign = -1;
            i++;
        } else if (i < s.length() && s.charAt(i) == '+') {
            i++;
        }

        long limit = (sign == -1)
                ? 2147483648L
                : 2147483647L;

        long result = helper(s, i, 0, limit);
        result = sign * result;

        return (int) result;
    }

    private long helper(String s, int i, long res, long limit) {
        if (i == s.length()
                || s.charAt(i) < '0'
                || s.charAt(i) > '9') {
            return res;
        }

        int digit = s.charAt(i) - '0';

        if (res > (limit - digit) / 10) {
            return limit;
        }

        res = res * 10 + digit;
        return helper(s, i + 1, res, limit);
    }
}
```

## 16) Complexity

Time: `O(n)`

Space: `O(n)` because recursion uses stack space.

> **⚠ EXPANDED — this is where candidates lose the offer.**

| Version | Time | Space | Note |
|---|---|---|---|
| Recursive (this note) | `O(n)` | **`O(n)`** stack | One frame per digit |
| Iterative | `O(n)` | **`O(1)`** | Expected optimal |
| FSM | `O(n)` | `O(1)` | Cleanest to extend |

**Three things to say when asked about space:**

1. *"Space is `O(n)` because of the recursion stack — one frame per digit character."*
2. *"Strictly it's `O(d)` where `d` is the digit-run length, which is bounded by `n`."*
3. *"This function is **tail-recursive** — the recursive call is the last operation, nothing
   happens to its return value. A compiler with tail-call optimisation would reduce this to
   `O(1)`. **Java's JVM does not do TCO**, so the frames really are allocated and a
   100,000-character input can throw `StackOverflowError`. That's why I'd ship the
   iterative version in production."*

```text
   WHY THIS IS TAIL RECURSION

   return helper(s, i + 1, res, limit);
   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |                                 |
   +-- nothing wraps the result ------+
       no  ( 1 + helper(...) )
       no  ( helper(...) * 10 )
       just  return helper(...)

   => the parent frame has NO remaining work
   => a TCO compiler can REUSE the frame
   => Java does not. Kotlin does (with `tailrec`). Scala does.
```

Pattern:

```text
State-Carrying / Top-Down Recursion
```

Structure:


For this problem:


## 21) ADDED — The iterative version (ship this in production)

Same logic, `O(1)` space, no stack-overflow risk. **Always offer this after the recursive one.**

```java
class Solution {
    public int myAtoi(String s) {
        int i = 0, n = s.length();

        // 1. SPACE — only ASCII ' ', not \t or \n
        while (i < n && s.charAt(i) == ' ') i++;

        // 2. SIGN — at most one
        int sign = 1;
        if (i < n && (s.charAt(i) == '+' || s.charAt(i) == '-')) {
            if (s.charAt(i) == '-') sign = -1;
            i++;
        }

        // 3. DIGITS — with guard-before-mutate overflow check
        int res = 0;
        while (i < n) {
            char c = s.charAt(i);
            if (c < '0' || c > '9') break;          // first non-digit terminates
            int digit = c - '0';

            // res*10 + digit would exceed MAX? clamp using SIGNED limits.
            if (res > Integer.MAX_VALUE / 10
                    || (res == Integer.MAX_VALUE / 10 && digit > Integer.MAX_VALUE % 10)) {
                return sign == 1 ? Integer.MAX_VALUE : Integer.MIN_VALUE;
            }

            res = res * 10 + digit;
            i++;
        }

        // 4. SIGN APPLY
        return sign * res;
    }
}
```

**Why this needs no `long` at all:** we clamp *before* the multiply, so `res` never exceeds
`Integer.MAX_VALUE`. This is the answer to *"what if you had no wider type available?"*

`Integer.MAX_VALUE / 10 = 214748364` and `Integer.MAX_VALUE % 10 = 7`.

```text
   THE OVERFLOW GUARD, VISUALLY

   MAX = 2147483647
          |||||||||
          214748364 | 7
          \_______/   \_ last digit
           res limit

   if res >  214748364                      -> definitely overflows -> CLAMP
   if res == 214748364 AND digit > 7        -> overflows            -> CLAMP
   otherwise                                -> safe                 -> res = res*10 + digit

   Note: MIN_VALUE is -2147483648, so the negative side can take digit == 8.
   Clamping to MIN_VALUE anyway is still CORRECT, because the only input that
   would be wrongly clamped is "-2147483648" itself — and for that input
   res == 214748364, digit == 8, and we return MIN_VALUE. Which is the right answer. ✓
```

## 22) ADDED — The Finite State Machine version (the "senior engineer" answer)

Use this when the interviewer says *"now also support hex / exponents / a base parameter."*
The FSM makes extension trivial; the ad-hoc version becomes spaghetti.

```text
                 ' '            +/-            0-9          other
              +--------+    +--------+    +--------+    +--------+

   START  --->  START        SIGNED        NUMBER          END
   SIGNED --->  END          END           NUMBER          END
   NUMBER --->  END          END           NUMBER          END
   END    --->  END          END           END             END


         ' '
        +---+
        |   v
     +--------+   +/-    +--------+   0-9   +--------+
     | START  |--------->| SIGNED |-------->| NUMBER |<--+ 0-9
     +--------+          +--------+         +--------+---+
         |                    |                  |
         | 0-9                | other            | other
         v                    v                  v
     +--------+ <-------------+------------------+
     |  END   |   (absorbing / trap state)
     +--------+
```

```java
class Solution {
    private enum State { START, SIGNED, NUMBER, END }

    public int myAtoi(String s) {
        State state = State.START;
        int sign = 1;
        long res = 0;

        for (char c : s.toCharArray()) {
            state = next(state, c);
            if (state == State.END) break;
            if (state == State.SIGNED) { sign = (c == '-') ? -1 : 1; }
            else if (state == State.NUMBER) {
                res = res * 10 + (c - '0');
                if (sign == 1 && res > Integer.MAX_VALUE) return Integer.MAX_VALUE;
                if (sign == -1 && -res < Integer.MIN_VALUE) return Integer.MIN_VALUE;
            }
        }
        return (int) (sign * res);
    }

    private State next(State s, char c) {
        switch (s) {
            case START:  return c == ' ' ? State.START
                              : (c == '+' || c == '-') ? State.SIGNED
                              : isDigit(c) ? State.NUMBER : State.END;
            case SIGNED: return isDigit(c) ? State.NUMBER : State.END;
            case NUMBER: return isDigit(c) ? State.NUMBER : State.END;
            default:     return State.END;
        }
    }

    private boolean isDigit(char c) { return c >= '0' && c <= '9'; }
}
```

> **Why `c >= '0' && c <= '9'` and NOT `Character.isDigit(c)`:**
> `Character.isDigit('١')` (Arabic-Indic one) returns **`true`**, but `'١' - '0'` is **1633**,
> not 1. That is a genuine production bug. Mention it — it lands extremely well.

# PHASE 2 — CONCEPT REBUILDING

## CONCEPT 1: Accumulator (State-Carrying) Recursion

### LEVEL 1 — Beginner Intuition

**Why does it exist?**

There are two ways to do recursion:

```text
  STYLE A: "BUILD UP"  (classic recursion)
  ---------------------------------------
  Go all the way down, then construct the answer on the way BACK UP.

      sum(n) = n + sum(n-1)
                   ^^^^^^^^
                   parent must WAIT and then add


  STYLE B: "CARRY DOWN"  (accumulator recursion)  <-- THIS PROBLEM
  ---------------------------------------------
  Compute as you descend. The bottom already HAS the answer.

      sum(n, acc) = sum(n-1, acc + n)
                    ^^^^^^^^^^^^^^^^^
                    parent does NOTHING after the call
```

**What problem does it solve?**
It solves the problem of *"I can't make the input smaller, but I can make the remaining work
smaller."* You can't shrink a `String` cheaply (strings are immutable — `substring` copies).
But you *can* shrink the **region of interest** by moving an index.

**When to use it:**
When your recursion is really a **loop in disguise** — a single left-to-right pass where each
step updates a running value.

### LEVEL 2 — Mental Visualization

```text
   INPUT:  "1337c0d3"
            0123456 7

   THE STATE MACHINE OF THE RECURSION
   -----------------------------------

   helper(s, i=0, res=0)
        |  s[0]='1'  digit=1   res = 0*10 + 1
        v
   helper(s, i=1, res=1)
        |  s[1]='3'  digit=3   res = 1*10 + 3
        v
   helper(s, i=2, res=13)
        |  s[2]='3'  digit=3   res = 13*10 + 3
        v
   helper(s, i=3, res=133)
        |  s[3]='7'  digit=7   res = 133*10 + 7
        v
   helper(s, i=4, res=1337)
        |  s[4]='c'  NOT a digit  -> BASE CASE
        v
      return 1337
        |
        | <-- notice: nothing is ADDED on the way back up.
        |     The value just falls straight through.
        v
      1337  ->  1337  ->  1337  ->  1337  ->  1337
```

**The string never shrinks — the WINDOW shrinks:**

```text
   i=0    [1 3 3 7 c 0 d 3]      res = 0
           ^
   i=1     1[3 3 7 c 0 d 3]      res = 1
             ^
   i=2     1 3[3 7 c 0 d 3]      res = 13
               ^
   i=3     1 3 3[7 c 0 d 3]      res = 133
                 ^
   i=4     1 3 3 7[c 0 d 3]      res = 1337
                   ^
                   |
                   +-- 'c' is not a digit -> STOP. Return res.

   [ ... ] = "the part I still have to look at"
   The array itself is NEVER copied.
```

**Stack frame view (why space is `O(n)`):**

```text
   CALL STACK (grows downward)

   +--------------------------------+
   | myAtoi("1337c0d3")             |  sign=+1, i=0
   +--------------------------------+
   | helper(i=0, res=0)             |
   +--------------------------------+
   | helper(i=1, res=1)             |
   +--------------------------------+
   | helper(i=2, res=13)            |
   +--------------------------------+
   | helper(i=3, res=133)           |
   +--------------------------------+
   | helper(i=4, res=1337)  <- BASE |  returns 1337
   +--------------------------------+

   5 frames for 4 digits.  1,000,000 digits -> 1,000,001 frames -> StackOverflowError.
   In the ITERATIVE version this entire tower collapses to ONE frame.
```

### LEVEL 3 — Real-World Analogy

> **Accumulator Recursion = A Relay Race with a Baton**
>
> Each runner (stack frame) runs one leg (one character). They don't wait at the finish line
> to add up times — they **hand the baton forward** with the running total already written on it.
> The last runner crosses the line holding the *final* answer. Everyone else just steps aside.
>
> Contrast: **build-up recursion = a pyramid scheme.** Everyone waits for the person below
> them to report back before they can compute their own number.

> **The index pointer = a bookmark in a physical book.**
> You don't tear out pages you've read (`substring`) — you just move the bookmark (`i + 1`).

> **The whole problem = a supermarket checkout conveyor belt.**
> Items come by one at a time. You scan (read digit), add to the running total (`res`),
> and the moment a **divider bar** appears (non-digit), you stop and print the receipt.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"This is accumulator-style recursion. Instead of shrinking the string — which would mean
> an `O(n)` substring copy at every level and `O(n²)` overall — I keep the original string and
> shrink the **state**: an index `i` and a running result `res`. Each call reads one digit,
> folds it in with `res = res*10 + digit`, and passes the new state down. The base case fires
> at end-of-string or the first non-digit, and it returns the accumulated `res`, not zero.
> Because the recursive call is the last thing I do, this is tail recursion — so it maps
> one-to-one onto a simple `while` loop, which is what I'd actually ship for `O(1)` space."*

## CONCEPT 2: Guard-Before-Mutate (Safe Overflow Detection)

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because in fixed-width integer arithmetic, **overflow is silent**.
There is no exception. `2147483647 + 1` quietly becomes `-2147483648`. So you cannot
detect overflow *after* it happens — the evidence is destroyed.

**What problem does it solve?** It converts an unobservable failure into a predictable,
checkable condition — by asking *"would this operation overflow?"* using only safe arithmetic.

**When to use it:** Any time you multiply or add toward a bound: atoi, Reverse Integer,
Multiply Strings, Pow(x, n), factorial, hash accumulation, sum of subarray.

### LEVEL 2 — Mental Visualization

```text
   THE WRONG WAY — checking after the crime
   -----------------------------------------

   res = res * 10 + digit;      <-- overflow ALREADY happened here
   if (res > MAX) ...           <-- res is now garbage. Check is meaningless.

        2147483647
      +          1
      ------------
       -2147483648      <-- WRAPPED. No error. No warning. Silent corruption.

      |<------------ int range ------------>|
      -2147483648                   2147483647
            ^                             |
            |_____________________________|
                    wraps around like a clock


   THE RIGHT WAY — checking before the crime
   ------------------------------------------

   if (res > (limit - digit) / 10) return limit;   <-- SAFE: division shrinks
   res = res * 10 + digit;                         <-- now provably safe


   ALGEBRA (this is the whole trick):

        we want to know:   res * 10 + digit  >  limit  ?
        but computing the left side may overflow.
        so rearrange — subtract and divide instead of multiply:

        res * 10 + digit > limit
        res * 10         > limit - digit
        res              > (limit - digit) / 10     <-- all operands SHRINK. Safe. ✓
```

**The odometer picture:**

```text
   res = 214748364   digit = 8

   +---+---+---+---+---+---+---+---+---+  [8]
   | 2 | 1 | 4 | 7 | 4 | 8 | 3 | 6 | 4 |   ^
   +---+---+---+---+---+---+---+---+---+   |
                                           +-- pushing this in shifts everything left

   becomes 2147483648  ->  but MAX is 2147483647
                                    ^
                                    +-- one too many. CLAMP.

   The guard asks: "is there room for one more digit?" BEFORE pushing it in.
```

### LEVEL 3 — Real-World Analogy

> **Guard-before-mutate = the weight limit sign on an elevator.**
> You read *"Max 8 persons"* and count **before** stepping in. You do not step in, hear the
> cable snap, and *then* conclude it was too heavy.

> **Integer overflow = an odometer rolling over.**
> A 6-digit car odometer at `999999` doesn't show `1000000` — it shows `000000`. The car
> has no idea. Neither does your `int`.

> **The asymmetric limit (`|MIN| = |MAX| + 1`) = a building with a basement.**
> Floors `1..7` above ground, but the basement counts `0` as a floor too — so there's one
> more level below than above. That's two's complement: zero lives on the positive side,
> so the negatives get one extra slot.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"Overflow in Java is silent — it wraps, it doesn't throw. So I can't check after the fact,
> because the value is already corrupted. Instead I check the **precondition**: rather than
> asking `res*10 + digit > limit`, which itself overflows, I rearrange it algebraically to
> `res > (limit - digit)/10`. Subtraction and division only shrink the operands, so that
> comparison is always safe. If it trips, I clamp to `MAX_VALUE` or `MIN_VALUE`. I use
> `MIN_VALUE` asymmetrically because two's complement gives one extra value on the negative
> side — `-2147483648` is valid but `+2147483648` is not."*

## CONCEPT 3: Base Case Must Return the ACCUMULATED Answer

### LEVEL 1 — Beginner Intuition

**Why does it exist?** In build-up recursion the base case returns an **identity** (`0` for
sums, `1` for products, `""` for strings) because the real answer is assembled on the way up.
In accumulator recursion the answer is *already complete* when you hit the base case — so
returning `0` **throws away everything you computed.**

### LEVEL 2 — Mental Visualization

```text
   RETURNING 0 IN THE BASE CASE — the catastrophic bug
   ----------------------------------------------------

   helper(i=0, res=0)
     -> helper(i=1, res=1)
          -> helper(i=2, res=13)
               -> helper(i=3, res=133)
                    -> helper(i=4, res=1337)
                         -> base case hit
                         -> return 0        <-- ✗ the 1337 is DELETED
                    <- 0
               <- 0
          <- 0
     <- 0
   ANSWER: 0     (you did all the work and threw it in the bin)


   RETURNING res — correct
   -----------------------
                         -> return res = 1337   <-- ✓
                    <- 1337
               <- 1337
          <- 1337
     <- 1337
   ANSWER: 1337
```

**The rule, generalised:**

```text
   +---------------------------+-------------------------------+
   | RECURSION STYLE           | BASE CASE RETURNS             |
   +---------------------------+-------------------------------+
   | Build-up  f(n)=n+f(n-1)   | IDENTITY   (0, 1, "", null)   |
   | Accumulator f(n,acc)      | THE ACCUMULATOR  (acc)        |
   +---------------------------+-------------------------------+

   Ask yourself: "Is the answer in my PARAMETERS or in my RETURN VALUES?"
        parameters  -> return the parameter
        return vals -> return the identity
```

### LEVEL 3 — Real-World Analogy

> **A delivery driver reaching the last house.**
> The parcel is already in the van (the accumulator). At the final stop you **hand over the
> parcel**, you don't hand over an empty box and say "identity element, sorry."

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The base case has to return `res`, not `0`. In accumulator recursion the answer lives in
> the parameters, not in the return values — by the time I reach the base case the number is
> fully built, so returning an identity would discard all of it. The quick test I use: if the
> parent does arithmetic on the child's return value, the base case returns an identity; if
> the parent just forwards the child's return value, the base case returns the accumulator."*

## CONCEPT 4: Loop Invariants vs. Recursive State

### LEVEL 1 — Beginner Intuition

Not every variable deserves to be a parameter. Passing a constant through 1,000 stack frames
wastes memory and hides intent. The test from your Section 11 is the right one — formalised:

```text
   FOR EACH VARIABLE, ASK:
   "Does its value DIFFER between two different recursive calls?"

        YES -> it is STATE       -> pass as a parameter
        NO  -> it is a CONSTANT  -> capture it outside (field / closure / final local)
```

### LEVEL 2 — Mental Visualization

```text
   VARIABLE   CHANGES PER CALL?   VERDICT
   --------   -----------------   ----------------------------------
   s          NO  (same string)   constant — but Java passes a cheap reference, fine
   i          YES (0,1,2,3...)    STATE ✓
   res        YES (0,1,13,133)    STATE ✓
   sign       NO  (fixed at +1/-1) constant — handle OUTSIDE ✓ (your §11, correct!)
   limit      NO  (fixed once)     constant — your code passes it anyway ✗ inconsistent


   VISUAL:

   helper( s , i , res , limit )
           ^   ^    ^      ^
           |   |    |      |
        const | STATE|   const  <-- two of four params are dead weight
              +------+
              the only things that actually move
```

### LEVEL 3 — Real-World Analogy

> **A road trip.** Your **odometer** and **current town** change every hour — those are state.
> Your **destination** and **fuel-tank capacity** don't change — you don't re-announce them at
> every road sign. Constants belong on the dashboard, not in every conversation.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"I decide parameters by asking which values actually vary across calls. `i` and `res` vary,
> so they're recursive state. `sign` and `limit` are fixed the moment I've read the sign
> character, so they're loop invariants — I hoist them out of the recursion. That keeps the
> recursive signature minimal, which makes the base case and the transition much easier to
> reason about, and it's a smaller stack frame per call."*

# PHASE 4 — INTERVIEW PATTERN RECOGNITION

## WHEN TO USE: Accumulator / State-Carrying Recursion

```text
   USE WHEN:

   ✓ You traverse the input EXACTLY ONCE, left to right
   ✓ The input is IMMUTABLE (String) or expensive to copy
   ✓ A running value updates at each step (sum, product, count, parsed number)
   ✓ The parent does NOTHING with the child's return value except forward it
   ✓ You could write it as a `for` loop without changing the logic
   ✓ You need to "remember what I've seen so far" while moving forward

   DO NOT USE WHEN:

   ✗ You need to combine results from MULTIPLE branches (trees, subsets) -> build-up
   ✗ You must undo choices (backtracking) -> build-up + explicit undo
   ✗ Work must happen AFTER the child returns (postorder) -> build-up
   ✗ Depth can exceed ~10,000 in Java -> convert to iteration
```

## WHEN TO USE: Guard-Before-Mutate

```text
   ✓ Multiplying or adding toward a fixed-width limit
   ✓ Input size is unbounded but output type is bounded
   ✓ The problem statement mentions "32-bit", "fits in an int", "clamp", "saturate"
   ✓ You see MAX_VALUE / MIN_VALUE in the constraints
   ✓ Parsing user-supplied / untrusted numeric input  (SECURITY: CWE-190)
```

# PHASE 5 — PROBLEM IDENTIFICATION SYSTEM

## The Master Mapping for THIS problem

```text
   String to Integer (atoi)
            ↓
   Observation: messy prefix, one number, bounded output
            ↓
   Pattern: Single-pass parse + accumulate + saturating arithmetic
            ↓
   Data Structure: none — just an index and a running int
            ↓
   Algorithm: Accumulator recursion (or while loop) + guard-before-mutate
            ↓
   Complexity: O(n) time | O(n) stack recursive, O(1) iterative
```

## Mapping Library — build the reflex

```text
1.  String -> bounded integer
       ↓ messy prefix, must clamp
       ↓ Parse + Saturate Pattern
       ↓ index + running int
       ↓ Accumulator recursion / while loop
       ↓ O(n) time, O(1) space

2.  Reverse the digits of an integer  (LC 7)
       ↓ Need last digit repeatedly
       ↓ Digit Extraction Pattern
       ↓ int only
       ↓ res = res*10 + n%10, guard first
       ↓ O(log n) time, O(1) space

3.  Validate a number format "-1.2e10"  (LC 65)
       ↓ Many legal shapes, grammar-like
       ↓ Finite State Machine Pattern
       ↓ transition table
       ↓ FSM walk
       ↓ O(n) time, O(1) space

4.  Multiply two huge number-strings  (LC 43)
       ↓ Exceeds every primitive type
       ↓ Schoolbook Arithmetic Pattern
       ↓ int[] of digits
       ↓ digit-by-digit with carry
       ↓ O(m*n) time, O(m+n) space

5.  Roman numeral -> integer  (LC 13)
       ↓ Value depends on NEXT symbol
       ↓ Lookahead Scan Pattern
       ↓ HashMap<Character,Integer>
       ↓ subtract if cur < next
       ↓ O(n) time, O(1) space

6.  K largest elements
       ↓ Need repeated maximum
       ↓ Heap Pattern
       ↓ Priority Queue
       ↓ Min-heap of size k
       ↓ O(n log k) time, O(k) space

7.  Longest substring without repeats
       ↓ Contiguous + constraint
       ↓ Sliding Window Pattern
       ↓ HashMap / int[128]
       ↓ Expand right, shrink left
```

# PHASE 8 — FAANG FOLLOW-UP QUESTIONS

```text
   +-------+------------------------------------------+--------------------------+
   |  #    |  FOLLOW-UP                               |  WHAT THEY'RE TESTING    |
   +-------+------------------------------------------+--------------------------+
```

**Q1. "Can you do it without recursion?"**
Yes — the tail-recursive form maps directly to a `while` loop (Section 21). `O(n)` → `O(1)` space.
*Testing: do you understand tail recursion, or did you memorise a template?*

**Q2. "What's the actual space complexity, and why does it matter?"**
`O(n)` stack frames for the recursive version. It matters because Java's default thread stack
is ~512 KB–1 MB; at roughly 50–100 bytes/frame, ~10,000–50,000 digits throws `StackOverflowError`.
*Testing: do you connect Big-O to real machine limits?*

**Q3. "The input is 1 GB. What breaks?"**
Three things: (a) the recursion stack overflows; (b) `String` can't hold >2³¹−1 chars anyway;
(c) you're scanning a gigabyte to produce at most 10 meaningful digits. Fix: iterate, stream,
and **early-exit the moment you clamp** — after clamping, no later digit can change the answer.

**Q4. "Can this work on a stream / `InputStream`?"**
Yes, and it's *natural* — the algorithm is single-pass and needs `O(1)` state. Replace
`s.charAt(i)` with `reader.read()`. You must handle `-1` (EOF) as a terminator, and you must
**push back** the first non-digit char if the caller needs to keep parsing (`PushbackReader`).
*Testing: do you recognise a streaming-friendly algorithm?*

**Q5. "Can it be parallelised?"**
Mostly no, and saying so confidently is the right answer — it's an inherently sequential fold
with early termination. *But*: you could split into chunks, have each thread compute
`(value, digitCount)` for its chunk, then combine with `left * 10^rightCount + right`. That's
a valid **monoid/associative reduce**. It's only worth it for enormous numbers, and the
sign/whitespace prefix and early termination make chunk 0 special.

**Q6. "What if the target type were `long` or arbitrary precision?"**
For `long`: same guard with `Long.MAX_VALUE`. For arbitrary precision: you can't use a
primitive accumulator at all — store digits in an `int[]`/`byte[]` and do schoolbook carry
arithmetic (that's LC 43). The overflow guard *disappears* and is replaced by memory limits.

**Q7. "What if you had NO wider type — no `long` at all?"**
Already handled: the `res > MAX/10 || (res == MAX/10 && digit > MAX%10)` form never exceeds
`int`. This is the answer for embedded C on a 32-bit MCU.

**Q8. "Support a base parameter — `atoi(s, base)` for base 2–36."**
Replace `c - '0'` with a digit-value function handling `0-9`, `a-z`, `A-Z`; validate
`digitValue < base`; change the guard to `MAX/base` and `MAX%base`. This is C's `strtol`.

**Q9. "Support hex literals like `0x1A` and octal `017`."**
Add a prefix-detection state after the sign: `0x`/`0X` → base 16, leading `0` → base 8,
otherwise base 10. Cleanest with the FSM version — which is *why* you present the FSM.

**Q10. "Now write `atof` — support `1.5`, `-2.5e-3`."**
Now you genuinely need an FSM (`INT → FRAC → EXP_SIGN → EXP`) plus floating-point precision
care. Mention that naively doing `mantissa * 10^exp` loses precision and real implementations
use algorithms like Eisel–Lemire / Grisu.

**Q11. "Throw an exception instead of clamping. What changes?"**
The contract changes from *total* to *partial*. You need distinct errors (`NoDigitsFound` vs
`Overflow`), callers need `try/catch`, and it becomes unusable in hot loops (exceptions are
expensive in Java). Note that `Integer.parseInt` throws while `atoi` clamps — **two valid API
philosophies**, and knowing why each was chosen is the real answer.

**Q12. "Return the parse position too, like C's `strtol` endptr."**
Return a small record `(value, endIndex, status)`. This is what you need to parse
`"12,34,56"` in one pass. It also forces you to confront: what's `endIndex` when no digits
were found? (Answer: the original start — signals failure.)

**Q13. "What if duplicates / repeated signs appear: `"++1"`, `"--1"`, `"+-1"`?"**
All return `0`. The FSM makes this automatic: `SIGNED` has no transition back to `SIGNED`.
Ad-hoc code usually gets this wrong with a `while` loop over sign characters.

**Q14. "What if the input is unsorted / garbage / adversarial?"**
This is a **security** question. Untrusted numeric input is CWE-190 (Integer Overflow).
Points to make: never trust length, never allocate based on parsed values before validating,
clamp rather than wrap, and cap the scan length to avoid a DoS on a 1 GB digit string.

**Q15. "Handle Unicode digits — Arabic-Indic `١٢٣`, Devanagari `१२३`."**
`Character.isDigit` returns `true` for them, but `c - '0'` produces garbage. Use
`Character.digit(c, 10)` which returns the correct numeric value, or
`Character.getNumericValue`. Also beware of surrogate pairs for digits outside the BMP —
iterate by code point, not `char`.

**Q16. "What if the number is spread across multiple chunks/buffers?"**
Keep `(state, sign, res)` as an explicit resumable context object between chunk calls.
This is exactly how real streaming parsers (SAX, JSON push parsers) work.

**Q17. "How would you test this exhaustively?"**
Four layers: (1) the edge-case table in Phase 1; (2) boundary values MAX, MAX±1, MIN, MIN±1;
(3) **property-based testing** — generate random ints, `toString` them, assert round-trip
equality; (4) **differential testing** against `Integer.parseInt` on inputs where both are
defined. Mentioning property-based + differential testing is a strong senior signal.

**Q18. "Make it branch-free / SIMD for performance."**
Digit check `(unsigned)(c - '0') <= 9` is branchless. For SIMD, load 16 bytes, subtract `'0'`,
compare against 9 to find the first non-digit via a movemask, then combine with a
multiply-add reduction. This is how `fast_float` and simdjson parse numbers.

**Q19. "Can you cache or memoise anything?"**
No — every input is distinct and the work is already `O(n)` with `O(1)` per character. Being
able to say *"memoisation does not apply here, and here's why"* is worth more than forcing a
HashMap in. (You could cache the small `MAX/10`, `MAX%10` constants — trivial.)

**Q20. "What if this is called a billion times per second?"**
Profile first. Then: avoid `charAt` bounds checks with `toCharArray` (or `getBytes` for
Latin-1 compact strings), hoist `MAX/10` and `MAX%10`, avoid megamorphic call sites,
consider branchless digit detection, and ensure the method stays small enough to be
JIT-inlined (<325 bytecodes by default).

**Q21. "What if the data is distributed across machines?"**
Same monoid argument as Q5: each shard returns `(partialValue, digitCount)` and you reduce
with `left · base^rightCount + right`. Practically, a single number never justifies
distribution — but *parsing a billion separate numbers* does, and that's embarrassingly
parallel by record.

**Q22. "What if updates happen continuously — the string is being appended to live?"**
Keep the resumable context from Q16. Because the algorithm is a left-fold, appended digits
just continue the fold — **unless** you already hit a terminator or clamped, in which case the
result is frozen. Prepending, however, invalidates everything.

**Q23. "Why is `Integer.MIN_VALUE` special? Show me a bug it causes."**
`Math.abs(Integer.MIN_VALUE) == Integer.MIN_VALUE` (still negative!) and `-MIN_VALUE`
overflows back to itself. So any solution that parses the magnitude as a positive `int` and
negates at the end **cannot represent −2147483648**. That's precisely why this note builds
the magnitude in a `long`, or clamps before the multiply.

**Q24. "Rewrite it as `itoa` — integer to string, no `toString`."**
Repeatedly `n % 10` and `n /= 10`, building backwards, then reverse. **The trap:** handle
`MIN_VALUE` by working in negative space (since `-MIN_VALUE` overflows but `-MAX_VALUE`
doesn't), and handle `n == 0` explicitly or you return `""`.

**Q25. "What's the difference between your solution and `strtol` in C?"**
`strtol` skips all `isspace` whitespace (not just `' '`), supports bases 2–36 with auto-detect
via base 0, sets `errno = ERANGE` and clamps to `LONG_MAX`/`LONG_MIN` on overflow, and returns
an `endptr`. LeetCode's atoi is a deliberately simplified subset. Knowing the real-world
contract signals engineering maturity.

# PHASE 9 — COMMON INTERVIEW MISTAKES

| # | Mistake | Why it's fatal | Fix |
|---|---|---|---|
| 1 | `res = res*10 + digit;` **then** checking `res > MAX` | Overflow already wrapped; the check reads corrupted data | Guard **before** mutating: `res > MAX/10 \|\| (res == MAX/10 && d > MAX%10)` |
| 2 | Base case returns `0` instead of `res` | Discards the entire accumulated answer | Accumulator recursion → base case returns the accumulator |
| 3 | Using `s.substring(1)` per recursive call | `O(n)` copy per level → `O(n²)` time and space | Pass `i + 1`; the string never moves |
| 4 | `Character.isWhitespace(c)` for the skip loop | Wrongly skips `\t`, `\n` — LC 8 skips **only `' '`** | `while (i < n && s.charAt(i) == ' ')` |
| 5 | `Character.isDigit(c)` then `c - '0'` | Unicode digits pass the check, produce garbage values | `c >= '0' && c <= '9'`, or `Character.digit(c, 10)` |
| 6 | `res = -res` to apply a negative sign when `res == 0` | `-0 == 0`; sign silently vanishes | Store `sign` as `±1`, multiply once at the end |
| 7 | Allowing multiple signs (`"+-12"` → `-12`) | Should be `0` | Consume **at most one** sign character; no loop |
| 8 | Forgetting the empty string / all-spaces case | `charAt` → `StringIndexOutOfBoundsException` | Bounds-check `i < n` before **every** `charAt` |
| 9 | `"+"` or `"-"` alone crashes or returns garbage | Sign consumed, then unguarded `charAt(i)` | The digit loop's `i < n` guard handles it → returns `0` |
| 10 | Clamping negatives to `-2147483647` | Off by one; `MIN` is `-2147483648` | Use asymmetric limits, or clamp to `Integer.MIN_VALUE` explicitly |
| 11 | Parsing magnitude into an `int` then negating | `-2147483648` is unrepresentable as a positive `int` | Accumulate in `long`, or apply `sign` inside the guard |
| 12 | `Math.abs(Integer.MIN_VALUE)` anywhere | Returns `MIN_VALUE` — still negative | Never `abs` an `int` you don't control |
| 13 | Continuing to scan after the first non-digit | `"12a34"` → `1234` instead of `12` | `break`/return on the **first** non-digit |
| 14 | Passing loop-invariant `limit` through every frame | Contradicts your own "is it state?" rule; bloats frames | Hoist constants out of the recursive signature |
| 15 | Claiming `O(1)` space for the recursive version | Wrong — it's `O(n)` stack; interviewers always catch this | Say `O(n)`, then offer the iterative `O(1)` version |
| 16 | Not asking about `null` input | Silent `NullPointerException` in production | **Ask** the interviewer; then handle it explicitly |
| 17 | Saying "Java optimises tail calls" | It does not. The JVM has no TCO. | Say: *"this is tail-recursive, but the JVM won't optimise it, so I'd iterate"* |

# PHASE 10 — REVISION SECTIONS

## 2-MINUTE REVISION

```text
   S.S.D.O.S.

   SPACE      skip only ' '  (NOT \t, NOT \n), prefix only
   SIGN       at most ONE + or -, store as ±1, consume it
   DIGITS     while '0' <= c <= '9':  res = res*10 + (c - '0')
   OVERFLOW   BEFORE the multiply:
                 res > MAX/10 || (res == MAX/10 && d > MAX%10)  -> clamp
   SIGN-APPLY return sign * res    (never res = -res)

   STOP at the FIRST non-digit. Never resume.

   MAX = 2147483647  ->  214748364 | 7
   MIN = -2147483648 ->  one MORE than MAX in magnitude

   Recursive: O(n) time, O(n) stack   |   Iterative: O(n) time, O(1) space
   It IS tail recursion. Java has no TCO. So ship the loop.

   HOOK: AIRPORT SECURITY — wave the gaps, note one badge,
         board the digits, weigh before boarding,
         close the gate on the first non-passenger, stamp the badge once.
```

## 10-MINUTE REVISION

**The state design (the transferable lesson)**

```text
   helper(s, i, res)
            ^  ^
            |  +-- accumulated number so far    } these CHANGE -> parameters
            +----- current index                }

   sign, limit  -> never change -> hoist OUT of the recursion

   "A problem does not need a smaller INPUT; it needs a smaller STATE."
```

**The five steps, with their traps**

| Step | Code | Trap |
|---|---|---|
| Skip spaces | `while (i<n && s.charAt(i)==' ') i++;` | Don't use `isWhitespace` |
| Read sign | one `if`, not a loop | `"+-12"` must be `0` |
| Read digits | `res = res*10 + (c-'0')` | Stop at first non-digit, forever |
| Guard overflow | before the multiply | `MAX/10` and `MAX%10` |
| Apply sign | `return sign * res` | `-0` bug if you negate `res` |

**Why `res > (limit - digit)/10` is safe**

```text
   res*10 + digit > limit        <- computing this overflows
   res*10         > limit-digit  <- subtraction shrinks: safe
   res            > (limit-digit)/10  <- division shrinks: safe  ✓
```

**Base case rule**

```text
   Parent does arithmetic on the child's return  ->  base returns IDENTITY (0/1/"")
   Parent just forwards the child's return       ->  base returns ACCUMULATOR (res)
                                                     ^ atoi is here
```

**Complexity, stated correctly**

```text
   Recursive : O(n) time, O(n) stack, StackOverflowError at ~10k-50k digits
   Iterative : O(n) time, O(1) space  <- ship this
   FSM       : O(n) time, O(1) space  <- extend this (hex, exponents, bases)
```

**Must-know edge cases (say these out loud before coding)**

```text
   ""  "   "  "+"  "-"  "+-12"  "  -0012a42"  "3.14"
   "2147483648" -> MAX      "-2147483649" -> MIN
   "-2147483648" -> exactly MIN (must NOT be wrong by one)
```

## 30-MINUTE REVISION

**1. Recite the five phases and write the iterative solution from memory (Section 21).**

**2. Explain the state-design heuristic**

For every candidate variable ask: *does it differ between two recursive calls?*
Yes → parameter. No → hoist it. Here: `i` ✓, `res` ✓, `sign` ✗, `limit` ✗.

**3. Derive the overflow guard from scratch — don't recall it, derive it.**
Start from `res*10 + d > MAX`, move terms so every operation *shrinks*.
Then state both forms: `res > (MAX-d)/10` and `res > MAX/10 || (res==MAX/10 && d>MAX%10)`.

**4. Explain two's complement asymmetry**
32 bits → 2³² patterns → split as 2³¹ negatives and 2³¹ non-negatives, but zero occupies a
positive slot ⇒ `[-2³¹, 2³¹−1]` ⇒ `|MIN| = |MAX| + 1`. Consequences: `-MIN` overflows,
`Math.abs(MIN) == MIN`, `MIN / -1` overflows (LC 29's whole difficulty).

**5. Write the FSM version (Section 22) and explain why it's better for extension.**
Then extend it verbally to hex and exponents.

**6. Tail recursion**
Identify it (`return helper(...)` with nothing wrapping the call). Explain that it *can* be a
loop, that Kotlin's `tailrec`/Scala do it, and that the JVM does not — hence `StackOverflowError`.

**7. Run the full edge-case table from Phase 1 mentally against your code.**
Specifically trace `"-2147483648"` and `"2147483648"` digit by digit.

**8. Answer these six follow-ups without looking:** Q1 (iterative), Q2 (space), Q4 (stream),
Q11 (throw vs clamp), Q15 (Unicode), Q23 (MIN_VALUE bug).

**9. Solve the sibling problems in this order:**
LC 7 (same guard) → LC 13 (lookahead) → LC 43 (no primitive fits) → LC 65 (FSM boss fight).

**10. The 30-second interviewer pitch** — say it aloud until it's fluent (Phase 2, Concept 1,

## The traps, ranked by how often they're sprung

```text
   TRAP 1  "-2147483648"
           The single most common rejection input. If you parse the
           magnitude into an int and negate, you CANNOT produce this value.

   TRAP 2  "2147483648"  (MAX + 1)
           Checks whether your guard is > or >=, and whether it fires
           BEFORE the multiply.

   TRAP 3  "\t123"
           Checks if you lazily used isWhitespace(). Expected answer: 0.

   TRAP 4  "+-12"  /  "++1"
           Checks if you looped over sign characters. Expected: 0.

   TRAP 5  ""  and  "   "  and  "+"
           Checks bounds-checking discipline. Any of these should NOT throw.

   TRAP 6  "  0000000000000000000000001"
           Checks that leading zeros don't trip the overflow guard.

   TRAP 7  "words 987"
           Checks that you don't "search for" digits — you stop at the
           first non-digit in the NUMBER position.

   TRAP 8  The silent one: they ask "space complexity?" and wait.
           Saying O(1) for the recursive version is an instant red flag.
```

## Most frequent follow-ups (in real loops)

1. *"Now do it iteratively."* — expect this ~90% of the time.
2. *"What if it's a `long`?"* / *"arbitrary precision?"*
3. *"What if the input streams in?"*
4. *"Why did you use `long` — could you avoid it?"*
5. *"Now support hex / a base parameter."* (This is where the FSM pays off.)
6. *"How would you test it?"*

## Optimisation discussion — what to say, in order

```text
   1. "The algorithm is already optimal at O(n) — every character must be
       examined at least once in the worst case."

   2. "The real win is SPACE: recursion is O(n) stack, iteration is O(1).
       I'd ship the iterative version."

   3. "Second win: EARLY EXIT. Once I clamp, no subsequent digit can change
       the result, so I can return immediately instead of scanning the rest."

   4. "Micro-optimisations if this were hot: hoist MAX/10 and MAX%10 out of
       the loop, use a branchless digit test (c - '0') <= 9 on unsigned,
       and keep the method small enough for JIT inlining."

   5. "But I'd profile before doing any of #4."     <-- say this. Always.
```

# PHASE 12 — FINAL CHEAT SHEETS

## Complexity cheat sheet

| Approach | Time | Space | Stack-safe? | When to use |
|---|---|---|---|---|
| Recursive accumulator | `O(n)` | `O(n)` | ✗ (~10k–50k limit) | Interview, to show recursion mastery |
| Iterative loop | `O(n)` | `O(1)` | ✓ | **Production / final answer** |
| FSM | `O(n)` | `O(1)` | ✓ | When extension is required (hex, exp, bases) |
| Substring recursion | `O(n²)` | `O(n²)` | ✗ | **Never.** Anti-pattern. |
| `Integer.parseInt` | `O(n)` | `O(1)` | ✓ | Real code — but throws instead of clamping |

## Final takeaway (upgraded)

```text
   THREE THINGS TO CARRY OUT OF THIS PROBLEM INTO EVERY OTHER PROBLEM:

   1. STATE DESIGN
      Shrink the STATE, not the INPUT. Ask of every variable:
      "does this differ between two calls?" If no, it is not state.

   2. GUARD BEFORE MUTATE
      Validate the PRECONDITION, because the failure destroys its own evidence.
      Rearrange the inequality so every operation SHRINKS its operands.

   3. RIGOUR BEATS CLEVERNESS
      This problem has no clever trick. It is graded entirely on whether you
      enumerate edge cases before you code. That is also how you are graded
      as an engineer.
```

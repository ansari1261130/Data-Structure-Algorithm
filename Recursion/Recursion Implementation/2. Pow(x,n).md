### Missing Concepts

- **Iterative binary exponentiation** (`O(1)` space) — the expected optimal.
- **Bit view:** `n = 13 = 1101₂ ⇒ x¹³ = x⁸·x⁴·x¹`. Multiply in the squares where the bit is 1.
- **Modular exponentiation** `(x^n) mod m` — and why you *must* use `long` for the intermediate.
- **Matrix exponentiation** — same algorithm, different monoid. Fibonacci in `O(log n)`.
- **The monoid generalisation:** binary exponentiation works for *any* associative operation
  (numbers, matrices, strings, permutations, min-plus algebra).
- **Floating point:** `double` has 53 bits of mantissa; relative error of repeated squaring is
  `O(log n)·ε`, which is *better* than naive `O(n)·ε`. Squaring is more accurate **and** faster.
- **Overflow/underflow of the result**: `2^1024` → `Infinity`, `0.5^1074` → `0.0` (denormal).
- **`Math.pow` uses a completely different algorithm** (exp/log with extended precision) —
  binary exponentiation is *not* what the JDK does for `double`.
- **`0^0 = 1`** by convention in LC 50 (and in IEEE 754 `pow`).
- Tail-recursive variant with an accumulator (links back to the atoi note).

### Missing Interview Patterns

- **Exponentiation by squaring** — named explicitly (the note describes it but never names it).
- **Normalise-then-solve** — collapse the negative case into the positive case *before*
  recursing, instead of writing two recursions. (Transfers to Divide Two Integers, Reverse
  Integer, absolute-value problems.)
- **Divide & conquer with a single sub-call** — distinguishes `T(n)=T(n/2)+O(1)` → `O(log n)`
  from `T(n)=2T(n/2)+O(1)` → `O(n)`.
- **Bit-scanning accumulation** — process `n` bit by bit, squaring the base each step.
- **Monoid / associativity exploitation** — the reason the algorithm generalises.

### Missing Optimization Techniques

| Technique | Gain |
|---|---|
| Recursion → iteration | `O(log n)` stack → `O(1)` |
| `(n & 1) == 1` instead of `n % 2 != 0` | Avoids a division; clearer intent |
| `n >>= 1` instead of `n /= 2` | Same, and correct for the unsigned-style loop |
| Compute `x^|n|` then invert **once** at the end | One rounding instead of one-then-propagated |
| Early return for `x == 1.0`, `x == -1.0` | Turns the worst case into `O(1)` |
| Modular reduction after every multiply | Keeps intermediates inside `long` |
| Montgomery / sliding-window exponentiation | Fewer multiplications in crypto contexts |

# PART A — CORE NOTES (ORIGINAL, CORRECTED & EXPANDED)

*Your original 21 sections are preserved below. Corrections and additions are marked.*

## 1) Core idea

Calculate `x^n` efficiently.

Examples:

- `2^3 = 8`
- `2^-3 = 0.125`
- `2.1^3 = 9.261`

The main challenge is to make recursion move toward the base case and reduce work quickly.

---

## 2) First thought — simple recursion

```java
pow(x, n) = x * pow(x, n - 1)
```

Base case:

```java
if (n == 0) return 1;
```

Example:

```text
pow(2.1, 3)
= 2.1 * pow(2.1, 2)
= 2.1 * 2.1 * pow(2.1, 1)
= 2.1 * 2.1 * 2.1 * pow(2.1, 0)
= 9.261
```

This works, but it is too slow for large `n`.

---

## 3) Problem with negative n

If we do:

```java
pow(x, n - 1)
```

then for negative `n` we move away from zero:

```text
-3 -> -4 -> -5 -> ...
```

This never reaches the base case.

Important rule:

A recursive state must move toward the base case.

For negative powers:

```text
x^(-n) = 1 / x^n
```

Example:

```text
2^-3 = 1 / 2^3 = 1 / 8 = 0.125
```

---

## 4) First attempt for negative n

One idea is:

```java
n < 0 -> return (1 / x) * pow(x, n + 1)
```

This moves toward `0`:

```text
-3 -> -2 -> -1 -> 0
```

Example:

```text
pow(2, -3)
= (1/2) * pow(2, -2)
= (1/2) * (1/2) * pow(2, -1)
= (1/2) * (1/2) * (1/2) * pow(2, 0)
= 1/8 = 0.125
```

This is mathematically correct, but still too slow.

---

## 5) Why O(n) is too slow

With:

```java
n -> n - 1
```

for `n = 1,000,000,000`, the recursion depth is huge.

So the time complexity is:

```text
O(n)
```

This is not acceptable.

---

## 6) Key optimization — reduce n by half

Instead of reducing by 1, reduce by half:

```java
n -> n / 2
```

Use the identity:

```text
x^8 = x^4 * x^4
```

and in general:

```text
x^n = x^(n/2) * x^(n/2)
```

Therefore we can do:

```java
half = pow(x, n / 2);
return half * half;
```

This reduces recursion depth to:

```text
O(log n)
```

> **⚠ CRITICAL ADDITION — the #1 interview trap on this problem.**
>
> Look very carefully at *why* we store the result in `half` first:
>
> ```java
> // ✓ CORRECT — O(log n).  ONE recursive call.
> double half = pow(x, n / 2);
> return half * half;
>
> // ✗ WRONG — O(n).  TWO recursive calls. Looks identical. Is catastrophically slower.
> return pow(x, n / 2) * pow(x, n / 2);
> ```
>
> Both are **mathematically** identical. Only the first is **computationally** fast.
>
> ```text
>    ONE CALL  T(n) = T(n/2) + O(1)      ->  O(log n)      1,000,000,000 -> ~30 steps
>    TWO CALLS T(n) = 2T(n/2) + O(1)     ->  O(n)          1,000,000,000 -> 1e9 steps
>
>    THE RECURSION TREE TELLS THE WHOLE STORY:
>
>    ✗ TWO CALLS — a full binary tree, every node duplicated
>
>                      n
>                    /   \
>                 n/2     n/2          <- SAME value computed TWICE
>                /  \     /  \
>             n/4  n/4  n/4  n/4       <- computed FOUR times
>             / \  / \  / \  / \
>            ...  exponential blow-up ...
>
>            total nodes = 1 + 2 + 4 + ... = 2^(log n) = n     -> O(n)
>
>    ✓ ONE CALL — a single straight chain
>
>                      n
>                      |
>                     n/2
>                      |
>                     n/4
>                      |
>                     ...
>                      |
>                      0
>
>            total nodes = log2(n) + 1                         -> O(log n)
> ```
>
> **Say this out loud in the interview.** Interviewers specifically watch for whether you
> write `pow(...) * pow(...)`. It is the difference between a hire and a no-hire on this
> question, and by the Master Theorem it is the difference between `T(n)=T(n/2)+O(1)` and
> `T(n)=2T(n/2)+O(1)`.

---

## 7) Even exponent case

For even `n`:

```text
x^n = x^(n/2) * x^(n/2)
```

So:

```java
half = pow(x, n / 2);
return half * half;
```

Example:

```text
pow(2, 8)
half = pow(2, 4) = 16
return 16 * 16 = 256
```

---

## 8) Odd exponent case

For odd `n`:

```text
x^5 = x * x^4
```

and since:

```text
x^4 = x^2 * x^2
```

we get:

```text
x^5 = x * x^2 * x^2
```

So:

```java
half = pow(x, n / 2);
return x * half * half;
```

Example:

```text
pow(2, 5)
half = pow(2, 2) = 4
return 2 * 4 * 4 = 32
```

---

## 9) Important observation about `half`

Every recursive call has its own local variables.

So:

```java
double half = pow(x, n / 2);
```

in one call does not overwrite the value in another call.

Example:

```text
pow(2, 8)   -> half = 16
pow(2, 4)   -> half = 4
pow(2, 2)   -> half = 2
pow(2, 1)   -> half = 1
pow(2, 0)   -> base case
```

The value from the deeper call returns upward through the recursion stack.

---

## 10) Negative exponent + optimization

We know:

```text
x^(-n) = (1 / x)^n
```

So instead of a separate negative recursion style, we transform first:

```java
if (N < 0) {
    x = 1 / x;
    N = -N;
}
```

Then we apply the same positive-exponent recursion.

---

## 11) Integer.MIN_VALUE problem

Java `int` cannot store:

```text
2147483648
```

So for `n = Integer.MIN_VALUE`, doing:

```java
n = -n;
```

overflows.

This is why we use:

```java
long N = n;
```

Then:

```java
N = -N;
```

is safe.

---

## 12) Final recursive structure

Base case:

```java
if (n == 0) return 1;
```

Recursive step:

```java
half = pow(x, n / 2);
result = half * half;

if (n % 2 != 0) {
    result = x * result;
}

return result;
```

This is the divide-and-conquer binary exponentiation pattern.

---

## 13) Final Java code

```java
class Solution {
    public double myPow(double x, int n) {
        long N = n;

        if (N < 0) {
            x = 1 / x;
            N = -N;
        }

        return power(x, N);
    }

    private double power(double x, long n) {
        if (n == 0) {
            return 1;
        }

        double half = power(x, n / 2);
        double result = half * half;

        if (n % 2 != 0) {
            result = x * result;
        }

        return result;
    }
}
```

State:

## 22) ADDED — The bit-manipulation insight (why this is really about binary)

Binary exponentiation has nothing to do with "halving" in a mysterious way. It's just
**reading the binary representation of `n`**.

```text
   n = 13  =  1 1 0 1  (binary)
              ^ ^ ^ ^
              | | | |
              | | | +-- bit 0 (value 1)  -> multiply by x^1
              | | +---- bit 1 (value 2)  -> bit is 0, skip
              | +------ bit 2 (value 4)  -> multiply by x^4
              +-------- bit 3 (value 8)  -> multiply by x^8

   x^13 = x^8 * x^4 * x^1          (8 + 4 + 1 = 13)  ✓

   And each x^(2^k) is ONE squaring away from the previous:

        x^1  --square-->  x^2  --square-->  x^4  --square-->  x^8
```

```text
   THE ITERATION TABLE FOR x=2, n=13

   step | n (binary) | bit | base (x^(2^k)) | result
   -----+------------+-----+----------------+--------------------------
     0  |   1101     |  1  |       2        | 1 * 2      = 2
     1  |    110     |  0  |       4        | 2          = 2      (skip)
     2  |     11     |  1  |      16        | 2 * 16     = 32
     3  |      1     |  1  |     256        | 32 * 256   = 8192
     4  |      0     |  -  |       -        | STOP

   2^13 = 8192   ✓

   "n's bits tell you WHICH squares to keep.
    Squaring builds the squares. AND-ing picks them."
```

This is why `n` shrinking by half and `n` shifting right by one bit are **the same operation** —
`n / 2 == n >> 1`. The recursion depth is literally the **number of bits in `n`**, which is
`floor(log₂ n) + 1`. For `n = 2,147,483,647` that's **31 steps**.

## 23) ADDED — The iterative version (ship this in production)

`O(1)` space, no stack, and it falls straight out of Section 22.

```java
class Solution {
    public double myPow(double x, int n) {
        long N = n;                      // long FIRST — before any negation
        if (N < 0) {
            x = 1 / x;
            N = -N;                      // safe now: |MIN_VALUE| fits in long
        }

        double result = 1.0;
        while (N > 0) {
            if ((N & 1) == 1) {          // current bit is set -> keep this square
                result *= x;
            }
            x *= x;                      // build the next square: x^(2^k)
            N >>= 1;                     // move to the next bit
        }
        return result;
    }
}
```

**Read it as three lines of English:**

```text
   if the bit is set   -> fold the current square into the answer
   square the base     -> ready for the next bit
   shift n right       -> look at the next bit
```

**Why `(N & 1) == 1` beats `N % 2 != 0`:**

```text
   For POSITIVE n they are identical.
   For NEGATIVE n in Java:   -5 % 2  ==  -1   (NOT 1!)
                             -5 & 1  ==   1   (correct bit test)

   Your code only works because N was normalised to positive first.
   Using & makes it correct even if that normalisation is ever removed.
   It also expresses the INTENT: "is the low bit set?"
```

## 24) ADDED — Modular exponentiation (the real-world version)

This is what binary exponentiation is *actually used for*: RSA, Diffie–Hellman, hashing,
and roughly half of competitive programming.

```java
// Computes (base^exp) % mod  without ever overflowing.
long modPow(long base, long exp, long mod) {
    if (mod == 1) return 0;

    long result = 1;
    base %= mod;                         // reduce BEFORE you start

    while (exp > 0) {
        if ((exp & 1) == 1) {
            result = (result * base) % mod;   // reduce after EVERY multiply
        }
        base = (base * base) % mod;
        exp >>= 1;
    }
    return result;
}
```

```text
   WHY REDUCE AFTER EVERY MULTIPLY?

   result and base are each < mod.
   So result * base  <  mod^2.

   If mod fits in 32 bits (mod < 2^31), then mod^2 < 2^62 -> fits in long. ✓
   If mod is a full 64-bit value, mod^2 overflows long     -> you need
      Math.multiplyHigh, __int128, BigInteger, or Montgomery multiplication.

   THE RULE:  "Reduce early, reduce often, and check that mod^2 fits."
```

**Key identity that makes this legal:**

```text
   (a * b) mod m  ==  ((a mod m) * (b mod m)) mod m

   Modular arithmetic is a RING — multiplication commutes with taking the remainder.
   That is the ONLY reason you're allowed to reduce mid-computation.
```

> **Note:** this works for `+`, `-`, `*` but **NOT for `/`**. Division requires the modular
> multiplicative inverse (Fermat's little theorem: `a⁻¹ ≡ a^(m−2) mod m` when `m` is prime —
> which itself uses `modPow`). Interviewers love this loop-back.

# PHASE 2 — CONCEPT REBUILDING

## CONCEPT 1: Exponentiation by Squaring (Binary Exponentiation)

### LEVEL 1 — Beginner Intuition

**Why does it exist?**

Because multiplying one at a time is stupid when you can **reuse what you've already built**.

```text
   NAIVE: to get x^8 you do 7 multiplications
          x·x·x·x·x·x·x·x
          and you THREW AWAY every intermediate result along the way.

   SMART: to get x^8 you do 3 multiplications
          x^2 = x·x          (reuse x)
          x^4 = x^2·x^2      (reuse x^2)
          x^8 = x^4·x^4      (reuse x^4)

   Each step DOUBLES the exponent instead of adding 1 to it.
   Doubling reaches a billion in 30 steps. Adding reaches it in a billion.
```

**What problem does it solve?** Turning `O(n)` work into `O(log n)` work whenever the
operation is **associative** — meaning you're free to regroup it however you like.

**When to use it:** Any time you apply the same associative operation `n` times, where `n` is
large: powers, matrix powers, graph-path counting, repeated function application, modular
crypto.

### LEVEL 2 — Mental Visualization


**The doubling ladder (why it's logarithmic):**

```text
   exponent:  1    2    4    8    16   32   64  ...  2^30
              |    |    |    |    |    |    |         |
   squaring:  +----+----+----+----+----+----+---...---+
```

```text
                                            9/2 = 4 loses the odd one
```

### LEVEL 3 — Real-World Analogy

> **Exponentiation by squaring = FOLDING PAPER.**
> Fold a sheet once → 2 layers. Fold again → 4. Again → 8. After **42 folds** the stack would
> reach the Moon. You never counted to a trillion — you just **doubled 42 times.** That is
> exactly `O(log n)`.

> **The odd case = making change.**
> To pay ₹13 you use notes of ₹8, ₹4, ₹1 — the powers of two whose bits are set in `1101₂`.
> You don't hand over thirteen ₹1 coins.

> **`half * half` vs `pow() * pow()` = photocopying.**
> Make one copy and duplicate *it* (fast), versus walking back to the original document and
> re-typing it from scratch every single time (absurdly slow). Same output, wildly different
> cost.

> **Modular exponentiation = a clock.**
> `10^100 mod 12` is unthinkable if you compute `10^100` first. But on a **clock face** you
> just keep wrapping around — the number never grows past 12. Reduce early, reduce often.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"Naive exponentiation is `O(n)` — one multiply per unit of the exponent. But exponentiation
> is associative, so I can regroup: `x^n = (x^(n/2))²`, times an extra `x` if `n` is odd. That
> halves the exponent each step, so it's `O(log n)`. The critical detail is that I compute the
> half **once** and store it — writing `pow(x,n/2) * pow(x,n/2)` would recompute the same
> subtree and collapse right back to `O(n)`. Before recursing I normalise: if `n` is negative
> I replace `x` with `1/x` and negate `n`, and I widen `n` to a `long` first, because
> `-Integer.MIN_VALUE` overflows. Equivalently this is just reading the bits of `n` — square
> the base each step and multiply into the result wherever a bit is set — which gives me an
> iterative `O(1)`-space version."*

## CONCEPT 2: Normalise-Then-Solve (killing the negative case)

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because handling two symmetric cases with two code paths doubles your
bug surface. If you can **transform** one case into the other, you only write the logic once.

```text
   ✗ TWO CODE PATHS                      ✓ ONE CODE PATH
   ----------------                      ---------------
   if (n > 0) { ...recursion A... }      if (n < 0) { x = 1/x;  n = -n; }
   else       { ...recursion B... }      ...single recursion...

   Twice the code.                       Half the code.
   Twice the bugs.                       One place to be correct.
```

**The identity that makes it legal:** `x⁻ⁿ = (1/x)ⁿ`. You push the negation out of the
*exponent* and into the *base*, where it's free.

### LEVEL 2 — Mental Visualization

```text
   THE NORMALISATION STEP

      myPow(2, -3)
           |
           |  n < 0  ->  flip both
           v
      x = 1/2 = 0.5      n = 3
           |
           v
      power(0.5, 3) = 0.125       ✓   (same as 1/8)


   WHY YOU CANNOT JUST DO n = -n WITH AN int

      int n = Integer.MIN_VALUE;     // -2147483648
      n = -n;                        // ???

      +2147483648 does NOT fit in an int (max is 2147483647)
      so it WRAPS and becomes ... -2147483648 again.  STILL NEGATIVE.

      -> infinite recursion / wrong answer

   THE FIX — widen BEFORE you negate:

      long N = n;      //  -2147483648L     <- widen FIRST
      N = -N;          //  +2147483648L     <- fits easily in a long ✓

      ORDER MATTERS:
         long N = -n;   ✗  the negation happens in INT, then widens the garbage
         long N = n; N = -N;   ✓  widen, THEN negate
```

```text
   THE int NUMBER LINE — the asymmetry that bites

   -2147483648                 0                 2147483647
        |-------------------- | ------------------|
        ^                                          ^
        |                                          |
       MIN                                        MAX
        |<---- 2147483648 values ---->|<-- 2147483647 -->|

   There is NO positive partner for MIN_VALUE.
   |MIN| = |MAX| + 1.   Zero sits on the positive side, so negatives get one extra slot.
```

### LEVEL 3 — Real-World Analogy

> **Normalisation = converting all currencies to one before adding.**
> You don't write separate addition rules for rupees, dollars and yen. You convert once at the
> door, then use a single adder.

> **The `MIN_VALUE` overflow = a hotel with rooms 1–100 and a basement room −100.**
> Every guest can "swap to the opposite floor" — except the one in −100, because room +100
> doesn't exist. He swaps and ends up back in his own room, confused. That's `-MIN_VALUE`.

> **`x⁻ⁿ = (1/x)ⁿ` = walking backwards vs turning around.**
> Instead of learning to walk backwards (a whole new skill), you **turn around once** and walk
> forwards normally.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"Rather than writing a separate recursion for negative exponents, I normalise the input:
> `x⁻ⁿ` equals `(1/x)ⁿ`, so I invert the base, make the exponent positive, and then run a
> single positive-exponent algorithm. The one trap is that `n` can be `Integer.MIN_VALUE`,
> and `-Integer.MIN_VALUE` overflows back to itself because two's complement is asymmetric.
> So I widen to `long` **before** negating — `long N = n;` then `N = -N;`, not `long N = -n;`,
> because in the second form the negation still happens in `int` arithmetic."*

## CONCEPT 3: One Sub-call vs Two — the Recurrence That Decides Everything

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because complexity isn't determined by how much *smaller* the
subproblem is — it's determined by **how many subproblems you create.**

```text
   THE THREE CLASSIC SHAPES

   T(n) = T(n/2) + O(1)      ->  O(log n)    binary search, THIS problem
   T(n) = 2T(n/2) + O(1)     ->  O(n)        naive tree recursion
   T(n) = 2T(n/2) + O(n)     ->  O(n log n)  merge sort
   T(n) = 2T(n-1) + O(1)     ->  O(2^n)      subsets, naive Fibonacci

   Halving the input is NOT what makes you fast.
   Halving the input AND NOT DUPLICATING WORK is what makes you fast.
```

### LEVEL 2 — Mental Visualization

```text
   SAME PROBLEM, TWO RECURRENCES, WILDLY DIFFERENT COST   (n = 8)

   ✗  return pow(x,n/2) * pow(x,n/2);          ->  T(n) = 2T(n/2) + O(1)

                          8
                      /       \
                    4           4
                  /   \       /   \
                 2     2     2     2
                / \   / \   / \   / \
               1  1  1  1  1  1  1  1
              /\ /\ /\ /\ /\ /\ /\ /\
              0000000000000000            <- 15 internal + 16 leaves

              CALLS ≈ 2n = 16             work grows LINEARLY with n


   ✓  double h = pow(x,n/2); return h*h;      ->  T(n) = T(n/2) + O(1)

                          8
                          |
                          4
                          |
                          2
                          |
                          1
                          |
                          0

              CALLS = log2(8) + 1 = 4     work grows LOGARITHMICALLY


   FOR n = 1,000,000,000:
        ✗  ~2,000,000,000 calls   -> several seconds, or StackOverflow/TLE
        ✓  ~31 calls              -> instant
```

**The memory aid:**

```text
   +--------------------------------------------------------------+
   |  COUNT THE RECURSIVE CALLS IN YOUR CODE, NOT THE MATH.       |
   |                                                              |
   |  "pow(...)" appears TWICE on that line?  -> you have O(n).    |
   |  Store it in a variable.  ONE call. ONE time.                 |
   +--------------------------------------------------------------+
```

### LEVEL 3 — Real-World Analogy

> **This is the Fibonacci lesson in disguise.**
> `fib(n) = fib(n-1) + fib(n-2)` is exponential purely because it recomputes the same values
> over and over. Memoisation fixes Fibonacci; a **local variable** fixes `pow`. Same disease —
> *recomputation* — cured by the cheapest possible medicine.

> **Making a cake for a party.**
> Bake one cake and cut it in half (one call, reuse). Don't bake **two identical cakes from
> scratch** because the recipe mentions "half a cake" twice.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The complexity here is decided by the recurrence, not by the fact that I'm halving. If I
> store the sub-result in a local and square it, the recurrence is `T(n) = T(n/2) + O(1)`,
> which unrolls to `O(log n)`. If I instead write `pow(x,n/2) * pow(x,n/2)`, the recurrence
> becomes `T(n) = 2T(n/2) + O(1)`, and by the Master Theorem that's `O(n^log₂2) = O(n)` — I'd
> have thrown away the entire optimisation while the code still looks correct. So the rule I
> apply is: count the recursive calls that actually execute, not the ones in the formula."*

## CONCEPT 4: Floating-Point Reality (what `double` actually does)

### LEVEL 1 — Beginner Intuition

**Why does it matter?** Because `double` is not a real number. It's 64 bits: 1 sign, 11
exponent, 52 stored mantissa bits (53 effective). Every multiplication rounds. LeetCode accepts
answers within `1e-5` **precisely because** exact equality is impossible.

### LEVEL 2 — Mental Visualization

```text
   IEEE 754 double — 64 bits

   +---+-----------+------------------------------------------------------+
   | S |  EXPONENT |                    MANTISSA                          |
   | 1 |    11     |                       52                             |
   +---+-----------+------------------------------------------------------+
     ^       ^                              ^
     |       |                              +-- ~15-17 decimal digits of precision
     |       +---------------------------------- range ~1e-308 .. 1e308
     +------------------------------------------ sign

   CONSEQUENCES FOR pow:

   x = 2.0,  n = 1024    ->  2^1024 > 1.8e308   ->  Infinity     (OVERFLOW)
   x = 0.5,  n = 1074    ->  < 4.9e-324         ->  0.0          (UNDERFLOW)
   x = 2.0,  n = -2^31   ->  astronomically small ->  0.0        ✓ expected answer
   x = 0.1,  n = 2       ->  0.010000000000000002  NOT 0.01      (rounding)


   ERROR ACCUMULATION — squaring is actually BETTER than naive:

        naive  : n multiplications   -> relative error grows like  n·ε
        squaring: log n multiplications -> relative error grows like log n·ε

        for n = 1e9:   naive ~1e9·ε        squaring ~30·ε
                       (also 1e9 times slower)

   So binary exponentiation is FASTER *and* MORE ACCURATE. Say this — it surprises people.
```

### LEVEL 3 — Real-World Analogy

> **`double` = a ruler with finite tick marks.**
> No matter how fine the ticks, some lengths fall *between* them, and you must round to the
> nearest tick. Do that a billion times and the drift is visible. Do it thirty times and it
> isn't.

> **Overflow to `Infinity` = a bathroom scale that maxes out.**
> Past its limit it doesn't report a bigger number — it just reads `ERR`. IEEE 754 reads
> `Infinity`, and it doesn't throw.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"`double` gives about 15–17 significant decimal digits, so exact comparison is meaningless
> — that's why the problem allows a `1e-5` tolerance. Worth noting: repeated squaring performs
> only `O(log n)` multiplications instead of `O(n)`, so it accumulates **less** rounding error
> than the naive loop — it's faster and more accurate. I'd also confirm the expected behaviour
> for overflow and underflow: `2^2147483647` saturates to `Infinity` and `2^-2147483648`
> underflows to `0.0`, and neither throws in Java."*

## 2. STORY METHOD

### The Master Story: **THE PAPER FOLDER**

> A student is told: *"Make me a stack of paper as thick as the distance to the Moon."*
>
> **The slow student (naive `O(n)`)** starts stacking sheets one at a time. One, two, three…
> He is still stacking when the Sun burns out. He needs about 10⁴⁰ sheets.
>
> **The clever student (binary exponentiation)** takes **one** sheet and **folds it**.
> 2 layers. Fold again: 4. Again: 8. He is *doubling*, not adding. After **42 folds** his
> stack reaches the Moon. Forty-two moves versus 10⁴⁰.
>
> **The trap (`pow() * pow()`).** A third student also folds — but each time he needs a folded
> sheet, he walks back to the paper mill and **manufactures a fresh one from a tree**, twice
> over. He's technically "halving", yet he does more work than the slow student. *Halving only
> helps if you reuse what you already built.*
>
> **The odd sock (odd exponents).** When the count is odd, folding gives you one layer too few.
> There is always **one leftover sheet** you must lay on top by hand. That's `result *= x`.
>
> **The mirror (negative exponents).** Asked for a stack that goes *downward*, the clever
> student doesn't invent a new folding technique — he **turns the whole stack upside down once**
> (`x = 1/x`) and folds exactly as before.
>
> **The one-room hotel (`MIN_VALUE`).** He's told "flip the sign of your instruction number."
> Every number flips fine — except `-2147483648`, which has no positive twin, so it flips into
> itself. The clever student first copies the number onto a **bigger notepad** (`long`), and
> only *then* flips it.

```text
   FOLD   FOLD   FOLD   ...   FOLD      + 1 loose sheet if odd
     |      |      |            |              |
     x^2    x^4    x^8   ...  x^(2^k)        · x
      \______\______\_____ ... __/             |
                   |                           |
                   +-------- multiply the ones whose BIT IS SET
```

### Mini-story: **The clock (modular exponentiation)**

> A monk must compute `7^1000000 mod 12`. He does *not* write out `7^1000000` — no paper on
> Earth would hold it. He watches a **clock**: every time the hand passes 12, he forgets the
> laps and keeps only the position. The number never exceeds 12. *Reduce early, reduce often.*

### Mini-story: **Two cakes**

> The recipe says *"combine half a cake with half a cake."* The wise baker bakes **one** cake
> and cuts it. The foolish baker bakes **two full cakes** because the phrase appears twice —
> and then his apprentices do the same, recursively, until the kitchen holds `n` cakes. Same
> dessert. Exponentially more flour.

# PHASE 4 — INTERVIEW PATTERN RECOGNITION

## WHEN TO USE: Binary Exponentiation

```text
   USE WHEN:

   ✓ You apply the SAME operation n times, and n is LARGE
   ✓ The operation is ASSOCIATIVE:  (a∘b)∘c == a∘(b∘c)
   ✓ There is an IDENTITY element (1 for ×, identity matrix for matmul)
   ✓ The problem says "n can be up to 1e9" or "1e18"  <- screaming hint
   ✓ You need (a^b) mod m
   ✓ You need the nth term of a LINEAR recurrence (-> matrix power)
   ✓ Repeated doubling would work: "after k operations" queries

   DO NOT USE WHEN:

   ✗ The operation is NOT associative (subtraction, division)
   ✗ n is tiny (< ~30) — a plain loop is clearer and just as fast
   ✗ Intermediate values overflow and you have no modulus to tame them
   ✗ The state changes between applications (not a fixed repeated op)
```

## WHEN TO USE: Normalise-Then-Solve

```text
   ✓ Symmetric ± cases that differ only by a sign
   ✓ You're about to write two near-identical branches
   ✓ An identity exists that maps hard case -> easy case
        x^-n = (1/x)^n        |a - b| symmetry      reverse-and-solve
   ✓ ALWAYS pair it with: "can the normalisation itself overflow?"
```

## INTERVIEW TRIGGER WORDS

```text
+==========================================================================+
|  TRIGGER WORDS                              =>  THINK                    |
+==========================================================================+
|  "n up to 10^9"  "10^18"  "very large n"    =>  BINARY EXPONENTIATION    |
|  "x to the power n"  "a^b"                  =>  EXPONENTIATION BY SQUARING|
|  "modulo 10^9+7"  "mod p"                   =>  MODULAR EXPONENTIATION   |
```

# PHASE 8 — FAANG FOLLOW-UP QUESTIONS

**Q1. "Do it iteratively — `O(1)` space."**
Section 23. Square the base, shift the exponent, multiply in wherever a bit is set. This is
the expected final answer; the recursion is just how you *explain* it.

**Q2. "Why `half*half` instead of `pow(x,n/2)*pow(x,n/2)`? Quantify it."**
One call gives `T(n)=T(n/2)+O(1) = O(log n)`; two calls give `T(n)=2T(n/2)+O(1) = O(n)` by the
Master Theorem (`a=2, b=2, f(n)=O(1)` ⇒ `O(n^log₂2) = O(n)`). For `n=10⁹` that's 31 calls
versus ~2×10⁹. Same maths, 60-million-fold difference.

**Q3. "Compute `(x^n) mod m`."**
Section 24. Reduce after every multiply. Warn that `result*base` reaches `mod²`, so `mod` must
be under 2³¹ for `long` to be safe; otherwise use `Math.multiplyHigh`, `BigInteger`, or
Montgomery multiplication.

**Q4. "`n` is a 1000-digit number given as `int[]`." (LC 372)**
Use `a^(10·d + r) = (a^d)^10 · a^r` and peel digits from the end:
`superPow(a, b[0..k]) = modPow(superPow(a, b[0..k-1]), 10) * modPow(a, b[k])`.
Also note Euler's theorem lets you reduce the exponent mod `φ(m)` when `gcd(a,m)=1`.

**Q5. "Now do it for matrices — give me Fibonacci in `O(log n)`."**
Binary exponentiation needs only **associativity**, and matrix multiplication is associative.

```text
   [ F(n+1)  F(n)  ]     [ 1  1 ]^n
   [ F(n)    F(n-1)]  =  [ 1  0 ]

   Replace `*` with matMul and `1` with the identity matrix. The algorithm is UNCHANGED.
   Cost: O(k^3 log n) for a k x k matrix -> O(8 log n) = O(log n) for Fibonacci.
```
This generalises to **any linear recurrence** — that's the big idea.

**Q6. "Can it be parallelised?"**
Poorly, and saying so is correct. The chain `x → x² → x⁴ → x⁸` is strictly sequential — each
squaring needs the previous result. You *can* split the exponent: `x^n = x^a · x^b` with
`a+b=n`, compute the two halves on separate cores, and multiply. That gives a ~2× speedup, not
a `log` improvement. For **matrix** power, parallelise inside each multiplication instead.

**Q7. "What if `x` is a `BigDecimal` / `BigInteger`?"**
The algorithm is identical, but the cost model changes: multiplication is no longer `O(1)`.
Numbers double in size each squaring, so the total is dominated by the final multiply —
roughly `O(M(n·log x))` where `M` is your multiplication cost. Note `BigInteger.modPow`
already implements this (with Montgomery reduction).

**Q8. "What's the precision error?"**
Each `double` multiply has relative error ≤ `ε = 2⁻⁵³ ≈ 1.1e-16`. Binary exponentiation does
`O(log n)` multiplies, so the bound is `~(log₂n)·ε`. For `n=2³¹` that's `~31ε ≈ 3.4e-15` —
comfortably inside the `1e-5` tolerance, and *far* better than naive's `n·ε`.

**Q9. "Would you invert the base first, or invert the result at the end?"**
Subtle and a great senior answer: `x = 1/x` introduces one rounding error that then gets
**squared repeatedly**, amplifying it. Computing `x^|n|` and inverting **once** at the end
introduces the rounding only at the final step. The end-inversion is slightly more accurate —
but it risks intermediate **overflow to `Infinity`** (e.g. `x=2, n=-2000` gives `2^2000 = Inf`,
then `1/Inf = 0.0`, which happens to be right, but the reasoning is fragile). In practice
invert-first is the safer, standard choice. **Mention both and justify your pick.**

**Q10. "What about `0^0`?"**
LC 50 and IEEE 754 both define `pow(0,0) = 1`. Mathematicians argue; the spec doesn't.
Your base case `if (n == 0) return 1;` handles it for free — **point that out**.

**Q11. "What if `x = 0` and `n < 0`?"**
`1/0 = Infinity` in IEEE 754 (no exception). LC constraints exclude it, but in production
you'd throw `ArithmeticException` or return `Infinity` by contract. **Ask which.**

**Q12. "Handle overflow and underflow of the result."**
`2^1024` → `Infinity`; `0.5^1074` → `0.0` (subnormal then zero). Neither throws. If you need
detection, check `Double.isInfinite(result)` / `result == 0.0 && x != 0.0`, or work in
log-space (`n·ln x`) and check the magnitude before exponentiating.

**Q13. "Compute `x^(1/n)` — the nth root."**
Different algorithm entirely: binary search on the answer, or Newton–Raphson
`y ← y − (yⁿ − x)/(n·yⁿ⁻¹)`, which converges quadratically. Binary exponentiation evaluates
`yⁿ` **inside** each Newton iteration — the two compose nicely.

**Q14. "Can you reduce the number of multiplications below `log₂n`?"**
Yes — **addition-chain exponentiation**. Binary uses `~log₂n + popcount(n)` multiplies;
optimal addition chains can do better (e.g. `x^15` in 5 multiplies, not 6). Finding the
shortest chain is NP-hard in general, but **sliding-window / k-ary exponentiation** is a
practical middle ground used in real crypto libraries.

**Q15. "What if `n` can be `long` — up to 10¹⁸?"**
Nothing changes structurally; the loop runs ~60 times instead of ~31. Only the
*normalisation* needs care: `-Long.MIN_VALUE` overflows and there's no wider primitive — use
`Math.negateExact` (throws) or `BigInteger`/unsigned handling.

**Q16. "Can you memoise anything?"**
No — every subproblem is visited exactly once in the one-call version, so there's nothing to
cache. Memoisation is the fix for the **two-call bug**, but eliminating the second call is
strictly better (it removes both the time *and* the memory cost). Saying this shows you
understand *why* memoisation works.

**Q17. "How would you test a floating-point function?"**
Never `assertEquals` on doubles. Use `assertEquals(expected, actual, 1e-9)` or compare
**relative** error for large magnitudes. Layer it: (1) exact small cases; (2) boundary values
`n = 0, ±1, MIN_VALUE, MAX_VALUE`; (3) `x = 0, 1, -1`; (4) property tests — `pow(x,a)*pow(x,b)
== pow(x,a+b)` within tolerance; (5) differential testing against `Math.pow`.

**Q18. "Why doesn't the JDK use binary exponentiation for `Math.pow`?"**
Because `Math.pow` takes a **double** exponent, not an integer. It computes `exp(y·ln x)` with
extended-precision tricks to keep the result within 1 ulp. Binary exponentiation only applies
to *integer* exponents. Knowing this distinction is a strong signal.

**Q19. "This runs a billion times a second. Optimise it."**
Profile first. Then: use the iterative form (no call overhead), keep it small enough for JIT
inlining, special-case `n ∈ {0,1,2}` and `x ∈ {0,1,-1}`, and avoid the `1/x` division when
`n > 0`. For batch workloads, vectorise across *many* `(x,n)` pairs rather than optimising one.

**Q20. "What if the data is distributed?"**
A single power never justifies distribution. But `x^n` splits cleanly: node `i` computes
`x^(nᵢ)` with `Σnᵢ = n`, then you multiply the partials — a perfectly associative reduce.
The realistic distributed case is computing **many** independent powers, which is
embarrassingly parallel.

**Q21. "What if `n` changes continuously — streaming updates?"**
Maintain `x^n` incrementally: `n+1` → multiply by `x`; `n−1` → divide by `x` (watch precision
drift); `n → 2n` → square. If updates are arbitrary jumps, recompute in `O(log n)` — it's
already cheap. Under a modulus, "divide" means multiplying by the modular inverse.

**Q22. "Prove your algorithm is correct."**
Strong induction on `n`. *Base:* `n=0` returns 1 = `x⁰`. ✓ *Step:* assume correct for all
`k < n`. If `n` is even, `n/2 < n`, so `half = x^(n/2)` and `half² = x^n`. ✓ If `n` is odd,
`n/2 = (n−1)/2`, so `half² = x^(n−1)` and `x·half² = x^n`. ✓ Termination: `n` strictly
decreases and is bounded below by 0. ∎

**Q23. "What's `Math.abs(Integer.MIN_VALUE)`?"**
`Integer.MIN_VALUE` — still negative. This is why the note widens to `long`. Any solution that
calls `Math.abs(n)` on an unvalidated `int` has the same latent bug.

**Q24. "Write it tail-recursively."**
Carry an accumulator: `power(x, n, acc)` where odd `n` folds `x` into `acc`. This links
directly to the atoi note's accumulator pattern — and the same caveat applies: the JVM has no
TCO, so it's still `O(log n)` stack (which is harmless here — 31 frames).

**Q25. "Where is this used in real systems?"**
RSA and Diffie–Hellman (modpow is *the* primitive), hash functions (polynomial rolling hashes),
`BigInteger.modPow`, competitive programming under `mod 1e9+7`, matrix-power solutions to
linear recurrences, binary lifting for LCA queries, and fast computation of transition
probabilities in Markov chains.

# PHASE 9 — COMMON INTERVIEW MISTAKES

| # | Mistake | Why it's fatal | Fix |
|---|---|---|---|
| 1 | `return pow(x,n/2) * pow(x,n/2);` | Silently `O(n)` instead of `O(log n)` — the #1 rejection | Store it: `double h = pow(x,n/2); return h*h;` |
| 2 | `int n = -n;` on `Integer.MIN_VALUE` | Overflows to itself → infinite recursion / wrong answer | `long N = n;` **then** `N = -N;` |
| 3 | `long N = -n;` (negate then widen) | Negation still happens in `int` — same overflow | Widen **first**, negate **second** |
| 4 | Forgetting the odd case | `x^5` computed as `x^4` — silently wrong | `if ((n & 1) == 1) result *= x;` |
| 5 | Recursing with `n-1` for negative `n` without normalising | Moves *away* from the base case → infinite recursion | Normalise to positive up front |
| 6 | Base case `n == 1` instead of `n == 0` | Breaks for `n = 0`; `x^0` must be 1 | Use `n == 0 → 1` |
| 7 | `n % 2 != 0` on a negative `n` | Java gives `-5 % 2 == -1`, not `1` | Use `(n & 1) == 1`, and normalise first anyway |
| 8 | Claiming `O(1)` space for the recursive version | It's `O(log n)` stack; interviewers always probe | Say `O(log n)`, then offer the iterative `O(1)` |
| 9 | Using `Math.pow` when asked to implement it | Answers nothing | Implement it; mention `Math.pow` only as a contrast |
| 10 | `Math.abs(n)` to normalise | `Math.abs(MIN_VALUE) == MIN_VALUE` | Widen to `long` and negate |
| 11 | Comparing doubles with `==` in tests | Rounding makes exact equality fail | Compare within `1e-9`, or relative error |
| 12 | Not handling `x = 1.0` / `-1.0` with huge `n` | Works, but misses a free `O(1)` early exit | Optional guard; at minimum *mention* it |
| 13 | Ignoring result overflow/underflow | `2^10⁹` is `Infinity`, not a number | State the expected behaviour explicitly |
| 14 | Forgetting `0^0 = 1` | Off-by-convention error | The `n == 0` base case covers it — say so |
| 15 | Recomputing `n/2` multiple times | Minor, but signals sloppiness | Compute once into a local |
| 16 | In modpow, reducing only at the end | `x^n` overflows long long before that | Reduce after **every** multiply |
| 17 | In modpow, forgetting `base %= mod` initially | First squaring can already overflow | Reduce the base before the loop |
| 18 | Assuming modpow works for division | Division isn't defined under mod | Use the modular inverse (`a^(p−2) mod p`) |
| 19 | Writing the recursion before stating the recurrence | You can't justify your complexity | Say `T(n)=T(n/2)+O(1)` out loud first |
| 20 | Not testing `n = 0`, `n = MIN_VALUE`, `x = 0` | Exactly the inputs that fail you | Dry-run these three, always |

```text
   THE 4 MISTAKES THAT ACTUALLY FAIL CANDIDATES

   +---+---------------------------------------------------------+
   | 1 | pow(x,n/2) * pow(x,n/2)   -> secretly O(n)              |
   | 2 | int negation of MIN_VALUE -> overflow, infinite loop     |
   | 3 | Forgetting the odd-exponent fix-up                       |
   | 4 | Saying "O(1) space" about a recursive solution           |
   +---+---------------------------------------------------------+
```

# PHASE 10 — REVISION SECTIONS

## 2-MINUTE REVISION

```text
   N.B.H.O.C.

   NEGATIVE   long N = n;  if (N < 0) { x = 1/x;  N = -N; }   <- widen BEFORE negate
   BASE       if (N == 0) return 1;                            <- also gives 0^0 = 1
   HALF       double h = power(x, N/2);     <- ONE call, STORED in a local
   ODD        if ((N & 1) == 1) result *= x;
   COMBINE    result = h * h;

   ITERATIVE (ship this):
       res = 1
       while (N > 0) { if (N&1) res *= x;   x *= x;   N >>= 1; }

   COMPLEXITY  O(log n) time | O(log n) stack recursive | O(1) iterative

   THE TRAP    pow(x,n/2)*pow(x,n/2)  ->  T(n)=2T(n/2)+O(1)  ->  O(n)   ✗
               h = pow(x,n/2); h*h    ->  T(n)=T(n/2)+O(1)   ->  O(log n) ✓

   BIT VIEW    n = 1101b = 13   ->   x^13 = x^8 · x^4 · x^1

   HOOK: THE PAPER FOLDER — 42 folds reach the Moon. Doubling, not adding.
```

## 10-MINUTE REVISION

**The derivation you should narrate in an interview**

```text
   1. Naive: x^n = x · x^(n-1)            -> O(n). Too slow for n = 1e9.
   2. Negative n with n-1 moves AWAY from the base case -> never terminates.
   3. Identity: x^(-n) = (1/x)^n          -> normalise, then only solve positive.
   4. Identity: x^n = (x^(n/2))^2         -> exponent HALVES -> O(log n).
   5. Odd n: integer division drops one x -> multiply it back.
   6. Overflow: -Integer.MIN_VALUE wraps  -> widen to long FIRST.
```

**The two recurrences (know these cold)**

| Code | Recurrence | Complexity |
|---|---|---|
| `h = pow(x,n/2); return h*h;` | `T(n) = T(n/2) + O(1)` | `O(log n)` ✓ |
| `return pow(x,n/2)*pow(x,n/2);` | `T(n) = 2T(n/2) + O(1)` | `O(n)` ✗ |

**The overflow story**

```text
   int range: [-2147483648, 2147483647]     |MIN| = |MAX| + 1
   -MIN_VALUE  == MIN_VALUE   (wraps to itself)
   Math.abs(MIN_VALUE) == MIN_VALUE

   long N = n;  N = -N;    ✓   widen, then negate
   long N = -n;            ✗   negates in int, THEN widens the garbage
```

**The bit view**

```text
   n = 13 = 1101b
   x^13 = x^8 · x^4 · x^1

   while (N > 0) { if (N&1) res *= x;   x *= x;   N >>= 1; }
                    ^^^^^^ pick        ^^^^^^ build   ^^^^^ advance
```

**Modular version (memorise the shape)**

```text
   base %= mod;                              <- reduce before starting
   while (exp > 0) {
       if ((exp & 1) == 1) res = res*base % mod;   <- reduce every multiply
       base = base*base % mod;
       exp >>= 1;
   }
   Requires mod^2 to fit in long  =>  mod < 2^31 is safe.
```

**Edge cases to say out loud**

```text
   n = 0            -> 1     (and 0^0 = 1)
   n = MIN_VALUE    -> the long-widening case
   x = 1 or -1      -> huge n must still be instant
   x = 0, n < 0     -> Infinity; ask the interviewer for the contract
   result overflow  -> Infinity;  underflow -> 0.0;  neither throws
```

## 30-MINUTE REVISION

**1. Write the recursive version from memory, then the iterative version (§23).**
Time yourself. Both should take under three minutes.

**2. Explain the `half*half` trap using the recursion tree**, and state both recurrences with
the Master Theorem result.

**3. Derive the bit view.** Write out `n = 13 = 1101₂` and trace the iteration table from §22
by hand for `x = 2`. Confirm you get 8192.

**4. Explain the `MIN_VALUE` overflow**, including why `long N = -n;` is wrong but
`long N = n; N = -N;` is right. State `Math.abs(MIN_VALUE) == MIN_VALUE`.

**5. Write `modPow` from memory (§24).** Explain why you reduce after every multiply and what
constraint that puts on `mod`.

**6. Derive the modular inverse connection:** division is illegal under mod; Fermat gives
`a⁻¹ ≡ a^(p−2) (mod p)` for prime `p` — which is computed with `modPow`.

**7. Do the matrix generalisation.** Write `[[1,1],[1,0]]^n` and explain why the *identical*
algorithm gives Fibonacci in `O(log n)`. State the requirement: associativity + identity.

**8. Prove correctness by strong induction** (Phase 8 Q22), out loud, in under a minute.

**9. Discuss floating point:** 53-bit mantissa, `1e-5` tolerance, `O(log n)·ε` error versus
naive `O(n)·ε`, overflow to `Infinity`, underflow to `0.0`.

**10. Solve the sibling problems in order:**
LC 231 (power of two, bits) → LC 29 (Divide Two Integers, same overflow trap) →
LC 372 (Super Pow, digit-wise) → Fibonacci by matrix power (the big generalisation).

```text
   The algorithm is famous — they assume you know it.
   What they're really testing is whether you handle MIN_VALUE and
   whether you accidentally write the O(n) version.
```

## The traps, ranked by how often they're sprung

```text
   TRAP 1  n = -2147483648  (Integer.MIN_VALUE)
           The single most common failure. -n overflows to itself.
           They WILL test this input. Widen to long first.

   TRAP 2  "Write it out" -> you type pow(x,n/2)*pow(x,n/2)
           Looks right, passes small tests, times out on n = 1e9.
           Interviewers watch your fingers for this exact line.

   TRAP 3  "What's the space complexity?"
           Answering O(1) for the recursive version is an instant flag.
           It is O(log n). ~31 frames for a 32-bit exponent.

   TRAP 4  n = 0
           Base case must be n == 0 -> 1, not n == 1 -> x.

   TRAP 5  x = 1.0 or -1.0 with n = 2147483647
           Correct code is instant. Naive O(n) code hangs here —
           it's the cheapest way for them to detect the O(n) bug.

   TRAP 6  "Now mod it by 1e9+7"
           Reveals whether you understand WHY reduction is legal,
           or just memorised a template.

   TRAP 7  Comparing your double output with ==
           In their test harness, or yours. Use a tolerance.
```

## Most frequent follow-ups (in real loops)

1. *"Now iteratively."* — expect this ~90% of the time.
2. *"Why did you store `half` in a variable?"* — they want the recurrence, out loud.
3. *"What if `n` is `Integer.MIN_VALUE`?"* — often asked *after* you finish, as a gotcha.
4. *"Now compute it modulo 10⁹+7."*
5. *"Can you use this to compute Fibonacci fast?"* — the matrix jump.
6. *"What's the space complexity, exactly?"*

## Optimisation discussion — what to say, in order

```text
   1. "The naive approach is O(n). For n up to 2^31 that's ~2 billion
       multiplications — far too slow."

   2. "Exponentiation is associative, so I can regroup as (x^(n/2))^2.
       That gives T(n) = T(n/2) + O(1) = O(log n) — about 31 steps."

   3. "I store the half in a local. Calling pow twice would make it
       T(n) = 2T(n/2) + O(1) = O(n) — I'd lose the entire optimisation."

   4. "Space is O(log n) for the recursion. The iterative bit-loop version
       is O(1), and that's what I'd ship."

   5. "Bonus: fewer multiplications also means LESS floating-point error —
       O(log n)·eps instead of O(n)·eps. Faster AND more accurate."

   6. "If this were hot, I'd special-case x = 0, 1, -1 and n = 0, 1, 2,
       and keep the method small enough to inline. But I'd profile first."
```

## Complexity cheat sheet

| Approach | Time | Space | Notes |
|---|---|---|---|
| Naive loop / `x·pow(x,n-1)` | `O(n)` | `O(n)` stack | TLE for `n > 10⁶`; stack overflow |
| **Two-call "halving"** | `O(n)` | `O(log n)` | **The trap.** Looks logarithmic, isn't |
| Recursive binary exponentiation | `O(log n)` | `O(log n)` stack | Interview-explainable form |
| **Iterative binary exponentiation** | `O(log n)` | `O(1)` | **Ship this** |
| Modular exponentiation | `O(log n)` | `O(1)` | Needs `mod² ` to fit in `long` |
| Matrix exponentiation (k×k) | `O(k³ log n)` | `O(k²)` | Linear recurrences, path counting |
| `BigInteger.modPow` | `O(M(b) log n)` | — | JDK built-in, Montgomery reduction |
| `Math.pow` | ~`O(1)` | `O(1)` | Different algorithm: `exp(y·ln x)` |

## Magic numbers & identities cheat sheet

```text
   Integer.MAX_VALUE =  2147483647   = 2^31 - 1
   Integer.MIN_VALUE = -2147483648   = -2^31
   -Integer.MIN_VALUE == Integer.MIN_VALUE      (overflow, wraps to itself)
   Math.abs(Integer.MIN_VALUE) == Integer.MIN_VALUE

   Long.MAX_VALUE = 9223372036854775807 = 2^63 - 1
   Common modulus: 1_000_000_007 (prime)  -> mod^2 ≈ 1e18 < 9.2e18  ✓ fits in long

   IDENTITIES
   x^0   = 1                 (including 0^0 = 1 by convention)
   x^-n  = (1/x)^n
   x^n   = (x^(n/2))^2                       n even
   x^n   = x · (x^(n/2))^2                   n odd
   x^(a+b) = x^a · x^b
   (a·b) mod m = ((a mod m)·(b mod m)) mod m
   a^(p-1) ≡ 1 (mod p)        Fermat, p prime, gcd(a,p)=1
   a^(-1)  ≡ a^(p-2) (mod p)  modular inverse

   double: 53-bit mantissa, ~15-17 decimal digits, range ~1e-308 .. 1.8e308
   epsilon = 2^-53 ≈ 1.11e-16
```

## The one-line recall (upgraded)

```text
long N = n FIRST -> if N<0 { x = 1/x; N = -N } -> N==0 return 1 ->
h = power(x, N/2) ONCE stored -> res = h*h -> if (N&1) res *= x ->
O(log n) because T(n)=T(n/2)+O(1) -> iterative bit-loop gives O(1) space ->
same algorithm works for mod and for matrices.
```

## Final takeaway (upgraded)

```text
   THREE THINGS TO CARRY OUT OF THIS PROBLEM INTO EVERY OTHER PROBLEM:

   1. ASSOCIATIVITY BUYS YOU LOGARITHMS
      If an operation is associative, you can regroup it — and regrouping
      into halves turns O(n) into O(log n). This is why the SAME code
      computes powers, modular powers, matrix powers, and tree jumps.

   2. COUNT THE RECURSIVE CALLS, NOT THE MATHS
      T(n)=T(n/2)+O(1) is O(log n). T(n)=2T(n/2)+O(1) is O(n).
      The difference is one local variable. Complexity lives in the
      recurrence, and the recurrence lives in your code, not your intent.

   3. NORMALISE EARLY — AND CHECK THAT THE NORMALISATION IS SAFE
      Collapsing the negative case into the positive one halves your code.
      But the collapse itself can overflow: widen to long BEFORE you negate,
      because |MIN_VALUE| = |MAX_VALUE| + 1.
```

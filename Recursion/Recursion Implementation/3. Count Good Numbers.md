## 1) Core idea

A digit string is called good if:

- even indices must be even digits
- odd indices must be prime digits

Indices are 0-based.

Even digits:

- 0, 2, 4, 6, 8
- choices = 5

Prime digits:

- 2, 3, 5, 7
- choices = 4

So each position is independent.

Instead of generating strings, count the number of valid choices per position.

## 2) First observation

For every even index:

- 5 choices

For every odd index:

- 4 choices

So the total number of valid strings is:

```text
5 × 5 × 5 × ... (for even positions)
×
4 × 4 × 4 × ... (for odd positions)
```

Example: `n = 1`

- index 0 is even
- choices = 5

Answer = 5

## 5) Count even and odd positions

We need to know:

- how many even indices exist
- how many odd indices exist

Examples:

- `n = 1` → even = 1, odd = 0
- `n = 2` → even = 1, odd = 1
- `n = 3` → even = 2, odd = 1
- `n = 4` → even = 2, odd = 2
- `n = 5` → even = 3, odd = 2

Pattern:

```text

even = n - odd
```

Because Java integer division gives floor(n / 2).

## 6) General formula

Each even index contributes 5 choices.
Each odd index contributes 4 choices.

So the answer is:

```text
answer = 5^even × 4^odd
```

where:

```text
odd = n / 2
even = n - odd
```

Final formula:

```text
answer = 5^(n - n/2) × 4^(n/2)
```

Example: `n = 5`

```text
odd = 5 / 2 = 2
even = 5 - 2 = 3

answer = 5^3 × 4^2 = 125 × 16 = 2000
```

## 7) Why we cannot use Math.pow()

For large `n`, values like `5^even` and `4^odd` can become enormous.

The problem requires answer modulo `10^9 + 7`.

So we need modular exponentiation, also called fast power / binary exponentiation.

## 8) Connection with Pow(x, n)

The previous problem taught us:

```text
x^n
```

can be calculated efficiently by dividing `n` by 2.

Instead of:

```text
n -> n - 1
```

we use:

```text
n -> n / 2
```

This is the same idea as:

```text
x^8 = x^4 × x^4
```

and recursively:

```text
x^n = x^(n/2) × x^(n/2)
```

So recursion depth becomes:

```text
O(log n)
```

This is exactly the pattern we reuse here.

## 9) Fast power — even exponent

For even exponent:

```text
x^8 = x^4 × x^4
```

So if `n` is even:

```java
half = power(x, n / 2);
return half * half;
```

---

## 10) Fast power — odd exponent

For odd exponent:

```text
x^5 = x × x^4
```

and since:

```text
x^4 = x^2 × x^2
```

we get:

```text
x^5 = x × x^2 × x^2
```

So for odd `n`:

```java
half = power(x, n / 2);
return x * half * half;
```

## 11) Modulo handling

The problem requires:

```text
answer % MOD
```

where:

```text
MOD = 1,000,000,007
```

We must apply modulo during recursive multiplication, not only at the end.

This is valid because:

```text
(a × b) % MOD = ((a % MOD) × (b % MOD)) % MOD
```

So we do:

```java
long res = (half * half) % MOD;
```

and for odd cases:

```java
return (int)((x * res) % MOD);
```

---

## 12) Java overflow issue

Even if both values are less than `MOD`, their product can still be large.

Example:

```text
a × b
```

can become around `10^18`, which is far greater than `int` max.

So we must use `long` before modulo.

```java
(long) a * b
```

Then apply modulo.

---

## 13) First version of my solution

I first wrote:

```java
return (int) pow(5, even) * pow(4, odd);
```

This had a bug because the multiplication could overflow before the final answer was computed.

Correct version:

```java
(long) pow(5, even) * pow(4, odd) % MOD
```

Also, inside `pow()`, repeated multiplication must stay modulo-safe.

---

## 14) Final solution

```java
class Solution {
    int MOD = 1_000_000_007;

    public int countGoodNumbers(long n) {
        long odd = n / 2;
        long even = n - odd;

        return (int)((long) pow(5, even) * pow(4, odd) % MOD);
    }

    private int pow(int x, long n) {
        if (n == 0) {
            return 1;
        }

        long half = pow(x, n / 2);
        long res = (half * half) % MOD;

        if (n % 2 != 0) {
            return (int)((x * res) % MOD);
        }

        return (int) res;
    }
}
```

## 17) Why this is not a string generation problem

At first, the problem talks about digit strings, which may make us think of generating all strings and checking them.

That is impossible for large `n`.

For example:

- `n = 4` → `10^4` strings
- `n = 50` → `10^50` strings

We should not generate strings.

The correct idea is:

- each position has independent choices
- count choices directly
- multiply them

This converts the problem from string generation to counting + mathematics.

## 27) ADDED — The elegant collapse: `20^(n/2)` (one power, not two)

Your formula `5^even · 4^odd` is correct. But look at what the positions actually do:

```text
   index:   0    1    2    3    4    5    6    7
            E    O    E    O    E    O    E    O
   choices: 5    4    5    4    5    4    5    4
            \___/     \___/     \___/     \___/
              |         |         |         |
             20        20        20        20        <- PAIR THEM UP

   Every (even, odd) PAIR contributes exactly 5 x 4 = 20.

   n = 8  ->  4 complete pairs           ->  20^4
   n = 9  ->  4 complete pairs + 1 even  ->  20^4 · 5
```

**The collapsed formula:**

```text
   answer = 20^(n/2)  ·  (n is odd ? 5 : 1)     (mod 1e9+7)
```

**Why this is strictly better:** two modpow calls become **one**. Same `O(log n)`, but half
the constant factor — and far less code to get wrong.

```java
class Solution {
    private static final long MOD = 1_000_000_007L;

    public int countGoodNumbers(long n) {
        long result = modPow(20, n / 2);            // every complete E-O pair
        if ((n & 1) == 1) {                          // one leftover EVEN position
            result = result * 5 % MOD;
        }
        return (int) result;
    }

    private long modPow(long base, long exp) {
        long result = 1;
        base %= MOD;
        while (exp > 0) {
            if ((exp & 1) == 1) result = result * base % MOD;
            base = base * base % MOD;
            exp >>= 1;
        }
        return result;
    }
}
```

**Verify against your own table:**

```text
   n = 1  ->  20^0 · 5  =  1 · 5   =    5    ✓
   n = 2  ->  20^1      =  20      =   20    ✓
   n = 3  ->  20^1 · 5  =  20 · 5  =  100    ✓
   n = 4  ->  20^2      =  400     =  400    ✓
   n = 5  ->  20^2 · 5  =  400·5   = 2000    ✓
```

> **Interview value:** deriving `5^even · 4^odd` is expected. Spotting the `20^(n/2)` collapse
> is the thing that makes an interviewer nod. **Present both** — show the general derivation
> first, then simplify. That sequence demonstrates you can both *derive* and *optimise*.

## 28) ADDED — Iterative version & a cleaner type discipline

Your recursive `pow` is **correct**, but it fights the type system: `MOD` is an `int`, `pow`
returns an `int`, and you cast at three different places. That's exactly the environment that
produced the bug you documented in §13.

```text
   THE ROOT CAUSE OF THE §13 BUG

   int MOD = 1_000_000_007;
   private int pow(...)          <- returns int

   (int) pow(5, even) * pow(4, odd)
   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   int * int  ->  INT multiplication  ->  overflows at ~2.1e9
                  but the product reaches ~1e18   ✗

   THE FIX YOU FOUND:  (long) pow(...) * pow(...) % MOD     ✓
   THE BETTER FIX:     make MOD and pow() BOTH long.  Then no cast can be forgotten.
```

```text
   MAKE THE TYPES CARRY THE INVARIANT

   ✗ int MOD, int pow()   -> every call site must REMEMBER to cast
   ✓ long MOD, long pow() -> impossible to get wrong; cast ONCE at the return
```

**Iterative, `O(1)` space, one cast total:**

```java
class Solution {
    private static final long MOD = 1_000_000_007L;

    public int countGoodNumbers(long n) {
        long odd  = n / 2;
        long even = n - odd;
        return (int) (modPow(5, even) * modPow(4, odd) % MOD);
        //            ^^^^^^ long  *  long ^^^^^^  -> long arithmetic, safe
    }

    private long modPow(long base, long exp) {
        long result = 1;
        base %= MOD;
        while (exp > 0) {
            if ((exp & 1) == 1) result = result * base % MOD;
            base = base * base % MOD;
            exp >>= 1;
        }
        return result;
    }
}
```

```text
   RECURSION DEPTH CHECK FOR THIS PROBLEM

   n <= 10^15   ->   log2(10^15) ≈ 50   ->   ~50 stack frames

   That is PERFECTLY SAFE. Unlike atoi (where depth = input length),
   recursion here is never a stack risk. So the iterative version is
   about STYLE and CONSTANT FACTOR, not about avoiding a crash.

   SAY THIS. Knowing WHEN recursion depth matters is more impressive
   than reflexively converting everything to loops.
```

## 29) ADDED — Why the modulus is exactly `1,000,000,007`

This number is not arbitrary. Three properties make it the standard choice, and **all three
matter for your code**.

```text
   1. IT IS PRIME
      -> every non-zero residue has a modular INVERSE (Fermat's little theorem)
      -> a^(-1) ≡ a^(MOD-2)  (mod MOD)
      -> so DIVISION becomes possible under the modulus
      -> essential for nCr, probabilities, expected values

   2. IT FITS IN AN int
      1_000_000_007 < 2_147_483_647 = Integer.MAX_VALUE     ✓
      -> results can be stored/returned as int
      -> arrays of results stay compact

   3. ITS SQUARE FITS IN A long           <- THIS is why your (long) cast works
      (MOD - 1)^2 = (1_000_000_006)^2 ≈ 1.0e18
      Long.MAX_VALUE              ≈ 9.22e18
      1.0e18 < 9.22e18                                      ✓

      -> a SINGLE multiplication of two reduced values NEVER overflows a long
      -> which is exactly why  `result * base % MOD`  is safe
```

```text
   THE SAFETY MARGIN, VISUALLY

   0 ────────────── 1e18 ─────────────────────── 9.22e18
                      ^                              ^
                      |                              |
             (MOD-1)^2 lands here            Long.MAX_VALUE
                      |<------- 9x headroom -------->|

   If the modulus were ~4e18 instead, (MOD-1)^2 would be ~1.6e37
   and a plain long multiply WOULD overflow. You'd then need
   Math.multiplyHigh, __int128, or Montgomery multiplication.
```

> **The invariant to state out loud:** *"I keep every value reduced below `MOD` at all times.
> Then any single product is below `MOD² ≈ 10¹⁸`, which fits comfortably in a `long`, so I
> reduce again immediately after each multiply."*

**Bonus — the modular inverse you'd need the moment division appears:**

```java
// Valid only because MOD is PRIME and a is not a multiple of MOD.
long modInverse(long a) {
    return modPow(a, MOD - 2);     // Fermat: a^(p-1) ≡ 1  =>  a^(p-2) ≡ a^(-1)
}
```

# PHASE 2 — CONCEPT REBUILDING

## CONCEPT 1: Count, Don't Generate (The Multiplication Principle)

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because the number of *things* can be astronomically larger than the
number of *decisions*. Here `n` can be `10¹⁵`, so there are more good strings than atoms in
the observable universe — but there are only **two kinds of position** and a single formula.

**What problem does it solve?** It converts an impossible enumeration into arithmetic.

```text
   THE NAIVE INSTINCT              THE COUNTING INSIGHT
   ------------------              --------------------
   "Generate every string,         "Each position's choice doesn't
    check each one, count          depend on any other position's
    the good ones."                choice. So just MULTIPLY the
                                    number of options."

   n = 50  ->  10^50 strings       n = 50  ->  5^25 · 4^25, computed
               (heat death of                   in ~6 multiplications
                the universe)
```

**When to use it:** Whenever the question asks **"how many"** rather than **"list them"**, and
the choices at each step are independent.

### LEVEL 2 — Mental Visualization

```text
   THE POSITION GRID — this is the whole problem in one picture

   index:      0      1      2      3      4      5
             +----+ +----+ +----+ +----+ +----+ +----+

                                 |

        position 0 has 5 options
        for EACH of those, position 1 has 4 options      -> 5 × 4 = 20
        for EACH of those 20, position 2 has 5 options   -> 20 × 5 = 100
        ...

   This is a CARTESIAN PRODUCT. Nothing couples position i to position j.
```

**The tree that shows why it's a product (tiny case, n = 2):**

```text
                        (empty)
         ┌────────┬────────┼────────┬────────┐
         0        2        4        6        8        <- 5 choices at index 0

       2 3 5 7  2 3 5 7  2 3 5 7  2 3 5 7  2 3 5 7    <- 4 choices at index 1

       \_______________________________________/
                         |
             5 branches × 4 leaves each = 20 leaves

   Every subtree has the SAME SHAPE. That identical shape is
   what lets you replace counting leaves with multiplying.
```

**Counting the positions:**

```text
   n = 7        indices:  0  1  2  3  4  5  6
                type:     E  O  E  O  E  O  E
                          ^     ^     ^     ^
                          even positions: 4
                             ^     ^     ^
                             odd positions: 3

   odd  = n / 2      = 7 / 2 = 3     (floor division)
   even = n - odd    = 7 - 3 = 4

   WHY: pairs (0,1)(2,3)(4,5) use up 6 indices = 3 odds.
        Index 6 is left over, and leftovers are always EVEN
        (because pairs always start on an even index).
```

### LEVEL 3 — Real-World Analogy

> **Counting outfits.** You own 5 shirts and 4 pairs of trousers. Nobody lays out all 20
> outfits on the bed to count them — you multiply. The shirt choice doesn't restrict the
> trouser choice, so it's `5 × 4`. That independence *is* the multiplication principle.

> **A combination lock.** A 4-dial lock with 10 digits per dial has `10⁴ = 10,000` codes. You
> don't write them out. And if two dials only allowed 5 values, it'd be `5·10·5·10`.

> **Restaurant menu.** 5 starters, 4 mains, 5 desserts → `100` possible meals. The menu is the
> *positions*; the dishes are the *choices*.

> **Why you don't generate:** asking "how many grains of sand are on this beach" is answered by
> *estimating volume × density*, not by counting grains. Same move.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The problem describes strings, but it only asks for a **count**, and `n` goes up to `10¹⁵`,
> so enumeration is impossible — there are `10^(10¹⁵)` candidate strings. The key observation
> is that the constraints are **positional and independent**: index `i` being even or odd fully
> determines its allowed digit set, and no constraint couples one index to another. So by the
> multiplication principle the answer is the product of the per-position option counts: even
> indices have 5 options (0,2,4,6,8) and odd indices have 4 (2,3,5,7). With `odd = n/2` and
> `even = n − odd`, the answer is `5^even · 4^odd`. And since each even–odd pair contributes
> `5·4 = 20`, that collapses to `20^(n/2)`, times 5 if `n` is odd."*

## CONCEPT 2: Modular Arithmetic Discipline

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because the true answer here has *hundreds of trillions of digits*. No
computer can store it. The modulus lets you compute a **fingerprint** of the answer using
numbers that never exceed `10⁹`.

**What makes it legal?** Modular reduction *commutes* with `+`, `−`, `×`:

```text
   (a + b) mod m = ((a mod m) + (b mod m)) mod m
   (a × b) mod m = ((a mod m) × (b mod m)) mod m

   You may reduce EARLY and OFTEN, and the final answer is unchanged.

   ⚠ BUT NOT DIVISION:
   (a / b) mod m ≠ ((a mod m) / (b mod m)) mod m        ✗
   Division needs the modular INVERSE.
```

### LEVEL 2 — Mental Visualization

```text
   THE CLOCK — why reduction keeps numbers small

        11  12   1
      10    ||     2
     9      ||      3          17 o'clock  ->  5 o'clock
      8            4           29 o'clock  ->  5 o'clock
        7   6   5              The hand's POSITION is all you keep.
                               The laps are discarded.

   17 mod 12 = 5        29 mod 12 = 5

   You never need to store "29". You store "5" and keep going.
```

```text
   WHERE OVERFLOW HIDES — the exact danger zone

   Suppose  a = 999,999,999   and   b = 999,999,999   (both < MOD)

       a * b  =  999,999,998,000,000,001   ≈ 1.0e18

       int  max = 2,147,483,647            ≈ 2.1e9    ->  OVERFLOWS ✗✗✗
       long max = 9,223,372,036,854,775,807 ≈ 9.2e18  ->  FITS       ✓

   SO:  reduced × reduced  needs a LONG, even though both inputs fit an int.

   +-------------------------------------------------------------+
   |  THE RULE:  WIDEN BEFORE YOU MULTIPLY, REDUCE AFTER.        |
   |                                                             |
   |     (long) a * b % MOD        ✓                             |
   |     a * b % MOD               ✗  (int overflow first)       |
   |     (long)(a * b) % MOD       ✗  (cast AFTER the damage)    |
   +-------------------------------------------------------------+
```

```text
   THE CAST-POSITION TRAP (this is your §13 bug, generalised)

   (long) a * b          ->  a widened, THEN long multiply.   ✓ CORRECT
   (long) (a * b)        ->  int multiply OVERFLOWS, then widens garbage. ✗

   The cast must touch an OPERAND, not the RESULT.
```

### LEVEL 3 — Real-World Analogy

> **The odometer / clock.** You only ever record the hand's position, never how many laps.
> That's modular reduction — and it's why the number never grows.

> **Emptying a bucket before it overflows.** Every time you add water, you immediately pour off
> everything above the line. The bucket never bursts. Reduce after *every* operation, not at
> the end.

> **A weighing scale rated to 10 kg.** Two 6 kg items each fit individually, but together they
> break it. Both `a` and `b` fit in an `int`; `a × b` does not. **Use a bigger scale before you
> combine them.**

### LEVEL 4 — Interview Explanation (30 seconds)

> *"The exact answer is astronomically large, so the problem asks for it mod `10⁹+7`.
> Modular reduction distributes over multiplication, so I can reduce after every step instead
> of at the end — that keeps every value below `10⁹`. The subtlety is that a single product of
> two reduced values reaches about `10¹⁸`, which overflows a 32-bit `int` but fits comfortably
> in a 64-bit `long` — that's actually one of the reasons `10⁹+7` was chosen. So I widen the
> operand to `long` **before** multiplying, never cast the result afterwards, and reduce
> immediately. `10⁹+7` is also prime, which matters if I ever need to divide, since I'd then
> use Fermat's little theorem for the modular inverse."*

## CONCEPT 3: Pair-and-Collapse (Finding Structure in a Formula)

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because a repeating pattern in a formula is usually a sign that you're
describing the same unit twice. Collapse the unit and the formula shrinks.

```text
   5 · 4 · 5 · 4 · 5 · 4 · 5 · 4
   \___/ \___/ \___/ \___/
    20    20    20    20          =  20^4

   The alternation E,O,E,O... isn't two interleaved sequences.
   It's ONE repeating unit: the PAIR.
```

### LEVEL 2 — Mental Visualization

```text
   TWO WAYS TO SEE THE SAME STRING

   VIEW 1 — two interleaved sequences (your original)
   ---------------------------------------------------
      E E E E     ->  5^4
      O O O       ->  4^3
      answer = 5^4 · 4^3          TWO powers, two modpow calls

   VIEW 2 — one repeating block (the collapse)
   --------------------------------------------
      [EO][EO][EO][E]
       20  20  20   5
      answer = 20^3 · 5           ONE power, one modpow call


   n = 7:
      ┌──┬──┐┌──┬──┐┌──┬──┐┌──┐
      │E │O ││E │O ││E │O ││E │
      └──┴──┘└──┴──┘└──┴──┘└──┘
        20     20     20     5
        ^                    ^
        |                    |
     n/2 = 3 complete pairs   n is odd -> one leftover EVEN slot
```

**The leftover is always even — here's why:**

```text
   Pairs start at indices 0, 2, 4, 6, ...  (always even)
   So a pair occupies (even, odd).

   If n is EVEN -> all positions pair up perfectly, no leftover.
   If n is ODD  -> exactly one position is left, and it must be the
                   LAST index n-1, which is even when n is odd.

   n = 7 -> last index 6 -> EVEN -> contributes 5.   ✓
```

### LEVEL 3 — Real-World Analogy

> **Buying socks.** A shop sells one left sock for ₹5 and one right sock for ₹4. For 8 socks
> you could compute `4 lefts × ₹5 + 4 rights × ₹4` — or just notice a **pair costs ₹9** and
> multiply by 4. Same answer, half the bookkeeping.

> **Tiling a floor.** You *could* count black and white tiles separately. It's far easier to
> notice the repeating 2-tile motif and count motifs.

> **Egg cartons.** Don't count 24 eggs one by one; count 2 cartons of 12.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"After deriving `5^even · 4^odd`, I noticed the alternation is really a single repeating
> unit: every consecutive (even, odd) index pair contributes `5 × 4 = 20`. There are `n/2`
> complete pairs, and when `n` is odd there's exactly one leftover position — which is always
> an even index, since pairs always begin on even indices — contributing another 5. So the
> whole answer collapses to `20^(n/2) · (n odd ? 5 : 1)`. Same complexity, but one modular
> exponentiation instead of two, and considerably less code to get wrong."*

## 2. STORY METHOD

### The Master Story: **THE HOTEL CORRIDOR**

> You manage a hotel corridor with `n` rooms, numbered from **0**.
>
> **The rule.** Even-numbered rooms may only be painted in one of **5 even colours**
> (0, 2, 4, 6, 8). Odd-numbered rooms may only be painted in one of **4 prime colours**
> (2, 3, 5, 7). Your boss asks: *"How many distinct ways can the whole corridor be painted?"*
>
> **The foolish painter** starts actually painting corridors, one arrangement at a time, to
> count them. With `n = 10¹⁵` rooms he will not finish before the Sun dies.
>
> **The clever manager** notices something crucial: **no rule connects one room to another.**
> Room 4's colour never restricts room 5's colour. So the choices are *independent*, and
> independent choices **multiply**: `5 × 4 × 5 × 4 × …`
>
> **The accountant's trick.** She walks the corridor and sees it isn't an alternating pattern
> at all — it's the **same two-room suite repeated**. Every (even, odd) suite has `5 × 4 = 20`
> colour schemes. `n/2` suites, so `20^(n/2)`. If the corridor has an odd number of rooms, one
> **even** room is left at the end (pairs always start on even numbers), adding a factor of 5.
>
> **The ledger problem.** The total is a number with trillions of digits — no ledger holds it.
> So the boss says: *"Just give me the total **modulo** `1,000,000,007`."* The manager keeps a
> **clock** instead of a ledger: after every multiplication she wraps around and keeps only the
> position. The number never exceeds `10⁹`.
>
> **The scale.** Two numbers each under `10⁹` fit in her small calculator — but their *product*
> reaches `10¹⁸` and breaks it. So before every multiplication she moves to the **big
> calculator** (`long`), multiplies, wraps, and moves the small result back.
>
> **The old tool.** Finally, `20^(500,000,000,000,000)` still needs computing. She doesn't
> multiply 20 by itself half a quadrillion times — she uses the **paper-folding trick** from
> last week (binary exponentiation): ~50 squarings and she's done.

```text
   ROOM:   0    1    2    3    4    5    6
          [E]  [O]  [E]  [O]  [E]  [O]  [E]
           5    4    5    4    5    4    5
           \____/    \____/    \____/    \
             20        20        20       5
                      20^3    ·    5           <- n = 7
```

### Mini-story: **The overflow that bit you (§13)**

> A cashier has two tills, each holding under ₹10⁹ — both fine. Asked for the *product* of the
> two amounts, she writes it in a small ledger box that only holds ₹2.1×10⁹. The true product
> is ₹10¹⁸. The box **silently wraps** and she reports a confidently wrong number. The fix
> isn't a bigger box *afterwards* — **it's writing into the big ledger from the start.**
> `(long) a * b`, never `(long)(a * b)`.

### Mini-story: **Why 10⁹+7**

> Three judges pick the modulus. The **first** insists it be prime, so that division is always
> possible (every non-zero value gets an inverse). The **second** insists it fit in 32 bits, so
> results stay compact. The **third** insists its *square* fit in 64 bits, so a single multiply
> never overflows. `1,000,000,007` satisfies all three — and that third judge is the reason
> your `long` cast is sufficient.

# PHASE 4 — INTERVIEW PATTERN RECOGNITION

## WHEN TO USE: Multiplication Principle (Count, Don't Generate)

```text
   USE WHEN:

   ✓ The question asks "HOW MANY", not "LIST THEM"
   ✓ n is huge (10^9, 10^15, 10^18) -> enumeration is impossible
   ✓ Each position/slot has a FIXED number of options
   ✓ NO constraint couples one position to another
   ✓ The answer is requested MODULO something (a dead giveaway)
   ✓ You can describe the object as "a sequence of independent decisions"

   DO NOT USE WHEN:

   ✗ Choices are DEPENDENT (digit i restricts digit i+1) -> use DP
   ✗ You must avoid duplicates / count DISTINCT results -> inclusion-exclusion
   ✗ Order doesn't matter -> combinations, not products
   ✗ The problem asks you to OUTPUT the objects -> backtracking
```

## WHEN TO USE: Modular Fast Exponentiation

```text
   ✓ "Return the answer modulo 10^9 + 7"
   ✓ An exponent larger than ~10^6
   ✓ Counting problems whose answer explodes
   ✓ You need a modular inverse (-> a^(p-2))
   ✓ Probability / expected value under a modulus
   ✓ Hashing (polynomial rolling hash)
```

```text

       ↓ none
```

# PHASE 8 — FAANG FOLLOW-UP QUESTIONS

**Q1. "Can you do it with one power instead of two?"**
Yes — Section 27. Each (even, odd) pair contributes `5·4 = 20`, so the answer is
`20^(n/2) · (5 if n is odd)`. One `modPow` call instead of two. Same `O(log n)`, half the work.

**Q2. "Do it iteratively — `O(1)` space."**
Section 28. Note the honest nuance: for `n ≤ 10¹⁵` the recursion is only ~50 frames deep, so
recursion is perfectly safe here. Converting is about style and constant factor, **not** about
avoiding a stack overflow — unlike in the atoi problem. Saying that distinction shows judgement.

**Q3. "Why `10⁹+7` specifically?"**
Section 29 — three reasons: prime (modular inverses exist via Fermat), under `2³¹` (fits an
`int`), and `(MOD−1)² ≈ 10¹⁸ < 9.22×10¹⁸` (a single `long` multiply can never overflow).
That third property is precisely why your `(long)` cast is sufficient.

**Q4. "What if the modulus weren't prime?"**
Fermat's little theorem no longer applies. A modular inverse of `a` exists only when
`gcd(a, m) = 1`, and you'd compute it with the **extended Euclidean algorithm** instead.
For composite `m` you could also use Euler's theorem with `φ(m)`, but you must know `φ(m)`,
which needs the factorisation of `m`.

**Q5. "What if the modulus were around `4×10¹⁸`?"**
Then `mod²` overflows `long` and `(long) a * b % MOD` is **wrong**. Options:
`Math.multiplyHigh` (Java 9+) for a 128-bit product, `BigInteger`, `__int128` in C++, or
**Montgomery multiplication** — which is what real crypto libraries use.

**Q6. "What if `n` were `10^100`, given as a string?"**
Two routes. (a) Use **Euler's theorem**: since `MOD` is prime, `a^(MOD−1) ≡ 1`, so reduce the
exponent mod `MOD − 1` — computable digit by digit from the string. (b) Use the **LC 372
digit-wise** approach: `a^(10d+r) = (a^d)^10 · a^r`. Caveat for (a): the reduction is only
valid when `gcd(a, MOD) = 1`; if `a` is a multiple of `MOD` the answer is 0.

**Q7. "Now compute `nCr mod p` — you'll need division."**
Division is undefined under a modulus. Use Fermat: `a⁻¹ ≡ a^(p−2) (mod p)`. So
`nCr = fact[n] · invFact[r] · invFact[n−r] % p`. Precompute `fact[]` in `O(n)`, then
`invFact[n]` with one `modPow` and the rest by the backward recurrence
`invFact[i−1] = invFact[i] · i % p` — giving `O(n)` total instead of `O(n log p)`.

**Q8. "What if there were three alternating position types (period 3)?"**
Same idea, larger block: each complete triple contributes `c₁·c₂·c₃`, so the answer is
`(c₁c₂c₃)^(n/3)` times the partial block's contribution for `n mod 3` leftovers. Generalises
to any period `k`: `(∏cᵢ)^(n/k) · ∏_{i<n mod k} cᵢ`.

**Q9. "What if the constraint coupled adjacent digits — e.g. no two equal neighbours?"**
Independence is destroyed, so the product formula becomes **invalid**. You'd need DP:
`dp[i][d]` = ways to fill the first `i` positions ending in digit `d`. For huge `n`, lift that
DP to **matrix exponentiation** to get back to `O(log n)`. Recognising *when the product
formula stops being legal* is the real test here.

**Q10. "Prove the formula is correct."**
Induction on `n`. *Base:* `n = 1` — only index 0 exists, it's even, 5 choices. ✓ *Step:*
assume the count for length `n` is `5^e·4^o`. Adding index `n` contributes 5 options if `n` is
even and 4 if odd, independently of all previous choices (no constraint references another
index). By the rule of product the total multiplies by exactly that factor, which matches the
updated `e` or `o`. ∎ The crucial clause is **"independently of all previous choices."**

**Q11. "How do you verify it without a proof?"**
Brute-force small `n` (1–6) by actually generating strings, and compare with the formula.
That's ~10⁶ strings for `n = 6` — fast. This **differential testing against a naive oracle** is
the standard way to validate combinatorial formulas, and mentioning it is a strong signal.

**Q12. "What if you needed the k-th good number in lexicographic order?"**
Counting flips into **ranking/unranking**. At each position, count how many completions each
candidate digit allows (a suffix product you already know), and use that to decide which digit
`k` falls under — then subtract and recurse. `O(n · alphabet)`. This is exactly how "k-th
permutation" works.

**Q13. "Can you precompute anything for many queries?"**
If there are `Q` queries with different `n`, each is already `O(log n)` — total `O(Q log n)`,
which is fine. If all `n` are below some bound `N`, precompute prefix products in `O(N)` for
`O(1)` queries. Otherwise caching buys nothing.

**Q14. "Can this be parallelised?"**
The `modPow` chain is sequential (each squaring needs the previous). But the *two* modpows
(`5^even` and `4^odd`) are independent and could run concurrently — a 2× win at best. For
*many* queries it's embarrassingly parallel. Honest answer: **not worth parallelising; it's
already ~50 operations.**

**Q15. "What's the actual running time for `n = 10¹⁵`?"**
`log₂(10¹⁵) ≈ 50`, so ~50 iterations, each a multiply and a modulo — well under a microsecond.
The `O(log n)` here is effectively `O(1)` at any realistic scale.

**Q16. "What if `n = 0`?"**
The empty string vacuously satisfies every constraint, so the answer is **1** (the empty
product). Your formula gives `5⁰·4⁰ = 1` automatically. LC constrains `n ≥ 1`, but **ask** —
it shows you think about domain boundaries.

**Q17. "Could the answer ever be 0?"**
Only if some position had zero valid options. Here every position has ≥ 4, so never. But
beware: the answer mod `10⁹+7` *can* be 0 even when the true count isn't — that's a
fingerprint collision, not a real zero. Worth stating.

**Q18. "How would you test this?"**
(1) Hand-verify `n = 1..5` against `5, 20, 100, 400, 2000`. (2) Brute-force generate for
`n ≤ 6`. (3) Boundary: `n = 1`, `n = 10¹⁵`. (4) Property test:
`f(n+2) == f(n) · 20 mod p`. (5) Compare the two formulas — `5^e·4^o` versus `20^(n/2)·5^(n&1)`
— against each other for random `n`.

**Q19. "What's the security relevance of `modPow`?"**
It's the core primitive of RSA and Diffie–Hellman. Critically, a **naive** implementation leaks
the exponent through timing (the `if (bit)` branch takes longer), so crypto libraries use
**constant-time** ladders (Montgomery ladder) instead. Mentioning side-channel resistance is a
strong differentiator.

**Q20. "What if you had to return the exact answer, not modulo?"**
`BigInteger.valueOf(5).pow(even).multiply(BigInteger.valueOf(4).pow(odd))`. But for
`n = 10¹⁵` the result has ~`7×10¹⁴` digits — hundreds of terabytes. Physically impossible.
**That is exactly why the problem specifies a modulus** — say this; it shows you understand
the constraint's purpose rather than treating it as noise.

**Q21. "Why is the leftover position always even?"**
Pairs occupy `(0,1), (2,3), (4,5), …` — each begins on an even index. So after `n/2` complete
pairs, if one index remains it is index `n−1`, and when `n` is odd, `n−1` is even. Hence the
leftover always contributes 5, never 4.

**Q22. "Derive `even = n − n/2` rigorously."**
Even indices in `[0, n)` are `0, 2, 4, …` — that's `⌈n/2⌉`. Odd indices are `1, 3, 5, …` —
that's `⌊n/2⌋`. In Java, `n/2` is floor for non-negative `n`, so `odd = n/2` and
`even = n − n/2 = ⌈n/2⌉`. ✓

**Q23. "What if even and odd digit sets overlapped — would anything change?"**
No. Independence is about *positions*, not about whether the option sets intersect. Note `2` is
already in **both** sets here (even *and* prime) and the formula is unaffected. Good probe of
whether you actually understand the multiplication principle.

**Q24. "Streaming: `n` grows by one each second — maintain the answer."**
Keep a running `result`. When `n` increments to a new index `i`, multiply by 5 if `i` is even,
by 4 if odd, then reduce. `O(1)` per update. Decrementing would require a modular inverse —
which is `modPow` again.

**Q25. "What if this ran a billion times a second?"**
Use the single-`modPow` form (Q1), keep `MOD` as a `long` constant so the JIT folds it, avoid
the `%` where possible via Barrett/Montgomery reduction, and batch queries to amortise. But
profile first — at ~50 operations per call, the bottleneck is almost certainly elsewhere.

# PHASE 9 — COMMON INTERVIEW MISTAKES

| # | Mistake | Why it's fatal | Fix |
|---|---|---|---|
| 1 | Generating strings to count them | `10^(10¹⁵)` candidates — never terminates | Count with the multiplication principle |
| 2 | `(int) pow(5,even) * pow(4,odd)` | `int × int` overflows at 2.1e9; product is ~1e18 | `(long) a * b % MOD` — cast an **operand** |
| 3 | `(long)(a * b) % MOD` | The `int` multiply already overflowed; cast is too late | Cast before: `(long) a * b` |
| 4 | Applying `% MOD` only at the end | `5^(10¹⁵)` overflows long almost immediately | Reduce after **every** multiply |
| 5 | Swapping even/odd counts | `odd = n/2`, `even = n − odd` — not the reverse | Verify with `n = 3`: even=2, odd=1 |
| 6 | Declaring `MOD` and `pow` as `int` | Forces casts everywhere; invites mistake #2 | Make both `long`; cast once at return |
| 7 | Forgetting `base %= MOD` before the loop | The first squaring can overflow if base ≥ MOD | Reduce the base up front |
| 8 | `n % 2 != 0` instead of `(n & 1) == 1` | Fine for `n ≥ 0`, but wrong if ever reused with negatives | Use the bit test; it states intent |
| 9 | Using `int` for `n` | `n` reaches `10¹⁵`; `int` caps at `2.1×10⁹` | Signature must take `long n` |
| 10 | Using `Math.pow` | Returns a `double`; loses precision past 2⁵³ and can't do modular arithmetic | Write `modPow` with `long` |
| 11 | Assuming positions are dependent | Leads to unnecessary DP; slower and more complex | Check: does any rule reference another index? |
| 12 | Assuming positions are independent when they're not | **The reverse error** — gives a wrong answer silently | If a rule couples indices, you need DP |
| 13 | Two recursive calls in `pow` | `O(n)` instead of `O(log n)` | Store the half in a local (see the Pow note) |
| 14 | Base case `n == 1` in `pow` | Breaks `pow(x, 0)`, which must be 1 | Base case is `n == 0 → 1` |
| 15 | Negative results after subtraction under a mod | Java's `%` can return a negative value | `(a - b + MOD) % MOD` |
| 16 | Dividing under the modulus directly | Division isn't defined in modular arithmetic | Multiply by `b^(MOD−2)` (Fermat) |
| 17 | Not stating the complexity | Interviewers assume you don't know | "`O(log n)` time, `O(1)` space" |
| 18 | Never testing small `n` | Off-by-one in the even/odd split goes unnoticed | Check `n = 1..5` against `5,20,100,400,2000` |
| 19 | Not mentioning why the modulus exists | Looks like you're following a ritual | "The exact answer has ~10¹⁴ digits" |
| 20 | Forgetting the leftover factor in the `20^(n/2)` form | Off by a factor of 5 for odd `n` | `if ((n & 1) == 1) result = result * 5 % MOD;` |

```text

   +---+---------------------------------------------------------+
   | 1 | Trying to generate/enumerate instead of counting        |
   | 2 | int overflow in the final multiply  ((long) a * b)      |
   | 3 | Applying MOD only at the end                            |
   | 4 | Swapping even and odd position counts                   |
   +---+---------------------------------------------------------+
```

## 10-MINUTE REVISION

**The derivation to narrate**

```text
   1. "How many", n up to 1e15 -> CANNOT enumerate (10^(1e15) strings).
   2. Are positions independent? YES — the rule for index i mentions only i.
   3. => multiplication principle: total = product of per-position options.
   4. even index -> {0,2,4,6,8} -> 5     odd index -> {2,3,5,7} -> 4
   5. odd = n/2, even = n - odd          (pairs start even; leftover is even)
   6. answer = 5^even · 4^odd
   7. Collapse: each pair = 5·4 = 20  =>  20^(n/2) · (n odd ? 5 : 1)
   8. Evaluate with binary exponentiation under MOD -> O(log n).
```

**The even/odd split**

| `n` | indices | even | odd | formula | value |
|---|---|---|---|---|---|
| 1 | 0 | 1 | 0 | `5¹·4⁰` | 5 |
| 2 | 0,1 | 1 | 1 | `5¹·4¹` | 20 |
| 3 | 0,1,2 | 2 | 1 | `5²·4¹` | 100 |
| 4 | 0..3 | 2 | 2 | `5²·4²` | 400 |
| 5 | 0..4 | 3 | 2 | `5³·4²` | 2000 |

**Modular safety rules**

```text
   (a + b) % m                      ✓
   (a - b + m) % m                  ✓  (Java % can go negative)
   (long) a * b % m                 ✓  cast the OPERAND
   (long) (a * b) % m               ✗  int overflow already happened
   a / b % m                        ✗  use a · b^(m-2) % m   (m prime)

   Keep everything < MOD  =>  any product < MOD^2 ≈ 1e18  =>  fits long ✓
```

**The modPow shape (write it from memory)**

```text
   long result = 1;  base %= MOD;
   while (exp > 0) {
       if ((exp & 1) == 1) result = result * base % MOD;
       base = base * base % MOD;
       exp >>= 1;
   }
```

**Independence check — the decision that matters most**

```text
   Does the rule for position i mention any OTHER position?
        NO  -> multiplication principle, closed form   (THIS PROBLEM)
        YES -> dynamic programming
               (+ matrix exponentiation if n is huge)
```

## Complexity cheat sheet

| Approach | Time | Space | Verdict |
|---|---|---|---|
| Generate all strings | `O(10ⁿ)` | `O(n)` | Impossible — `n` up to `10¹⁵` |
| DP over positions | `O(n)` | `O(1)` | Too slow — `10¹⁵` steps |

| **`20^(n/2) · 5^(n&1)` + iterative modpow** | `O(log n)` | `O(1)` | **Best — one modpow** |

> **Difficulty:** Easy–Medium · **Interview Difficulty:** The pattern everything else is built on
> **Asked By:** Amazon, Microsoft, Google, Meta, Adobe, Goldman Sachs, Flipkart

```text
   MEMORY HOOK FOR THIS ENTIRE PROBLEM

   EVERY ELEMENT ASKS ONE QUESTION:   "AM I IN, OR AM I OUT?"

                         element i
                        /         \
                    TAKE           SKIP
                   (i+1,          (i+1,
                  str + c)          str)
```

### Missing Concepts

- **Bitmask enumeration:** `for (mask = 0; mask < (1<<n); mask++)` — subset ↔ binary number.
- **The bijection itself:** subset `S` ↔ the `n`-bit number whose `i`-th bit is 1 iff `i ∈ S`.
  This is *why* `|P(S)| = 2ⁿ`.
- **Cascading construction:** begin with `[[]]`; for each element, append a copy of every
  existing subset with that element added. Each step **doubles** the list.
- **`StringBuilder` + un-choose** — the canonical backtracking template.
- **Duplicate handling** (LC 90): sort, then skip `i > start && a[i] == a[i−1]`.
- **Output ordering** — take-first vs skip-first, and lexicographic generation.
- **Subsequence vs substring vs subset** — a precise three-way distinction.
- **Counting vs generating** — `2ⁿ` needs no recursion.
- **Gray code ordering** — enumerate subsets so consecutive ones differ by one element.
- **Why this is the parent of 0/1 Knapsack** — identical take/skip skeleton plus a value/weight
  accumulator and memoisation.

# PART A — CORE NOTES (ORIGINAL, CORRECTED & EXPANDED)

*Your original 19 sections are preserved below. Corrections and additions are marked.*

## 1) Core idea

We are asked to generate all possible subsequences of a string.

For a string like `abc`, valid outputs are:

```text
""
"a"
"b"
"c"
"ab"
"ac"
"bc"
"abc"
```

The empty string is valid.

A subsequence keeps the original relative order of characters.

```text
abc -> "ac" is valid
abc -> "ba" is not valid
```

---

## 2) The real decision

For every character, there are only two choices:

- Take it
- Skip it

This gives the standard recursive pattern:

```text
Take / Not Take
```

For `abc`:

```text
start with a
Take a -> "a"
Skip a -> ""

Then do the same for b
Then do the same for c
```

So each level of recursion represents one character.

---

## 3) Why this is the right structure

The problem is not asking for a single answer.

It is asking for all answers.

That means every character must be explored in both states:

```text
current character can be present or absent
```

This is exactly the subsequence pattern.

---

## 4) Important state

The important state is:

- current index `i`
- current subsequence `str`

Conceptually:

```text
State = (i, str)
```

The original string itself does not change.

Only the index moves forward, and the chosen characters are accumulated into `str`.

---

## 5) Take / Not Take transitions

### Take current character

```java
helper(s, i + 1, str + s.charAt(i), list);
```

### Skip current character

```java
helper(s, i + 1, str, list);
```

Why `i + 1` in both cases?

Because after making the decision for the current character, we move to the next character.

This is the heart of the recursion.

---

## 6) Base case

When all characters have been processed:

```java
if (i == s.length()) {
    list.add(str);
    return;
}
```

This means one complete subsequence has been built.

We store it and stop exploring that branch.

---

## 7) Why empty string is included

If we skip every character:

```text
skip a -> skip b -> skip c -> ""
```

Then the empty subsequence is produced.

That is why `""` must be included in the answer list.

---

## 8) Recursion tree

For `abc`, the structure is:

```text
        ""
      /    \
    take   skip
      a      ""
     / \     / \
   ab  a   b   ""
   / \ / \ / \ / \
 abc ab ac a bc b c ""
```

Each level corresponds to one character.

At every level, we either:

- include the character
- exclude the character

---

## 9) Final Java code

```java
class Solution {

    public ArrayList<String> powerSet(String s) {
        ArrayList<String> list = new ArrayList<>();
        helper(s, 0, "", list);
        return list;
    }

    private void helper(String s, int i, String str, ArrayList<String> list) {
        if (i == s.length()) {
            list.add(str);
            return;
        }

        helper(s, i + 1, str + s.charAt(i), list);
        helper(s, i + 1, str, list);
    }
}
```

---

## 10) Why this works

Every recursive call makes a decision for the current index.

Then it continues with the next index.

Eventually, when `i == s.length()`, we have decided for every character.

At that moment, `str` represents one valid subsequence.

Since we explored both branches at each step, all subsequences are generated.

---

## 11) Complexity

Each character has 2 choices:

```text
Take or Skip
```

Therefore total subsequences = `2^n`.

Time complexity:

```text
O(n * 2^n)
```

because each of the `2^n` strings can have length up to `n`.

Space complexity:

```text
O(n)
```

for recursion stack, plus output storage.

---

## 12) Comparison with ATOI

ATOI is linear recursion:

```text
process current char -> move to next index
```

Power Set is branching recursion:

```text
current char -> take OR skip -> move to next index
```

This difference is important.

- ATOI: one path continues
- Power Set: two paths continue

---

## 13) Comparison with Generate Parentheses

Generate Parentheses:

- multiple choices
- extra constraint
- prune invalid branches

Power Set:

- multiple choices
- no validity constraint
- explore both branches

So:

```text
Generate Parentheses -> Choice + Constraint + Pruning
Power Set -> Choice + Exhaustive Exploration
```

---

## 14) Common mistakes

### Mistake 1: only taking characters

If we only take every character, we miss outputs such as:

```text
""
"a"
"b"
"c"
"ab"
```

So both branches are necessary.

### Mistake 2: forgetting the base case

At `i == s.length()`, we must store the current subsequence.

### Mistake 3: thinking the string must physically shrink

It does not need to shrink.

We can keep the same string and just move the index forward.

### Mistake 4: forgetting the empty subsequence

Skipping every element yields `""`, so it must be included.

---

## 15) Recognition signal

When a problem says:

```text
Generate all subsequences / power set / subsets
```

ask this immediately:

```text
For every element, can I take it or skip it?
```

If the answer is yes, think:

```text
TAKE / NOT TAKE
```

Then define:

```text
helper(index, currentState)
```

where currentState is whatever data the problem needs to carry.

---

## 16) Generic template

```java
void helper(int index, State state) {
    if (index == n) {
        processAnswer();
        return;
    }

    helper(index + 1, takeState());
    helper(index + 1, skipState());
}
```

This is the classic subsequence template.

---

## 17) One-line recall

```text
For every character: take it or skip it, move to next index, and when all characters are processed, save the current subsequence.
```

---

## 18) Final takeaway

The important idea is not memorizing the code.

The important idea is recognizing the pattern:

```text
Element
   /   \
 TAKE  NOT TAKE
   |      |
 recurse  recurse
```

This is the core subsequence pattern.

Once you see it, problems like:

- Power Set
- Subset Sum
- Count Subsets
- 0/1 Knapsack

all start to feel structurally similar.

---

## 19) Final recall questions

Before solving a new problem, ask:

1. Is this asking for subsequences or subsets?
2. For every element, do I have a take/skip decision?
3. What is the current index?
4. What state must I carry?
5. What is the base case?
6. Do I store the answer at the base case?

If the answer to question 2 is yes, start thinking:

```text
TAKE / NOT TAKE
```

That is the memory signal for this pattern.

## 20) ADDED — Every subset IS a binary number (the bitmask solution)

This is the most elegant way to see the problem, and it explains the name.

```text
   THE BIJECTION

   For "abc" (n = 3), number the positions:  a=bit0, b=bit1, c=bit2

   mask  binary   bits set      subset
   ----  ------   --------      ------
     0    000     none          ""
     1    001     a             "a"
     2    010     b             "b"
     3    011     a,b           "ab"
     4    100     c             "c"
     5    101     a,c           "ac"
     6    110     b,c           "bc"
     7    111     a,b,c         "abc"

   EVERY n-bit number  <->  EXACTLY ONE subset.
   There are 2^n n-bit numbers.  Therefore there are 2^n subsets.

   +------------------------------------------------------------------+
   |  "POWER set" is literally named after the POWER of two.          |
   |  |P(S)| = 2^|S|                                                  |
   +------------------------------------------------------------------+
```

```java
// Iterative bitmask enumeration — no recursion, no stack.
public List<String> powerSetBitmask(String s) {
    int n = s.length();
    List<String> result = new ArrayList<>(1 << n);

    for (int mask = 0; mask < (1 << n); mask++) {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < n; i++) {
            if ((mask & (1 << i)) != 0) {       // is bit i set?
                sb.append(s.charAt(i));
            }
        }
        result.add(sb.toString());
    }
    return result;
}
```

```text
   ⚠ OVERFLOW WARNING

        1 << n   overflows int when n >= 31.
        For n up to 62 use  1L << n  and a long loop counter.
        Beyond that, generating is impossible anyway (see §25).
```

### The third approach: cascading construction

```java
// Start with the empty subset; each element DOUBLES the list.
public List<String> powerSetCascading(String s) {
    List<String> result = new ArrayList<>();
    result.add("");                               // the empty subset

    for (char c : s.toCharArray()) {
        int size = result.size();                 // snapshot BEFORE growing
        for (int i = 0; i < size; i++) {
            result.add(result.get(i) + c);        // copy + add c
        }
    }
    return result;
}
```

```text
   THE DOUBLING, VISUALISED

   start:        [""]                                    size 1  = 2^0
   add 'a':      ["", "a"]                               size 2  = 2^1
   add 'b':      ["", "a", "b", "ab"]                    size 4  = 2^2
   add 'c':      ["", "a", "b", "ab",
                  "c", "ac", "bc", "abc"]                size 8  = 2^3

   EACH NEW ELEMENT DOUBLES THE ANSWER — the clearest possible
   demonstration of why the count is 2^n.

   ⚠ Snapshot `size` BEFORE the inner loop, or you'll iterate over
     the items you are appending and loop forever.
```

### Which to use when

```text
   +----------------------+------------------------------------------------+
   | RECURSION (take/skip)| BEST FOR EXPLAINING. Generalises to Knapsack,  |
   |                      | Subset Sum, and every include/exclude problem.  |
   +----------------------+------------------------------------------------+
   | BITMASK              | No stack. Trivially PARALLEL (mask ranges are  |
   |                      | independent). Easy to jump to the k-th subset.  |
   +----------------------+------------------------------------------------+
   | CASCADING            | Simplest to write. Best cache locality.        |
   |                      | Great for showing WHY the count doubles.       |
   +----------------------+------------------------------------------------+

   In an interview: write the RECURSION, then offer the BITMASK.
   Mentioning all three, with reasons, is a strong signal.
```

## 21) ADDED — `StringBuilder` and the canonical backtracking template

Your code uses `str + s.charAt(i)`. That is correct but allocates a new `O(n)` string at **every
node** — the same issue flagged in the Generate Parentheses note.

```java
class Solution {
    public List<String> powerSet(String s) {
        List<String> list = new ArrayList<>();
        helper(s, 0, new StringBuilder(), list);
        return list;
    }

    private void helper(String s, int i, StringBuilder sb, List<String> list) {
        if (i == s.length()) {
            list.add(sb.toString());          // materialise ONLY at a leaf
            return;
        }

        // TAKE
        sb.append(s.charAt(i));               // CHOOSE
        helper(s, i + 1, sb, list);           // EXPLORE
        sb.deleteCharAt(sb.length() - 1);     // UN-CHOOSE   <- MANDATORY

        // SKIP
        helper(s, i + 1, sb, list);           // nothing to undo
    }
}
```

```text
   WHY THE UNDO IS MANDATORY HERE BUT NOT IN YOUR VERSION

   YOUR VERSION:  helper(s, i+1, str + s.charAt(i), list);
                                ^^^^^^^^^^^^^^^^^^
                  a NEW immutable string. The caller's `str` is untouched.
                  Restore is AUTOMATIC. Cost: an O(n) copy per node.

   BUILDER:       ALL frames share ONE buffer.
                  If the TAKE branch doesn't remove its character, the
                  SKIP branch inherits it -> every "skip" secretly takes.
                  -> completely wrong output.

   +------------------------------------------------------------------+
   |  IMMUTABLE = free restore, expensive copies                      |
   |  MUTABLE   = cheap operations, you MUST restore manually         |
   +------------------------------------------------------------------+

   Note the asymmetry: only the TAKE branch needs an undo,
   because only TAKE mutated anything.
```

## 22) ADDED — Output order (and when the judge cares)

Your recursion puts **take first**, which produces a specific, non-obvious order.

```text
   TAKE-FIRST (your code) on "abc":

        "abc", "ab", "ac", "a", "bc", "b", "c", ""

   SKIP-FIRST (swap the two recursive calls):

        "", "c", "b", "bc", "a", "ac", "ab", "abc"

   NEITHER IS LEXICOGRAPHICALLY SORTED.

   LEXICOGRAPHIC ORDER would be:
        "", "a", "ab", "abc", "ac", "b", "bc", "c"
```

```text
   ⚠ CHECK THE PROBLEM STATEMENT.

   Some judges (several GFG variants) require SORTED output.
   Others explicitly say order does not matter (LeetCode 78).

   IF SORTING IS REQUIRED:
        Collections.sort(result);          // O(2^n · n log(2^n)) = O(n^2 · 2^n)

   BETTER: generate in lexicographic order directly.
        Sort the input string first, and at each index recurse
        SKIP-FIRST is NOT enough — true lexicographic order needs
        the "take then extend" ordering:

            for (int j = i; j < n; j++) {     // choose the next element
                sb.append(s.charAt(j));
                list.add(sb.toString());
                helper(s, j + 1, sb, list);
                sb.deleteCharAt(sb.length() - 1);
            }

        with list.add("") done once at the start.
```

> **In an interview, ask:** *"Does the output order matter?"* It takes three seconds and it is
> the difference between Accepted and Wrong Answer on several judges.

## 23) ADDED — What if the input has DUPLICATES? (LC 90)

Your code assumes all characters are distinct. If they aren't, it produces **duplicate
subsequences**.

```text
   INPUT "aab"  with the naive take/skip recursion:

        take a1, take a2, take b  ->  "aab"
        take a1, take a2, skip b  ->  "aa"
        take a1, skip a2, take b  ->  "ab"     <-- DUPLICATE
        take a1, skip a2, skip b  ->  "a"      <-- DUPLICATE
        skip a1, take a2, take b  ->  "ab"     <-- DUPLICATE
        skip a1, take a2, skip b  ->  "a"      <-- DUPLICATE
        skip a1, skip a2, take b  ->  "b"
        skip a1, skip a2, skip b  ->  ""

        8 results, but only 6 DISTINCT: "", "a", "b", "aa", "ab", "aab"

   CAUSE: a1 and a2 are INTERCHANGEABLE, so "take the first, skip the
          second" and "skip the first, take the second" give the SAME set.
```

**The fix — sort, then allow only a contiguous prefix of each duplicate run:**

```java
public List<String> powerSetWithDuplicates(String s) {
    char[] a = s.toCharArray();
    Arrays.sort(a);                            // duplicates become ADJACENT
    List<String> list = new ArrayList<>();
    helper(a, 0, new StringBuilder(), list);
    return list;
}

private void helper(char[] a, int start, StringBuilder sb, List<String> list) {
    list.add(sb.toString());                   // every node is a valid subset

    for (int i = start; i < a.length; i++) {
        if (i > start && a[i] == a[i - 1]) continue;   // skip duplicate siblings
        sb.append(a[i]);
        helper(a, i + 1, sb, list);
        sb.deleteCharAt(sb.length() - 1);
    }
}
```

```text
   WHY  `i > start && a[i] == a[i-1]`  IS THE RIGHT CONDITION

        i > start          -> we are choosing a SIBLING at this level,
                              not the first choice. Skipping the first
                              occurrence would lose "aa" entirely.
        a[i] == a[i-1]     -> this value was already tried at this level.

   EFFECT: from a run of k identical characters you may take
           0, 1, 2, ... k of them — but only as a PREFIX of the run.
           Exactly one representative per multiset. ✓

   ⚠ THE SORT IS MANDATORY. Without it duplicates aren't adjacent
     and the check silently fails.
```

> **The alternative** — collect into a `HashSet` — works but is `O(n·2ⁿ)` extra memory and
> hides the insight. Interviewers want the sort-and-skip version.

## 24) ADDED — Subsequence vs Substring vs Subset (get this straight)

These three are constantly confused, and the confusion produces wrong algorithms.

```text
   FOR "abc":

   +--------------+------------------+-------------------+-------------------+
   |              | CONTIGUOUS?      | ORDER PRESERVED?  | COUNT             |
   +--------------+------------------+-------------------+-------------------+
   | SUBSTRING    | YES              | YES               | n(n+1)/2 + 1 = 7  |
   | SUBSEQUENCE  | NO               | YES               | 2^n = 8           |
   | SUBSET       | NO               | irrelevant (set)  | 2^n = 8           |
   | PERMUTATION  | n/a              | NO                | n! = 6            |
   +--------------+------------------+-------------------+-------------------+

   SUBSTRINGS of "abc":   "", "a", "b", "c", "ab", "bc", "abc"
                          NOT "ac"  <- 'a' and 'c' are not adjacent

   SUBSEQUENCES of "abc": "", "a", "b", "c", "ab", "ac", "bc", "abc"
                          "ac" IS valid   <- order kept, gaps allowed
                          "ca" is NOT     <- order broken

   PERMUTATIONS of "abc": "abc","acb","bac","bca","cab","cba"
                          order may change, ALL elements used
```

```text
   THE ALGORITHM EACH ONE IMPLIES

        SUBSTRING     ->  two nested loops (i, j) or sliding window   O(n^2)
        SUBSEQUENCE   ->  TAKE / NOT TAKE recursion                   O(n·2^n)
        SUBSET        ->  same as subsequence (order is irrelevant)   O(n·2^n)
        PERMUTATION   ->  backtracking with used[] or swapping        O(n·n!)

   +------------------------------------------------------------------+
   |  "CONTIGUOUS" or "SUBARRAY"  ->  window / two pointers, NOT 2^n  |
   |  "SUBSEQUENCE" or "SUBSET"   ->  take/skip, 2^n                  |
   |  "REARRANGE" / "ORDER"       ->  permutations, n!                |
   +------------------------------------------------------------------+

   Misreading "subarray" as "subsequence" turns an O(n) problem into
   an O(2^n) one. This is a VERY common and costly interview slip.
```

# PHASE 2 — CONCEPT REBUILDING

## CONCEPT 1: Take / Not-Take (Include–Exclude)

### LEVEL 1 — Beginner Intuition

**Why does it exist?** Because a subset is defined by a **membership decision per element** —
and those decisions are completely independent of one another.

```text
   THE REFRAME THAT MAKES IT EASY

   ✗ WRONG QUESTION: "what are all the subsets?"   (feels enormous)
   ✓ RIGHT QUESTION: "for THIS one element — in or out?"  (trivial)

   Answer that tiny question n times and every subset appears exactly once.

        element 0:  in or out    (2 ways)
        element 1:  in or out    (2 ways)
        ...
        element n-1: in or out   (2 ways)
                                 ---------
                                  2^n total
```

**Why the index always advances in both branches:**

```text
   helper(i + 1, str + s.charAt(i))    <- TAKE, then move on
   helper(i + 1, str)                  <- SKIP, then move on
             ^
             |
   The decision for element i is FINAL once made.
   You never revisit it. That is what guarantees:
        - every subset is generated (all 2^n combinations of decisions)
        - no subset is generated twice (each is one unique decision path)
```

### LEVEL 2 — Mental Visualization

```text
   THE FULL DECISION TREE FOR "abc"   (left = TAKE, right = SKIP)

                              ""  i=0
                    take a /            \ skip a
                          /              \
                      "a" i=1            "" i=1
                   take/    \skip     take/    \skip
                     /       \          /       \
                 "ab" i=2   "a" i=2  "b" i=2   "" i=2
                  / \        / \       / \      / \
              take  skip  take skip take skip take skip
                /     \    /    \   /    \   /     \
            "abc"  "ab" "ac"  "a" "bc"  "b" "c"    ""
              |      |    |     |   |     |   |     |
            111    110  101   100 011   010 001   000   <- the BITMASK!

   READ THE PATH:  take-take-take = 111 = "abc"
                   take-skip-take = 101 = "ac"
                   skip-skip-skip = 000 = ""

   +------------------------------------------------------------------+
   |  THE DECISION PATH *IS* THE BINARY NUMBER.                       |
   |  8 leaves = 8 subsets = 2^3. Every leaf is an answer.            |
   +------------------------------------------------------------------+
```

**Tracing one path in detail:**

```text
   helper(i=0, str="")      element 'a'
        |
        | TAKE 'a'
        v
   helper(i=1, str="a")     element 'b'
        |
        | SKIP 'b'
        v
   helper(i=2, str="a")     element 'c'
        |
        | TAKE 'c'
        v
   helper(i=3, str="ac")    i == length -> BASE CASE -> add "ac"   ✓

   Decisions: TAKE, SKIP, TAKE  =  1,0,1  =  binary 101  =  5
```

**Why there is nothing to prune (compare with Generate Parentheses):**

```text
   GENERATE PARENTHESES: guards block SOME branches (close<open).
   POWER SET           : NO constraint at all. BOTH branches always legal.

                  =>  the tree is a PERFECT binary tree of depth n
                  =>  2^n leaves, ALL of them answers
                  =>  zero waste, nothing to prune
                  =>  output-optimal (same conclusion, different reason)
```

### LEVEL 3 — Real-World Analogy

> **Packing for a holiday.** You hold each item and ask: *"take it or leave it?"* Every distinct
> combination of those yes/no answers is a different packed suitcase. Ten items → 1,024
> possible suitcases. You never ask "what are all possible suitcases?" — you just answer ten
> small questions.

> **A row of light switches.** `n` switches, each on or off. Every distinct lighting pattern is
> a subset. `n` switches → `2ⁿ` patterns. **This is literally the bitmask.**

> **RSVPs to a party.** Each invited guest independently says yes or no. Every possible
> attendance list is a subset of the invitees.

> **A pizza with `n` optional toppings.** `2ⁿ` possible pizzas — including the plain one (the
> empty set), which is exactly why `""` must be in your answer.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"A subsequence is defined by an independent include-or-exclude decision for each element, so
> I recurse on the index with two branches: take `s[i]` and move to `i+1`, or skip it and move
> to `i+1`. The base case is `i == n`, where the accumulated string is one complete subsequence
> and I record it. Because each element contributes an independent binary choice, there are
> exactly `2ⁿ` leaves — and in fact the decision path *is* the binary representation of the
> subset, which is why an iterative bitmask loop over `0 … 2ⁿ−1` produces the identical answer.
> Time is `O(n·2ⁿ)` since each of `2ⁿ` strings costs `O(n)` to build, and auxiliary space is
> `O(n)` for the recursion depth."*

## CONCEPT 2: Subset ↔ Binary Number (the bitmask bijection)

### LEVEL 1 — Beginner Intuition

**Why does it matter?** Because it converts a *search* problem into *counting from 0 to 2ⁿ−1* —
no recursion, no stack, and it makes the `2ⁿ` obvious rather than asserted.

```text
   THE IDEA IN ONE LINE:

        subset  <->  an n-bit number
        bit i is 1  <=>  element i is IN the subset

   "abc", mask = 5 = binary 101
        bit 0 = 1 -> take 'a'
        bit 1 = 0 -> skip 'b'
        bit 2 = 1 -> take 'c'
        => "ac"
```

### LEVEL 2 — Mental Visualization

```text
   THE ODOMETER VIEW — just count in binary

   mask:  000  001  010  011  100  101  110  111
          ---  ---  ---  ---  ---  ---  ---  ---
   set :   ""   a    b   ab    c   ac   bc  abc

   Counting 0,1,2,...,7 enumerates EVERY subset EXACTLY ONCE,
   because binary representation is unique.

   +------------------------------------------------------------------+
   |  THE RECURSION AND THE BITMASK ARE THE SAME ALGORITHM.           |
   |  The recursion builds the bits depth-first;                      |
   |  the loop builds them by counting.                               |
   +------------------------------------------------------------------+
```

```text
   THE BIT OPERATIONS YOU NEED (memorise these four)

   (mask & (1 << i)) != 0     is element i IN the subset?
   mask | (1 << i)            ADD element i
   mask & ~(1 << i)           REMOVE element i
   mask ^ (1 << i)            TOGGLE element i

   Integer.bitCount(mask)     how many elements are in it
   mask == 0                  is it the empty set?
   (1 << n) - 1               the FULL set (all n bits on)

   ⚠ 1 << n overflows int for n >= 31.  Use 1L << n for n up to 62.
```

```text
   WHY BITMASK IS SOMETIMES STRICTLY BETTER

   ✓ No recursion -> no stack-overflow risk
   ✓ TRIVIALLY PARALLEL: split the range [0, 2^n) across threads;
     each mask is completely independent
   ✓ Direct random access: "give me the 1000th subset" is just mask = 1000
   ✓ Subsets of a fixed size k: iterate masks with Integer.bitCount(mask)==k
   ✓ Enables SUBSET-SUM DP over masks (Travelling Salesman, LC 847, LC 1494)
```

### LEVEL 3 — Real-World Analogy

> **A row of `n` light switches.** Each pattern of on/off is a binary number *and* a subset.
> Walking through every pattern is just counting up in binary.

> **A car odometer.** Turning it from `000` to `999` visits every three-digit number exactly
> once. In base 2 with `n` digits, that's every subset exactly once.

> **A checklist with `n` boxes.** Each box ticked or not. The filled-in checklist *is* a binary
> string and *is* a subset.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"There's a natural bijection between subsets and `n`-bit numbers: bit `i` is set exactly when
> element `i` is in the subset. That immediately proves there are `2ⁿ` subsets, and it gives an
> iterative solution — loop `mask` from `0` to `2ⁿ−1`, and for each mask include element `i`
> whenever `mask & (1 << i)` is non-zero. It's the same algorithm as the recursion, just
> enumerating the decision paths by counting rather than by DFS. I'd prefer it when I want to
> avoid recursion, parallelise across mask ranges, or jump directly to a particular subset. One
> caveat: `1 << n` overflows `int` at `n = 31`, so use `1L << n`."*

## CONCEPT 3: Choose → Explore → Un-choose (with a shared accumulator)

### LEVEL 1 — Beginner Intuition

Identical to the Generate Parentheses note — and that repetition is the point. **One template,
many problems.**

```text
        make the choice        <- CHOOSE      sb.append(c)
        recurse                <- EXPLORE     helper(i+1, ...)
        undo the choice        <- UN-CHOOSE   sb.deleteCharAt(last)

   HERE THE ASYMMETRY IS INSTRUCTIVE:
        the TAKE branch mutates  -> it MUST undo
        the SKIP branch mutates nothing -> nothing to undo
```

### LEVEL 2 — Mental Visualization

```text
   WHAT GOES WRONG WITHOUT THE UNDO  (shared StringBuilder, "ab")

   CORRECT                            BROKEN (no undo after TAKE)
   -------                            ---------------------------
   sb=""                              sb=""
   take 'a' -> sb="a"                 take 'a' -> sb="a"
     take 'b' -> sb="ab" LEAF ✓         take 'b' -> sb="ab" LEAF ✓
     undo    -> sb="a"                  (no undo) sb="ab"
     skip 'b' -> LEAF "a"  ✓            skip 'b' -> LEAF "ab"  ✗ WRONG
   undo      -> sb=""                   (no undo) sb="ab"
   skip 'a'                             skip 'a'
     take 'b' -> sb="b" LEAF ✓            take 'b' -> sb="abb" ✗✗
     ...                                  ...

   The SKIP branch is supposed to mean "element not included" —
   but without the undo it inherits the TAKE branch's character,
   so EVERY skip secretly becomes a take.
```

```text
   THE SHARED-WHITEBOARD PICTURE

        All recursive frames write on ONE whiteboard (the StringBuilder).
        Before handing it to your sibling, RUB OUT what you wrote.

        Your version avoids this by giving every frame its own
        private notepad (a fresh immutable String) — simpler, but
        it costs an O(n) copy at every node.
```

### LEVEL 3 — Real-World Analogy

> **Trying on clothes in a shop.** Put the jacket on (choose), look in the mirror (explore),
> **take it off** (un-choose) before trying the next one. Skip the undo and you leave wearing
> the whole shop.

> **A chess player analysing lines.** Move the piece, look ahead, **move it back**. Forgetting
> to reset the board means every subsequent analysis is nonsense.

> **Borrowing a shared tool.** Put it back where you found it, or the next person can't work.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"With an immutable `String`, `str + c` creates a new object so each frame has its own copy
> and the restore is automatic — but that's an `O(n)` allocation at every node. With a shared
> `StringBuilder` I get `O(1)` appends, but I must explicitly `deleteCharAt` after the take
> branch returns, otherwise the skip branch inherits the character and every 'skip' silently
> becomes a 'take'. Note only the take branch needs an undo, since the skip branch never mutated
> anything. It's the same choose–explore–un-choose idiom as the stack problems: remove, solve,
> restore."*

## CONCEPT 4: The Parent Pattern (Power Set → Knapsack)

### LEVEL 1 — Beginner Intuition

Your §18 spotted this, and it deserves full development: **take/not-take is the skeleton of an
entire problem family.** Learn it once here, where there's no extra complication.

```text
   THE SAME SKELETON, FOUR PROBLEMS

   POWER SET            take -> str + c        |  skip -> str
                        base: collect str

   SUBSET SUM           take -> sum + a[i]     |  skip -> sum
                        base: return sum == target

   COUNT SUBSETS        take -> count(...)     |  skip -> count(...)
                        base: return (sum == target) ? 1 : 0

   0/1 KNAPSACK         take -> val[i] + f(i+1, W - wt[i])   (if it fits)
                        skip -> f(i+1, W)
                        base: return 0;   answer = MAX of the two

   +------------------------------------------------------------------+
   |  IDENTICAL STRUCTURE. ONLY THREE THINGS CHANGE:                  |
   |     1. what you ACCUMULATE  (string / sum / count / value)       |
   |     2. what you COMBINE with (collect / OR / ADD / MAX)          |
   |     3. whether a choice is LEGAL (knapsack: does it fit?)        |
   +------------------------------------------------------------------+
```

### LEVEL 2 — Mental Visualization

```text
   THE EVOLUTION LADDER

   POWER SET                     O(2^n) — you WANT all leaves
        |  "I don't need the subsets, only whether one SUMS to target"
        v
   SUBSET SUM (boolean)          O(2^n) naive
        |  "the same (index, remainingSum) state repeats!"
        v
   + MEMOISATION                 O(n · target)
        |  "flip it bottom-up"
        v
   DP TABLE                      O(n · target) time, O(target) space
        |  "now attach values as well as weights"
        v
   0/1 KNAPSACK                  O(n · W)

   +------------------------------------------------------------------+
   |  THE KEY DIFFERENCE:                                             |
   |  Power Set CANNOT be memoised — you need every leaf, and every   |
   |  leaf is distinct. There are no overlapping subproblems because  |
   |  there is no aggregation.                                        |
   |                                                                  |
   |  Subset Sum CAN be memoised, because many different paths reach  |
   |  the SAME (index, sum) state and you only need one answer,       |
   |  not the paths. AGGREGATION is what creates overlap.             |
   +------------------------------------------------------------------+
```

```text
   WHEN DOES take/skip BECOME DP?

        Do I need to LIST the subsets?          -> NO memoisation possible
                                                   O(2^n) is inherent
        Do I only need a COUNT / MAX / BOOLEAN? -> states overlap
                                                   -> MEMOISE -> DP

   That single question decides exponential vs polynomial.
```

### LEVEL 3 — Real-World Analogy

> **Learning to drive.** You practise the turn in an empty car park (Power Set — no traffic, no
> constraints) before driving in a city (Knapsack — capacity limits, optimisation, deadlines).
> Same skill, increasing complexity.

> **Scales before music.** Take/not-take is the scale. Subset Sum, Count Subsets and Knapsack
> are the pieces you can play once the scale is automatic.

> **A recipe base.** One dough; add sugar for a cake, cheese for a pizza. The skeleton is the
> dough.

### LEVEL 4 — Interview Explanation (30 seconds)

> *"This is the parent of a whole family. The take/not-take skeleton is identical in Subset Sum,
> Count Subsets and 0/1 Knapsack — what changes is only what you accumulate and how you combine
> the two branches: collect for Power Set, OR for Subset Sum, addition for counting, `max` for
> Knapsack. The important distinction is that Power Set **cannot** be memoised, because I need
> every leaf and each is distinct. The moment the problem asks for an aggregate instead of the
> list — a count, a maximum, a yes/no — different paths collapse onto the same `(index, sum)`
> state, overlapping subproblems appear, and it becomes DP in polynomial time."*

## 2. STORY METHOD

### The Master Story: **PACKING FOR THE TRIP**

> You have `n` items on the bed and one suitcase. You want to know **every possible way** to
> pack.
>
> **The overwhelming way.** You try to imagine all the suitcases at once. With 10 items that's
> 1,024 combinations and your mind goes blank.
>
> **The calm way.** You pick up the **first item only** and ask one tiny question: *"In, or
> out?"* Two answers. You put the rest of the decision off until later — because whatever you
> decide about this sock, it doesn't change the choices available for the toothbrush. **The
> decisions are independent.**
>
> So you answer that one small question `n` times. Two choices, `n` times, gives `2ⁿ` suitcases
> — and every single one is different, because any two suitcases must differ on at least one
> item's in/out answer.
>
> **The empty suitcase counts.** Saying "out" to everything is a legitimate way to pack. That is
> why `""` belongs in the answer — it's the **plain pizza** with no toppings.
>
> **The accountant's insight.** Your friend writes each packing plan as a row of ticks and
> crosses: `✓✗✓` means take item 1, skip item 2, take item 3. She then notices these are just
> **binary numbers**: `101`. To list every suitcase she doesn't recurse at all — she simply
> **counts from 0 to 2ⁿ−1**. Same answer, no recursion.
>
> **The shared notebook problem.** You and your siblings share one notebook to record the
> current plan. When you finish exploring "item 1 is IN", you must **cross out that line**
> before your sibling explores "item 1 is OUT" — otherwise their plan silently includes your
> item. That's `deleteCharAt`. And note: only the sibling who **wrote** something needs to
> erase — the "skip" sibling wrote nothing.
>
> **The identical twins.** Two of your socks are indistinguishable. "Take the left, skip the
> right" and "skip the left, take the right" produce the **same suitcase**. To avoid listing it
> twice you line the twins up next to each other (sort) and agree to only ever take a
> **prefix** of the run.
>
> **The limit.** With 30 items there are over a billion suitcases — 32 GB of paper. At that
> point stop listing and just say **"there are 2³⁰ of them."** Counting is free; listing is not.

```text
   ITEM:     sock   brush   book
   DECIDE:    in     out     in
   BINARY:     1      0       1     =  5
   SUITCASE: "sock, book"
```

### Mini-story: **The light switches**

> A corridor has `n` switches. Every distinct lighting pattern is a subset of "switches that are
> on". Flipping through all patterns is literally counting in binary from `0` to `2ⁿ−1`. The
> all-off pattern is the empty set — and it's still a pattern.

### Mini-story: **The pizza menu**

> Start with one plain pizza on the menu. Add *olives* as an option and the menu **doubles** —
> every existing pizza now has a with-olives twin. Add *mushrooms* and it doubles again. After
> `n` toppings the menu has `2ⁿ` pizzas. That's the cascading construction, and it's the
> clearest possible proof of why the count is a power of two.

### Mini-story: **Scales before music**

> A pianist doesn't learn Chopin first; they learn scales. Take/not-take is the scale. Subset
> Sum, Count Subsets and 0/1 Knapsack are the pieces — the same fingering, with more going on.

# PHASE 4 — INTERVIEW PATTERN RECOGNITION

## WHEN TO USE: Take / Not-Take

```text
   USE WHEN:

   ✓ Each element has an INDEPENDENT include/exclude decision
   ✓ The problem says "all subsets / subsequences / combinations"
   ✓ Order within the result must match the original order (or is irrelevant)
   ✓ n is SMALL (<= ~20-25) — the answer is exponential
   ✓ You're building toward Subset Sum / Knapsack (same skeleton)

   DO NOT USE WHEN:

   ✗ The problem says CONTIGUOUS / SUBARRAY / SUBSTRING -> sliding window, O(n)
   ✗ Order may be REARRANGED -> permutations, n!
   ✗ Only a COUNT / MAX / BOOLEAN is needed -> memoise -> DP (polynomial!)
   ✗ n > ~25 and you must LIST them -> physically impossible
```

## WHEN TO USE: Bitmask Enumeration

```text
   ✓ n <= 20-25 and you want to avoid recursion
   ✓ You need subsets of a FIXED SIZE k (filter on Integer.bitCount)
   ✓ You want to PARALLELISE (mask ranges are independent)
   ✓ You need random access to the k-th subset
   ✓ You're doing bitmask DP (TSP, assignment problems)

   ⚠ 1 << n overflows int at n >= 31. Use 1L << n.
```

# PHASE 5 — PROBLEM IDENTIFICATION SYSTEM

## The Master Mapping for THIS problem

```text
   Power Set / All Subsequences
            ↓
   Observation: each element is independently in or out; "generate ALL"
            ↓
   Pattern: Take / Not-Take (include–exclude binary recursion)
            ↓
   Data Structure: index + StringBuilder accumulator (or a bitmask)
            ↓
   Algorithm: helper(i+1, with s[i]) and helper(i+1, without); leaf at i == n
            ↓
   Complexity: O(n·2ⁿ) time | O(n) auxiliary + O(n·2ⁿ) output
```

## Mapping Library — build the reflex

```text
1.  Generate all subsequences / subsets
       ↓ independent in/out per element
       ↓ Take / Not-Take Pattern
       ↓ index + accumulator (or bitmask)
       ↓ take branch + skip branch
       ↓ O(n · 2^n) time, O(n) aux

2.  Generate subsets with duplicates  (LC 90)
       ↓ equal elements are interchangeable
       ↓ Sort + Skip-Sibling Pattern
       ↓ sorted array + start index
       ↓ skip if i > start && a[i]==a[i-1]
       ↓ O(n · 2^n) time

3.  Count subsets (no listing)
       ↓ only the number is asked
       ↓ Combinatorics Pattern
       ↓ none
       ↓ 2^n
       ↓ O(1) time

4.  Subsets of size exactly k  (LC 77)
       ↓ fixed cardinality
       ↓ Combinations Pattern
       ↓ index + current list
       ↓ prune when remaining < needed
       ↓ O(C(n,k) · k) time

5.  Subset Sum — does one sum to target?
       ↓ aggregate, not a list
       ↓ Take/Skip + MEMOISATION Pattern
       ↓ dp[index][sum]
       ↓ OR of the two branches
       ↓ O(n · target) time

6.  Count subsets with a given sum
       ↓ aggregate count
       ↓ Take/Skip + DP Pattern
       ↓ dp[index][sum]
       ↓ ADD the two branches
       ↓ O(n · target) time

7.  0/1 Knapsack
       ↓ maximise value under a weight cap
       ↓ Take/Skip + DP Pattern
       ↓ dp[index][capacity]
       ↓ MAX of the two branches
       ↓ O(n · W) time, O(W) space

8.  Partition Equal Subset Sum  (LC 416)
       ↓ split into two equal halves
       ↓ Subset Sum Pattern
       ↓ boolean dp[sum]
       ↓ target = total/2, must be even
       ↓ O(n · sum) time

9.  Target Sum with +/-  (LC 494)
       ↓ assign a sign to each element
       ↓ Take/Skip (as +/-) Pattern
       ↓ dp map or array
       ↓ reduce to a subset-sum count
       ↓ O(n · sum) time

10. All permutations  (LC 46)
       ↓ ORDER matters, use all elements
       ↓ Backtracking + used[] Pattern
       ↓ boolean[] or in-place swap
       ↓ choose, recurse, un-choose
       ↓ O(n · n!) time

11. Maximum subarray sum  (LC 53)
       ↓ CONTIGUOUS — not a subsequence!
       ↓ Kadane / Sliding Pattern
       ↓ two variables
       ↓ extend or restart
       ↓ O(n) time, O(1) space

12. Longest Increasing Subsequence  (LC 300)
       ↓ subsequence + an ordering constraint
       ↓ DP / Patience Sorting Pattern
       ↓ dp[] or a tails array
       ↓ binary search on tails
       ↓ O(n log n) time

13. Combination Sum  (LC 39)
       ↓ reuse allowed, reach a target
       ↓ Backtracking + Pruning Pattern
       ↓ current list
       ↓ prune when the remainder < 0
       ↓ exponential, pruned

14. Letter Case Permutation  (LC 784)
       ↓ two choices per LETTER only
       ↓ Take/Skip Variant Pattern
       ↓ StringBuilder
       ↓ branch on letters, copy digits
       ↓ O(2^n · n) time

15. Travelling Salesman (small n)
       ↓ visit all, minimise cost
       ↓ Bitmask DP Pattern
       ↓ dp[mask][last]
       ↓ subsets as bitmasks
       ↓ O(2^n · n^2) time
```

# PHASE 8 — FAANG FOLLOW-UP QUESTIONS

**Q1. "Do it iteratively."**
Two ways. **Bitmask:** loop `mask` from `0` to `2ⁿ−1` and include element `i` when
`mask & (1<<i)` is set. **Cascading:** start with `[""]` and, for each element, append a copy of
every existing subset with that element added — the list doubles each step (§20). Both are
`O(n·2ⁿ)` with no recursion.

**Q2. "What if the input has duplicates?"**
Naive take/skip produces duplicate subsets because equal elements are interchangeable. Sort
first so duplicates are adjacent, then at each level skip a value already tried:
`if (i > start && a[i] == a[i-1]) continue;` (§23). This is LC 90 and it's the most common
follow-up.

**Q3. "What if I only need the COUNT?"**
It's `2ⁿ` — no recursion at all, `O(1)`. If the problem asks for a count **with a condition**
(e.g. subsets summing to `k`), that's a DP in `O(n·target)`, not exponential. *Never generate
when you only need a number.*

**Q4. "Avoid the string concatenation."**
`str + s.charAt(i)` allocates and copies `O(n)` at every node. Use a `StringBuilder` with
`append` / `deleteCharAt` and materialise only at the leaf (§21). Note only the **take** branch
needs the undo.

**Q5. "Does the output order matter?"**
**Ask this in the real interview.** Take-first yields `"abc","ab","ac","a","bc","b","c",""`,
which is neither sorted nor the mirror of skip-first. Some judges require lexicographic order —
either sort at the end or generate in lexicographic order directly (§22).

**Q6. "Generate subsets of size exactly `k`."**
Either filter by `Integer.bitCount(mask) == k` in the bitmask loop, or use a start-index
backtracking with pruning: stop early when `remaining elements < still needed`. That's
`O(C(n,k)·k)`, far better than generating all `2ⁿ` and filtering.

**Q7. "What if `n = 40`?"**
You cannot list `2⁴⁰ ≈ 10¹²` subsets. But if the question is a *decision* problem like subset
sum, use **meet in the middle**: split into two halves of 20, enumerate `2²⁰ ≈ 10⁶` sums for
each, sort one half, and binary-search for complements. `O(2^(n/2) · n)` — completely feasible.
This is the key trick for `n ≈ 40`.

**Q8. "Generate them in lexicographic order."**
Sort the input, then use the "extend" formulation: at each level loop `j` from `start` to `n−1`,
append `s[j]`, **record immediately**, recurse from `j+1`, then un-choose. That emits subsets in
lexicographic order naturally (§22).

**Q9. "How does this become 0/1 Knapsack?"**
Identical skeleton. Instead of accumulating a string, accumulate value and weight; instead of
collecting at the leaf, take the `max` of the two branches; and guard the take branch with
"does it fit?". Then notice that many paths reach the same `(index, capacity)` state, memoise,
and you get `O(n·W)` (§Concept 4).

**Q10. "Why can't you memoise Power Set itself?"**
Because you need **every leaf**, and each leaf is a distinct output. Memoisation helps only when
different paths reach an equivalent state *and you only need one answer for it*. Enumeration has
no aggregation, therefore no overlap. **Aggregation is what creates overlapping subproblems.**

**Q11. "What's the exact complexity?"**
`O(n·2ⁿ)` time: `2ⁿ` leaves, `O(n)` to materialise each. `O(n)` auxiliary space (recursion depth
plus the builder). The **output** is `O(n·2ⁿ)` and dominates. Phrase it as *"`O(n)` auxiliary
space excluding the output."*

**Q12. "Can this be parallelised?"**
With bitmasks, beautifully: the mask range `[0, 2ⁿ)` splits into independent chunks with zero
coordination. With recursion, fork the top few levels and give each subtree to a worker. The
tree is perfectly balanced (no pruning), so load balancing is ideal.

**Q13. "The output won't fit in memory."**
Return a **lazy iterator** instead of a list — yield each subset as it's generated, taking
memory from `O(n·2ⁿ)` down to `O(n)`. With bitmasks this is trivial: the iterator's state is
just the current `mask`.

**Q14. "Prove there are exactly `2ⁿ` subsets, with no duplicates."**
Bijection with `n`-bit numbers: map each subset to the number whose bit `i` is 1 iff element `i`
is included. It's injective (different subsets differ in some element, hence some bit) and
surjective (every bit pattern names a subset). There are `2ⁿ` such numbers. ∎

**Q15. "Sum of all subset sums?"**
Each element appears in exactly half the subsets — `2^(n−1)` of them — so the answer is
`(sum of all elements) × 2^(n−1)`. `O(n)`, no generation. This is the **contribution technique**
and interviewers love it.

**Q16. "Generate subsets so consecutive ones differ by exactly one element."**
**Gray code.** The `i`-th Gray code is `i ^ (i >> 1)`. Consecutive Gray codes differ in exactly
one bit, so consecutive subsets differ by exactly one element — useful when each transition is
expensive (e.g. incremental evaluation).

**Q17. "What breaks when `n` gets large?"**
`1 << n` overflows `int` at `n = 31` (use `1L << n`). Memory becomes impossible around `n = 30`
(~32 GB). Recursion depth is only `O(n)`, so the stack is never the binding constraint — the
**output** is.

**Q18. "How would you test this?"**
Check `"" → [""]`, `"a" → ["","a"]`, `"ab" → 4 results. Assert `result.size() == 2^n`. Assert
uniqueness with a `Set`. Cross-check the recursive output against the bitmask output for random
inputs (differential testing). For duplicates, verify the count matches the product of
`(run length + 1)` over distinct values.

**Q19. "Subsets of a `Set<Integer>` rather than a string?"**
Identical algorithm — replace the `StringBuilder` with a `List<Integer>`, and remember to add a
**copy** (`new ArrayList<>(current)`) at the leaf, not the live reference. Forgetting the copy
is an extremely common bug: you end up with `2ⁿ` references to one list that's empty at the end.

**Q20. "Only subsets whose sum is less than `k`?"**
Now pruning becomes possible: if the running sum already exceeds `k` and all values are
positive, abandon the branch. That's the first time this problem gains a guard — and it's what
turns pure enumeration into constrained search.

**Q21. "Compare this with Generate Parentheses."**
Both are backtracking over a binary choice, but Generate Parentheses has **guards**
(`close < open`) that block branches, while Power Set has none — both branches are always legal.
So Power Set's tree is a *perfect* binary tree with `2ⁿ` leaves, whereas Generate Parentheses
has `Cₙ` leaves. Both are output-optimal, for different reasons.

**Q22. "Why is the empty subset included?"**
Because skipping every element is a legitimate sequence of decisions — the all-zeros bitmask.
Formally, `∅ ⊆ S` for every set. Omitting it would give `2ⁿ − 1` results and break the bijection
with `n`-bit numbers.

**Q23. "Subsets of subsets — iterate over all sub-masks of a mask."**
The classic idiom: `for (int sub = mask; sub > 0; sub = (sub - 1) & mask)`, plus the empty
sub-mask. Summed over all masks this is `O(3ⁿ)`, not `O(4ⁿ)` — because each element is in one of
three states (in `sub`, in `mask` but not `sub`, or in neither). Essential for bitmask DP.

**Q24. "Where does this appear in the real world?"**
Feature selection in ML, test-case combination generation, power-set semantics in database query
optimisation (index subsets), configuration/flag combinations, knapsack-style resource
allocation, and any "try every combination" exhaustive search on a small item set.

**Q25. "When is exponential actually acceptable?"**
When `n` is genuinely small and bounded (`n ≤ 20–25`), when the output itself is exponential
(you're *asked* to list everything), or when heavy pruning collapses the practical search space.
Reading the constraint tells you which world you're in — `n ≤ 20` in a problem statement is an
explicit invitation to use `2ⁿ`.

# PHASE 9 — COMMON INTERVIEW MISTAKES

| # | Mistake | Why it's fatal | Fix |
|---|---|---|---|
| 1 | Only exploring the **take** branch | Misses `2ⁿ − 1` subsets | Both branches always recurse |
| 2 | Forgetting the base case | Infinite recursion / index out of bounds | `if (i == n) { record; return; }` |
| 3 | Forgetting `""` belongs in the output | Off-by-one in the result count | Skipping everything produces it naturally |
| 4 | Adding the **live** list instead of a copy | All `2ⁿ` entries alias one (empty) list | `new ArrayList<>(current)` at the leaf |
| 5 | Forgetting `deleteCharAt` with a shared builder | Skip branches inherit taken characters | Undo after the take branch only |
| 6 | String concatenation in the hot path | `O(n)` copy at every node | `StringBuilder`, materialise at leaves |
| 7 | Not handling duplicate inputs | Duplicate subsets in the output | Sort + `i > start && a[i]==a[i-1]` |
| 8 | Using `i > 0` instead of `i > start` in the dedup check | Loses legitimate subsets like `"aa"` | The bound is the level's `start` |
| 9 | Forgetting to **sort** before the dedup check | Duplicates aren't adjacent; check fails silently | `Arrays.sort` first |
| 10 | `1 << n` for `n ≥ 31` | Integer overflow → wrong loop bound | `1L << n` |
| 11 | Ignoring required output order | Wrong Answer on strict judges | Ask; sort or generate in order |
| 12 | Saying space is `O(1)` | Recursion depth is `n` | `O(n)` auxiliary, `O(n·2ⁿ)` output |
| 13 | Omitting the `n` factor in time | Each subset costs `O(n)` to build | `O(n·2ⁿ)`, not `O(2ⁿ)` |
| 14 | Trying to memoise Power Set | There's no overlap — every leaf is distinct | Memoise only when aggregating |
| 15 | Confusing **subsequence** with **subarray** | Turns `O(n)` into `O(2ⁿ)` (or vice versa) | Re-read the word: contiguous or not? |
| 16 | Confusing **subsequence** with **permutation** | Wrong algorithm entirely (`2ⁿ` vs `n!`) | Order preserved ⇒ subsequence |
| 17 | Generating then filtering for a target sum | Exponential when DP is polynomial | Aggregate ⇒ memoise ⇒ DP |
| 18 | Attempting to generate for `n = 30`+ | ~32 GB of output | Count instead, or stream |
| 19 | Not stating the complexity | Interviewers assume you don't know | `O(n·2ⁿ)` time, `O(n)` auxiliary |
| 20 | Not tracing `"ab"` | Trace bugs stay invisible | Dry-run → `["ab","a","b",""]` |

```text

   +---+---------------------------------------------------------+
   | 1 | Adding the LIVE list instead of a copy at the leaf      |
   | 2 | Forgetting duplicate handling (sort + skip)             |
   | 3 | Saying O(1) or O(2^n) space instead of O(n) auxiliary   |
   | 4 | Reading "subarray" as "subsequence" (or vice versa)     |
```

## 2-MINUTE REVISION

```text
   EVERY ELEMENT: "AM I IN, OR AM I OUT?"

        helper(i + 1, state WITH s[i])      <- TAKE
        helper(i + 1, state WITHOUT s[i])   <- SKIP
        base: i == n  ->  record the accumulated state

   n independent binary decisions  =>  2^n subsets
   THE DECISION PATH *IS* THE BITMASK:  101 = take,skip,take = "ac"

   THREE EQUIVALENT WAYS:
        RECURSION   take/skip            <- best to explain, generalises
        BITMASK     mask 0..2^n-1        <- no stack, parallel, random access
        CASCADING   start [""], double   <- simplest, shows WHY it's 2^n

   COMPLEXITY  Time  O(n · 2^n)
               Space O(n) auxiliary  +  O(n · 2^n) OUTPUT (dominates)

   ⚠ Add a COPY at the leaf, not the live list.
   ⚠ StringBuilder: deleteCharAt after the TAKE branch only.
   ⚠ Duplicates? SORT, then `if (i > start && a[i]==a[i-1]) continue;`
   ⚠ 1 << n overflows int at n >= 31 -> use 1L << n
   ⚠ "" is a valid subset. n=30 is ~32 GB — count, don't generate.

   WORD CHECK:  subarray/substring = CONTIGUOUS, n(n+1)/2, O(n) window
                subsequence/subset = gaps OK,     2^n,      take/skip
                permutation        = order changes, n!,     used[]

   HOOK: PACKING A SUITCASE — take it or leave it, n times.
```

## 10-MINUTE REVISION

**The pattern**

```text
   void helper(int i, State state) {
       if (i == n) { record(state); return; }
       helper(i + 1, take(state, a[i]));    // include
       helper(i + 1, state);                // exclude
   }

   The index ALWAYS advances in both branches — the decision for
   element i is final, which is what guarantees no duplicates
   and complete coverage.
```

**The canonical code**

```text
   private void helper(String s, int i, StringBuilder sb, List<String> list) {
       if (i == s.length()) { list.add(sb.toString()); return; }

       sb.append(s.charAt(i));               // TAKE: choose
       helper(s, i + 1, sb, list);           //       explore
       sb.deleteCharAt(sb.length() - 1);     //       un-choose

       helper(s, i + 1, sb, list);           // SKIP: nothing to undo
   }
```

**The tree for `"abc"` (know it cold)**

```text
   take-take-take = 111 = "abc"       take-skip-take = 101 = "ac"
   take-take-skip = 110 = "ab"        take-skip-skip = 100 = "a"
   skip-take-take = 011 = "bc"        skip-skip-take = 001 = "c"
   skip-take-skip = 010 = "b"         skip-skip-skip = 000 = ""

   8 leaves = 2^3.  Every leaf is an answer — nothing to prune.
```

**The three implementations**

| Approach | Code shape | Best for |
|---|---|---|
| Recursion | `take(i+1)` / `skip(i+1)` | Explaining; generalises to Knapsack |
| Bitmask | `for mask in 0..2ⁿ−1` | No stack; parallel; k-th subset |
| Cascading | `[""]`, double per element | Simplest; shows why it's `2ⁿ` |

**Duplicates (LC 90)**

```text
   Arrays.sort(a);                                  // MANDATORY
   for (int i = start; i < n; i++) {
       if (i > start && a[i] == a[i-1]) continue;   // skip duplicate SIBLINGS
       ...
   }
   => from a run of k equal values, take only a PREFIX (0..k of them)
```

**When take/skip becomes DP**

```text
   Need the LIST?          -> no overlap, O(2^n) is inherent
   Need COUNT/MAX/BOOLEAN? -> paths collapse on (index, aggregate)
                              -> MEMOISE -> DP -> polynomial

   Power Set    collect  ->  O(2^n)
   Subset Sum   OR       ->  O(n · target)
   Count Subsets ADD     ->  O(n · target)
   Knapsack     MAX      ->  O(n · W)
```

## The traps, ranked by how often they're sprung

```text
   TRAP 1  Adding the live accumulator instead of a copy.
           With a List<Integer> accumulator you get 2^n references
           to ONE list, which is empty at the end. Silent and baffling.
           With Strings you're safe — which is why this bug hides.

   TRAP 2  "Now the input has duplicates."
           Asked immediately after you finish. Sort + skip siblings.
           Candidates who reach for a HashSet miss the point.

   TRAP 3  "What's the space complexity?"
           O(1) is wrong (depth n). O(2^n) alone is incomplete —
           separate AUXILIARY from OUTPUT.

   TRAP 4  The word check.
           "Subarray" and "subsequence" differ by a factor of 2^n / n^2.
           Interviewers deliberately use the precise word.

   TRAP 5  "Can you memoise it?"
           A trick question. NO — every leaf is distinct. The correct
           answer explains WHY, and notes that Subset Sum CAN be.

   TRAP 6  "What if n = 40?"
           2^40 is a trillion. The expected answer is MEET IN THE MIDDLE
           for decision problems, or "it's impossible to list".

   TRAP 7  Output order.
           Some judges demand lexicographic order. Ask first.
```

## Most frequent follow-ups (in real loops)

1. *"Now handle duplicates."* — near-certain (LC 90).
2. *"Do it iteratively / with bitmasks."*
3. *"What's the space complexity?"*
4. *"Now find a subset that sums to `k`."* — the DP pivot.
5. *"What if `n = 40`?"*
6. *"Only subsets of size `k`."*

## Optimisation discussion — what to say, in order

```text
   1. "There are 2^n subsets and the problem asks me to list them all,
       so exponential output is unavoidable — the algorithm is
       output-optimal. There is nothing to prune: both branches are
       always legal, so every leaf is an answer."

   2. "Time is O(n · 2^n): 2^n leaves, O(n) to materialise each.
       Auxiliary space is O(n) for the recursion depth and the builder;
       the output is O(n · 2^n) and dominates."

   3. "I'd use a StringBuilder rather than string concatenation to avoid
       an O(n) copy at every node — with an explicit undo after the take
       branch, since all frames share the buffer."

   4. "An equivalent iterative form is the bitmask loop, where each subset
       is just an n-bit number. That removes the recursion, parallelises
       trivially, and lets me index directly to the k-th subset."

   5. "If the problem only needed a COUNT, or a max, or a yes/no, I would
       NOT generate — different paths collapse onto the same
       (index, accumulated) state, so I'd memoise and get polynomial time.
       That's exactly how this becomes Subset Sum and 0/1 Knapsack."

   6. "And if n were around 40, listing is impossible, but for a decision
       problem I'd use meet-in-the-middle for O(2^(n/2) · n)."
```

# PHASE 12 — FINAL CHEAT SHEETS

## Complexity cheat sheet

| Approach | Time | Auxiliary space | Notes |
|---|---|---|---|
| **Recursion (take/skip)** | `O(n·2ⁿ)` | `O(n)` | **Explain with this**; generalises to DP |
| Bitmask loop | `O(n·2ⁿ)` | `O(1)` | No stack; parallel; random access |
| Cascading | `O(n·2ⁿ)` | `O(1)` extra | Simplest; shows the doubling |
| With duplicates (LC 90) | `O(n·2ⁿ)` | `O(n)` | Sort first; fewer actual results |
| Subsets of size `k` | `O(C(n,k)·k)` | `O(k)` | Prune; don't filter `2ⁿ` |
| **Count only** | `O(1)` | `O(1)` | It's `2ⁿ` — never generate |
| Meet in the middle (`n≈40`) | `O(2^(n/2)·n)` | `O(2^(n/2))` | Decision problems only |

> Output is always `O(n·2ⁿ)` and **dominates** — state it separately from auxiliary space.

## Code skeleton cheat sheet

```text
   RECURSIVE (canonical)
   ---------------------
   if (i == n) { list.add(sb.toString()); return; }
   sb.append(a[i]);  helper(i+1);  sb.deleteCharAt(sb.length()-1);   // TAKE
   helper(i+1);                                                       // SKIP

   BITMASK
   -------
   for (int mask = 0; mask < (1 << n); mask++) {
       StringBuilder sb = new StringBuilder();
       for (int i = 0; i < n; i++)
           if ((mask & (1 << i)) != 0) sb.append(s.charAt(i));
       result.add(sb.toString());
   }

   CASCADING
   ---------
   result.add("");
   for (char c : s.toCharArray()) {
       int size = result.size();               // snapshot BEFORE growing
       for (int i = 0; i < size; i++) result.add(result.get(i) + c);
   }

   WITH DUPLICATES (LC 90)
   -----------------------
   Arrays.sort(a);
   void helper(int start) {
       list.add(new ArrayList<>(cur));         // COPY!
       for (int i = start; i < n; i++) {
           if (i > start && a[i] == a[i-1]) continue;
           cur.add(a[i]);  helper(i+1);  cur.remove(cur.size()-1);
       }
   }

   ⚠ WITH A List ACCUMULATOR, ALWAYS ADD A COPY AT THE LEAF.
```

## Bit operations cheat sheet

```text
   (mask & (1 << i)) != 0     is element i in the subset?
   mask | (1 << i)            add element i
   mask & ~(1 << i)           remove element i
   mask ^ (1 << i)            toggle element i
   Integer.bitCount(mask)     subset size
   (1 << n) - 1               the full set
   mask == 0                  the empty set

   ITERATE ALL SUB-MASKS OF mask:
       for (int sub = mask; sub > 0; sub = (sub - 1) & mask) { ... }
       // plus sub = 0 separately
       // total over all masks = O(3^n), not O(4^n)

   GRAY CODE (consecutive subsets differ by ONE element):
       gray(i) = i ^ (i >> 1)

   ⚠ 1 << n OVERFLOWS int for n >= 31. Use 1L << n.
```

## Final takeaway (upgraded)

```text
   THREE THINGS TO CARRY OUT OF THIS PROBLEM INTO EVERY OTHER PROBLEM:

   1. REDUCE A HUGE QUESTION TO ONE TINY DECISION
      "What are all the subsets?" is overwhelming. "Is THIS element in
      or out?" is trivial. Answer the tiny question n times and the huge
      one answers itself. That reframing — from the whole solution to a
      single local choice — is the essence of both recursion and DP.

   2. THIS IS THE PARENT PATTERN, NOT A PUZZLE
      Take/not-take is the skeleton of Subset Sum, Count Subsets, Target
      Sum, Partition, and 0/1 Knapsack. Only two things change: what you
      accumulate, and how you combine the two branches (collect / OR /
      ADD / MAX). Learn it here, where nothing else is in the way.

   3. AGGREGATION CREATES OVERLAP; ENUMERATION DOES NOT
      Power Set cannot be memoised because every leaf is a distinct
      required output. The moment the question becomes "how many" or
      "what is the maximum", different paths collapse onto the same
      state, overlapping subproblems appear, and exponential becomes
      polynomial. Knowing WHICH of the two you are in — before you write
      a line — is the difference between O(2^n) and O(n·W).
```
